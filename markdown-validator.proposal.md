# Предложение: починка Markdown-конвейера (валидатор + продюсеры код-блоков)

> Статус: реализовано (Шаги 1–4). Источник: ревью фазы 1 трека
> `bot-ui-dialog-mentor_20260905` (двойное экранирование в create-stream) +
> прод-наблюдение: «внутри блока кода ``` съедаются знаки апострофа `».
> Затрагиваемые файлы: `markdown-validator.ts`, `markdown.ts` (этот каталог),
> `apps/u7-bot/src/controllers/learning/shared.ts`.

## Контекст

Конвейер MarkdownV2:

- **Продюсеры** — `md` / `mdRaw` / `mdConcat` / `mdJoin` (`markdown.ts`) и
  `safeConvert` (контент уроков через пакет `markdown-to-telegram`).
- **Валидатор** — `validateMarkdownV2` / `assertMarkdownV2Safe`
  (`markdown-validator.ts`). Fail-fast последняя линия обороны: вызывается
  в тестах (`assertDialogResponseMarkdownSafe`) и в проде перед отправкой
  в Telegram.

Пакет `markdown-to-telegram` внутри code/pre экранирует корректно:
`` ` `` → `` \` `` и `\` → `\\` (`escapeSymbols(text, 'code')`). Значит путь
`safeConvert` безопасен. Проблемы — в нашем валидаторе и в ручной сборке
блоков кода.

---

## Проблема 1 (Высокая): слепая зона lookbehind — `\\X` считается экранированным `X`

`NEVER_FORMATTING_RE = /(?<!\\)[.!+\-=|#{}()[\]]/g` смотрит ровно на один
символ назад. Для `\\!` (литеральный `\` + голый `!`):

- валидатор видит перед `!` символ `\` → «экранирован, всё ок»;
- но этот `\` уже потреблён парой `\\` — фактически `!` голый;
- Telegram отвечает `400: Character '!' is reserved…`.

| MdText | Валидатор сейчас | Telegram |
|---|---|---|
| `\!` | valid | OK |
| `\\!` | valid (ошибка) | 400 |
| `\\.` | valid (ошибка) | 400 |

Именно так регресс двойного экранирования в create-stream (реплика
«✅ Поток успешно создан!», текст шага даты) прошёл все зелёные ассерты.
Сейчас прикрыт инвариант-тестом `not.toContain('\\\\')` в
`create-stream.test.ts` — но это защита одного файла, а не класса проблемы.

## Проблема 2 (Средняя): подсчёт парности не учитывает `\\X`

В §2 валидатора: `stripped.replace(/\\[_*~`|.!+\-=]/g, '  ')`. Для `\\*`
(литеральный `\` + форматирующая `*`) будет съедена пара `\*` — звёздочка
выпадает из подсчёта парности. Сломанный жирный (`\\*bold*`) пройдёт
валидатор.

## Проблема 3 (Высокая): код-блоки полностью исключены из проверки + продюсер вставляет сырой код

Две связанные части.

### 3а. Валидатор

`stripProtectedSyntax` вырезает ```-блоки и инлайн-код из ВСЕХ проверок.
Но по правилам Telegram внутри pre и code обязательны к экранированию
`` ` `` и `\`. Валидатор это не проверяет — любые голые бэктики и backslash
внутри кода проходят fail-fast.

### 3б. Продюсер `formatStepMessage` (learning/shared.ts)

```ts
// Блок кода: содержимое не форматируется (валидатор вырезает ```...```)
lines.push(md``, mdRaw(`\`\`\`\n${step.code}\n\`\`\``));
```

`step.code` — доменные данные (JS-код шага урока) — вставляется без
экранирования. Комментарий «валидатор вырезает» — иллюзия безопасности:
валидатор не проверяет вырезанное, а Telegram парсит весь текст.

Факты по прод-контенту (`data/courses/steps.json`): из 44 код-шагов —
1 с бэктиком (шаблонные строки JS) и 4 с `\`. Для них в Telegram:

- голый `` ` `` внутри pre — преждевременное закрытие блока / «съедание»
  бэктиков (прод-наблюдение владельца);
- голой `\` «съедает» сам себя и следующий символ: `\n` в коде урока
  отображается как `n`, путь `C:\path` — как `C:path`.

## Проблема 4 (Средняя): регекс инлайн-кода не понимает экранированный бэктик

`` `[^`]+` `` не матчит инлайн-код с корректно экранированным бэктиком
внутри: `` `a\`b` `` не распознаётся как код → содержимое уходит в общие
проверки → ложные срабатывания (и маскировка реальных).

## Прочее (Низкая, зафиксировать)

- Регекс ссылок `\[([^\]]*)\]\([^)]+\)`: `)` внутри URL (Википедия) не
  матчится → содержимое ссылки уйдёт в общие проверки. Наши URL идут через
  `escapeSymbols(text, 'link')` пакета — практический риск низкий.
- `>` в начале строки (blockquote) уже учтён — при переписывании сканером
  сохранить это исключение.

## План правки (producer-first: сначала генераторы, потом ужесточение)

Порядок важен: если ужесточить валидатор раньше продюсеров, прод-отправка
шагов с `\` в коде начнёт падать fail-fast (что честнее, чем съеденный текст,
но лучше чинить источники).

### Шаг 1. Хелпер безопасного код-блока — `markdown.ts`

Red-тест в `markdown.test.ts`:

```ts
// mdCodeBlock экранирует содержимое по правилам pre-entity Telegram
expect(mdCodeBlock('const s = `x\\n${y}`;'))
  .toBe('```\\nconst s = \\\`x\\\\n${y}\\\`;\\n```');
```

(ожидание: `` ` `` → `` \` ``, `\` → `\\`, обёрнуто в ```-блок).

Реализация: `mdCodeBlock(code: string): MdText` — экранировать `\` → `\\`,
затем `` ` `` → `` \` ``, обернуть в ```` ```\n…\n``` ````. Вернуть как
`MdText` (аналог `escapeSymbols(_, 'code')` пакета). Заодно можно добавить
`mdInlineCode(text)` для инлайн-кода (`` `…` `` с теми же двумя escape).

### Шаг 2. Применить в продюсере — learning/shared.ts

Red-тест (unit на `formatStepMessage`): шаг `kind: 'code'` с кодом,
содержащим `` ` `` и `\`, — результирующий MdText не содержит голых
бэктиков внутри блока и проходит ужесточённый валидатор.

Заменить:

```ts
lines.push(md``, mdRaw(`\`\`\`\n${step.code}\n\`\`\``));
```

на:

```ts
lines.push(md``, mdCodeBlock(step.code));
```

### Шаг 3. Переписать валидатор на линейный сканер — markdown-validator.ts

Семантика Telegram: «any character 1–126 can be escaped with preceding `\`».
Сканер слева направо, три состояния:

- **outside**: `\X` поглощает 2 символа (любой X из 1–126); голый
  зарезервированный символ → issue; `` ` `` открывает инлайн-код;
  ```` ``` ```` открывает pre; парность `*` `_` `~` — по счётчику вне
  экранированных последовательностей; `>` вне начала строки — issue.
- **inline code**: валидны только `` \` `` и `\\`; голый `` ` `` закрывает;
  прочие `\X` — issue (внутри code допустимо экранировать только ` и \).
- **pre**: валидны только `` \` `` и `\\`; ```` ``` ```` закрывает;
  одиночный `` ` `` внутри — issue; голый `\` — issue.

Красные тесты в `markdown-validator.test.ts` (кейсы-таблица):

| Вход | Ожидание |
|---|---|
| `\!` | valid |
| `\\!` | **invalid** (unescaped `!`) |
| `\\.` | **invalid** |
| `\\*bold*` | **invalid** (unpaired `*`) |
| `` `code` `` | valid |
| `` `a\`b` `` | valid |
| `` ```\njs\n``` `` | valid |
| `` ```\nfoo`bar\n``` `` | **invalid** (голый ` в pre) |
| `` ```\nC:\\path\n``` `` | valid |
| `` ```\nC:\path\n``` `` | **invalid** (голый `\`) |
| `[t](https://a.b/c)` | valid |

### Шаг 4. Прогон всего репозитория

`bun test` (2039+) — ужесточение не должно уронить существующие тексты.
Если упадут: чинить продюсеры (искать через упавшие ассерты), валидатор
НЕ ослаблять. Инвариант-тест `not.toContain('\\\\')` в create-stream.test.ts
после Шага 3 становится избыточным — оставить как быструю локальную защиту.

## Что НЕ входит

- Экранирование прочих символов (`_` `*` `.` и др.) внутри code — по
  правилам не требуется, а экранированный вариант Telegram отображает
  как есть (допустимо, но не нужно).
- Правка `markdown-to-telegram` (чужой пакет) — его поведение корректно.
