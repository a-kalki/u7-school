# Система сессий — Концепция

> v1 (2026-09-15). Бизнес-концепция модуля `sessions`: зачем школе реестр взаимодействий людей и как он кормит метрики. Уровень документа — концепция продукта; архитектурные детали появятся в spec трека при планировании.

---

## Бизнес-проблема

Метрики навыков строятся на анкетах, но анкета без привязки к событию — мнение без контекста: непонятно, где и при каких обстоятельствах оценивающий видел проявление навыка. Достоверность таких оценок низкая, а накрутка (договорные пятёрки) — ничем не ограничена.

При этом реальные взаимодействия уже существуют (пары на уроках, ревью, разборы), но нигде не фиксируются: анкеты `pair_programming`/`code_review` из [концепции метрик](./metrics-conception.md) повисают в воздухе — их нечем «заземлить».

## Бизнес-решение: сессия как первичная фиксация

**Сессия** — зафиксированное в системе взаимодействие двух и более людей с целью обмена и развития навыков. Сессия — источник наблюдений: анкета, запущенная по завершении сессии, получает обоснование («что», «где», «кто видел»).

### Сущность сессии

| Атрибут | Описание |
|---|---|
| Тип | `pair_programming`, `code_review` — начальные; список расширяем (менторская встреча, групповой разбор, доклад) |
| Участники + роли | Кто участвовал и в какой роли: «программировал» / «смотрел», «автор» / «ревьюер», «ментор» / «студент» |
| Место / контекст | Где происходило: поток, модуль, урок, мероприятие, канал — привязка к уже существующим сущностям либо свободное описание |
| Предмет | Что делали (тема, задача, описание) |
| Статус | `created → completed | cancelled` |
| Время | Начало и завершение |

Роли в сессии определяют, **к кого** анкету запускать по завершении: «смотревший» оценивает «программировавшего», ревьюер — автора (несимметрично; см. [маппинг контекстов](./metrics-conception.md)).

### Жизненный цикл

1. **Создание** — участник, ментор или система (например, при завершении парного урока).
2. **Завершение** — любой участник фиксирует результат; агрегат публикует `session.completed`.
3. **Реакция** — `peer-review` (оркестратор анкет) по событию создаёт задачи-приглашения анкет с контекстом по типу сессии (механика трека 3.1 [документа 3](./metrics-pipeline-and-modules.md) — без изменений).
4. Отменённая сессия анкет не порождает.

## Разграничение ответственности: `sessions` vs `peer-review`

Трек 3.3 [документа 3](./metrics-pipeline-and-modules.md) закладывал `ReviewSession` внутри `peer-review`. Решение этой концепции — разделить:

| Модуль | Ответственность |
|---|---|
| `sessions` | **Что произошло**: реестр сессий, участники, роли, место, статусы, событие `session.completed`. Не знает об анкетах и метриках |
| `peer-review` | **Как оцениваем**: подписка на `module.completed` и `session.completed` → задачи-приглашения анкет. Не хранит сессии |

Правило зависимостей: `peer-review` → `sessions` (читает сессию по событию), не наоборот. `metrics` получает анкеты уже с привязкой к сессии (`triggerEvent`) — контекст достоверности для витрины.

## Пользовательские сценарии

**Парное программирование на уроке.** Пара работала над задачей урока → по завершении урока система (или ментор) фиксирует сессию → «смотревший» получает задачу «оцени напарника» → анкета `pair_programming` → метрики.

**Код-ревью.** Студент отправил работу, ревьюер разобрал → сессия `code_review` → ревьюеру — анкета на автора, автору — опционально на ревьюера.

**Вне программы.** Двое поработали вместе сами (проект, хакатон, просто разобрали задачу) — любой из них фиксирует инициативную сессию → обмен оценками по тем же правилам.

## Открытые вопросы

1. Кто вправе фиксировать сессию: только участники, или свидетель тоже (наблюдатель пары)?
2. Фиксация «задним числом» — разрешать и с каким окном?
3. Подтверждение вторым участником: нужно ли (анти-накрутка) и в какой форме (молчание = согласие)?
4. Модель расширения типов сессий: закрытый enum или kind-модель как в задачах (`TaskKindMeta`)?
5. Порождают ли сессии вклад (менторская встреча — это навык или вклад?) — граница с [contribution-system](./contribution-system.md).
