# Система сбора метрик студента — Глобальная задача

**Назначение:** объединяющий документ для всей системы сбора и анализа метрик студента. Связывает три дочерних документа, каждый из которых делится на треки.

---

## Видение

Человек в школе проявляется в **двух ролях**, и профиль показывает обе:

- **Студент** — развивает навыки. Измеряется метриками навыков (см. ниже).
- **Член сообщества** — развивает школу и сообщество. Измеряется вкладом: кросс-анкеты командных задач + явные фиксации вклада — отдельная инициатива [contribution-system](../contribution-system.md), реализуется после модуля `metrics`.

Метрики навыков: к окончанию курсов мы собираем статистику о том, как студент проявлялся: профессионализм (качество работы, алгоритмическое мышление, владение инструментарием), командные навыки (коммуникативность, инициативность, честность, взаимовыручка), личностные качества (энтузиазм, ответственность, регулярность). Данные собираются через:

- **Анкеты при завершении модуля** — кросс-анкеты: студенты оценивают друг друга, ментор оценивает студентов, студенты — ментора
- **Анкеты по завершении сессий** ([sessions](../sessions-system.md)) — парное программирование («смотревший» оценивает «программировавшего»), код-ревью (ревьюер оценивает автора); сессия даёт анкете контекст достоверности: где, кто, что делали
- **Инициативные отзывы** — любой человек в любой момент: категория → подкатегория → likert-оценка + место/мероприятие (где увидел навык) и описание (что именно было сделано) — см. §4 [концепции метрик](./metrics-conception.md)

Все софт- и хард-скиллы набираются через likert-анкеты (единая шкала 1–5).

Итог: профиль человека с числовыми метриками навыков и (в будущем) баллом вклада + личные рекомендации ментора и студентов → заявка на трудоустройство и отражение роли в сообществе.

### Порядок реализации

```
Документ 2 (EventBus + Aggregate API)  ──┐
                                         ├──> Документ 3 (пайплайн + модули)
Документ 2 (questionnaire модуль) ───────┘

Документ 1 (концепция) — параллельно, задаёт структуру likertMapping
```

Документ 2 должен быть реализован первым, так как даёт инфраструктуру (EventBus, Aggregate API, questionnaire), на которой строится Документ 3. Документ 1 можно прорабатывать параллельно — он не зависит от кода.

⚠️ Документ 3 опирается на [tasks-system](../tasks-system.md) (этап B):
приглашения анкет — задачи модуля `task`. Треки 3.1+ идут после
`task-module` / `task-ui` (треки 1–2 этапа B).

## Ключевые архитектурные решения (приняты в обсуждении)

1. **Модуль `questionnaire`** — чистый движок анкет. Не знает о метриках, но вопросы в пуле содержат метаданные `likertMapping: { category, subcategory, weight }`. При завершении анкеты возвращает не только ответы, но и предвычисленные баллы по категориям.

2. **Иерархия анкет:** `QuestionnaireAr` (абстрактный) → `LikertQuestionnaireAr` (для метрик, умеет выдавать `LikertScore[]`). Онбординг-анкета использует `QuestionnaireFacade` напрямую, без наследования агрегата.

3. **Модель данных анкеты:** `subjectId` (о ком), `respondentId` (кто заполняет), `context` (module_completed/pair_programming/code_review/initiative/wish), `role` (student_student/mentor_student/student_mentor), `triggerEvent` (что породило).

4. **События генерирует агрегат, публикует UseCase.** Агрегат в `ArMeta.events` объявляет возможные события, метод `addEvent()` кладёт их внутрь. UseCase после вызова агрегата и сохранения вызывает `publishEvents(ar)`.

5. **EventBus** — в `core`, интерфейс + `InProcEventBus`. Подписка по типу события (строка). Публикация синхронная в цикле.

6. **Запуск анкеты — два пути (сведено с tasks-system, 2026-09-09):**
   - **Прямой старт** — пользователь инициировал сам действием в боте (онбординг, анкета желания): `QuestionnaireFacade.start(user, pool)` запускает анкету сразу, UI-инициатор делегирует экран в стори `fill` (`delegate`). Задача не создаётся.
   - **Приглашение** — асинхронное предложение («оцени напарника после модуля», «анкета после код-ревью»): модуль-владелец создаёт **задачу** `taskFacade.upsert` (kind `questionnaire.invite`, окно жизни, память отказа), task-модуль зовёт текстом «есть дело — /tasks», кнопка задачи ведёт в контроллер questionnaire. Прежний механику `sendInvite` + проактивные кнопки — легаси до миграции (врем. `invite`, ФР-6 bot-ui).
   Вопросы в пуле содержат метаданные `likertMapping: { category, subcategory, weight }`. При завершении анкеты возвращает не только ответы, но и предвычисленные баллы по категориям.

7. **Новые модули:**
   - `sessions` — реестр взаимодействий людей (парное программирование, код-ревью, ...), событие `session.completed`; реализуется до `metrics` (см. [sessions-system](../sessions-system.md))
   - `questionnaire` — универсальный движок анкет (потребители: `wish`, `peer-review`)
   - `peer-review` — оркестрация кросс-оценок: подписка на `module.completed` и `session.completed`, создание задач-приглашений (task-фасад); учёт самих сессий — в `sessions` (трек 3.3 [документа 3](./metrics-pipeline-and-modules.md) уточнён)
   - `metrics` — хранение и агрегация метрик, витрина профиля (два измерения: навыки + вклад)

8. **Поток для кейса «завершение модуля»:**
   `stream` (ModuleCompleted) → `peer-review` (создаёт задачи-приглашения) → пользователь из `/tasks` → `questionnaire` (анкеты, QuestionnaireComplete) → `metrics` (агрегация)

   Поток для кейса «завершение сессии»: `sessions` (SessionCompleted) → `peer-review` (задачи-приглашения по типу сессии) → далее аналогично.
