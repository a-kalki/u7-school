## 1. Видение

По каждому **мероприятию** школы (учёба в потоке, сессия код-ревью, парное
программирование) модуль собирает **факты**: кто участвовал, что участники
сказали друг о друге (текстовые отзывы) и как оценили (анкеты). Факты — сырьё
для досье студента и его цифрового паспорта.

Каркас — **кампания сбора = окно судьбы одного участника (субъекта)**: личное
событие субъекта (завершил / покинул) → персональное окно → снапшот его
окружения → сбор «по горячим следам». В окне два автора: субъект — о своём
окружении, ментор — о субъекте. Отзыв всегда виден всем участникам; анкета —
раздельная точка входа («Написать отзыв» / «Заполнить анкету»).

Ответственность модуля по слоям карты модулей — [roadmap](../../roadmap.md):
peer-review отвечает на вопрос «**что люди сказали друг о друге?**» — сбор фактов
по мероприятиям; агрегация в досье — модуль `dossier`, предъявление — `passport`,
реестр мероприятий — `sessions`. Термин «досье» закреплён за модулем агрегации
(по одному модулю учёбы и по студенту в целом) — кампании peer-review досье
не называются.

## 2. Ключевые решения

1. **Кампания — сбор фактов, не агрегатор.** Хранит снапшот участников, окно,
   собранные отзывы и (в будущем) анкетные оценки. «Все цифры по модулю» для
   паспорта — агрегация модуля `dossier` (композиция фасадов peer-review /
   sessions / stream); сам peer-review формулы агрегации не содержит.
   Отклонённая альтернатива (обсуждено с владельцем): «агрегирующая кампания
   модуля с дочерними досье сессий» — ломает границу сбора/агрегации: к какому
   модулю относится сессия, знает `sessions` (поле места), собирать их по скоупу —
   задача `dossier`, а не кампании.
2. **Контекст `stream_fate` — «судьба студента в потоке определена».** Триггеры —
   личные события студента: `student.completed` (завершил) и `student.abandoned`
   (покинул), оба уже существуют. Кампания **персональная**: ключ
   `(scopeId, subjectId)` — у участника одно окно на поток, открывается сразу
   по событию (ушедший не ждёт конца потока). Ядро кампании: `scopeId`,
   `subjectId`, `participants` — только id адресуемых соучеников (без ролей и
   статусов; состав фильтрует ER по событию: «завершил» → завершившиеся и
   ещё учащиеся без субъекта, «покинул» → пусто), специфика контекста — в
   payload: `subjectOutcome` (4-значная проекция исхода субъекта) и `mentorId`
   (второй автор окна). **Кампании ментора нет**: ментор пишет о субъекте в
   кампании субъекта — свежий отзыв и о покинувшем, в момент события.
   `stream.completed` peer-review не потребляет: инвариант терминальности
   гарантирует, что все кампании потока созданы до его закрытия. Каркас общий,
   специфика контекстов — в payload (дискриминант `context`); сессионные,
   курс — добавляются без смены каркаса.
3. **Отзыв — отдельная запись на пару** (кампания, автор, адресат), перезапись
   в пределах окна; хранит `direction` («кто о ком»: student_student /
   student_mentor / mentor_student — невозможная пара исключена типом) и
   снапшот `authorOutcome` исхода автора-студента (рендер «статуса автора»
   и будущие веса в досье; ментору исхода нет). Правила адресации — в
   агрегате кампании (данные payload; политика `ReviewPolicy` упразднена):
   субъект → `participants` + ментор, ментор → только субъект, никогда —
   отзыв о себе.
4. **Окно жизни хранится, не вычисляется на лету**: `expiresAt` фиксируется при
   создании кампании от момента события субъекта; константы окон — в домене
   пакета, свои значения по контекстам (7 дней для `stream_fate` — утверждено).
5. **Создание кампаний — доменная фабрика** по образцу анкет
   (`QuestionnaireFactory` в `questionnaire`): фабрика с create-методами по типу
   кампании и `restore(state)` по дискриминанту. Фабрику вызывает ER.
6. **Создание кампаний — ER, не UC** (решение 2026-09-18): операция чисто
   реактивная — UI её никогда не вызывает. Одна мультисобытийная реакция на
   `student.completed` + `student.abandoned` сама оркестрирует: идемпотентность
   по `(scopeId, subjectId)`, сбор состава фасадом stream, фабрика, сохранение,
   публикация `campaign.created` — канон содержательных ER (модуль `wish`).
   UC — только для пользовательских операций (написать отзыв, читать кампании).
7. **Анкетная фиксация (будущее) — не движок.** Результат анкеты по мероприятию
   фиксируется записью (кто, кого, контекст, баллы) из события
   `questionnaire.completed`; движок анкет — `questionnaire`, не дублируется.

## 3. Статусы и признаки студента: единый API

Решение владельца (v3): терминальные исходы студента выражаются **статусом +
признаками**, а знания о них инкапсулируются API агрегата студента — клиенты
(снапшоты кампаний, UI-лейблы, досье) не разбирают состояние сами:

| Статус (хранение, без изменений) | Категория | Признаки |
|---|---|---|
| `advanced` | завершил | прошёл |
| `not_advanced` | завершил | не прошёл |
| `abandoned` (+`abandonDetails`: `who`, `cause`) | забросил | не начал (нет завершённых шагов) · ушёл сам (`voluntary`) · снят ментором (`by_mentor`, `inactivity`) |

- Схема хранения статусов **не меняется** (гейтинг, события, существующие
  переходы); новый слой — read-API: категория исхода, признаки, словарь
  продуктовых меток («окончил», «окончил, не прошёл», «забросил», «не начал»,
  «покинул сам», «снят ментором») — единый источник для клиентских зон stream
  (карточки, мониторинг).
- **Решение владельца (v4.1, 2026-09-20): peer-review не копирует студенческий
  словарь.** У кампаний отзывов — собственная проекция исхода из четырёх
  значений: `completed_passed` «завершил и прошел» /
  `completed_not_passed` «завершил и не прошел» / `dropped` «забросил» /
  `never_started` «не начал» (вычисляется ER через read-API при создании
  кампании; исход субъекта всегда терминальный, `in_progress`-исход удалён).
  Разделение «прошёл / не прошёл» peer-review хранит сам — оно выбирает
  тексты-подсказки и лейблы автора отзыва. Каждый клиентский модуль строит
  от себя ту проекцию, от которой зависит его логика, а не тащит чужой
  словарь.
- **Адресация (решение 2026-09-18):** субъект «завершил» → ментор + соученики
  «завершил»/«ещё учился» по снапшоту; субъект «забросил»/«не начал» → только
  ментор (о том, что не подошло); ментор → только субъект (в т.ч. о покинувшем —
  отзыв для студента, если вернётся). Никогда — отзыв о себе. Правила —
  доменная политика по роли/исходу автора и снапшоту кампании.
- **Инвариант терминальности при завершении потока** (обнаружен при обследовании:
  UC блокировал только `active`, студент `enrolled` мог «зависнуть» навсегда):
  завершение потока требует терминального статуса у каждого студента; `active` и
  `enrolled` блокируют — ответственность агрегата потока. До завершения ментор
  разрешает судьбу каждого.
- Реализация — отдельный трек `student-status` (зона `stream`), до треков
  peer-review: их снапшоты и лейблы пользуются готовым API.

## 4. Техдолг модуля (осознанные deferred-решения)

1. **Анкеты в кампании.** Кнопка «Заполнить анкету» рядом с отзывами: запуск
   анкет через фасад `questionnaire` с ownerInfo кампании (контекст, subjectId);
   фиксация результатов (см. §2.7) событием; пулы вопросов по контекстам.
   Делается после этапа «отзывы»; имя агрегата фиксации и место пулов — при
   планировании того этапа.
2. **Приглашения — задачи.** Доставка приглашений (сейчас временная механика
   `invite`, ФР-6 bot-ui) заменяется задачами модуля `task` после его появления;
   домен peer-review при этом не меняется.
3. **Сессионные кампании.** Контексты по завершению сессий (парное
   программирование, код-ревью) — после модуля `sessions`.

> Пункт «Перенос триггеров на персональные события» (v3) реализован в v4 —
> персональные кампании судьбы студента (§2.2); открытый вопрос дублей отзывов
> о менторе закрыт конструктивно: у автора одна кампания на поток.
