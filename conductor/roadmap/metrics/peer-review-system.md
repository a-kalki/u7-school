## 1. Видение

По каждому **мероприятию** школы (завершение студентом потока, сессия код-ревью,
парное программирование, выход из учёбы) модуль собирает **факты**: кто участвовал,
что участники сказали друг о друге (текстовые отзывы) и как оценили (анкеты).
Факты — сырьё для досье студента и его цифрового паспорта.

Каркас — **кампания сбора**: событие-триггер → снапшот участников → окно жизни →
сбор. Отзыв всегда виден всем участникам; анкета — раздельная точка входа
(«Написать отзыв» / «Заполнить анкету»).

Ответственность модуля по слоям карты модулей — [roadmap](../../roadmap.md):
peer-review отвечает на вопрос «**что люди сказали друг о друге?**» — сбор фактов
по мероприятиям; агрегация в досье — модуль `dossier`, предъявление — `passport`,
реестр мероприятий — `sessions`. Термин «досье» закреплён за модулем агрегации
(по одному модулю учёбы и по студенту в целом) — кампании peer-review досье
не называются.

## 2. Ключевые решения

1. **Кампания — сбор фактов, не агрегатор.** Хранит снапшот участников, окно,
   собранные отзывы и (в будущем) анкетные оценки. «Все цифры по модулю» для
   паспорта — агрегация модуля `dossier` (композиция фасадов peer-review /
   sessions / stream); сам peer-review формулы агрегации не содержит.
   Отклонённая альтернатива (обсуждено с владельцем): «агрегирующая кампания
   модуля с дочерними досье сессий» — ломает границу сбора/агрегации: к какому
   модулю относится сессия, знает `sessions` (поле места), собирать их по скоупу —
   задача `dossier`, а не кампании.
2. **Контекст `stream_completed` — «студент завершил поток».** Студент проходит
   модуль курса через поток (терминология §шапки), повод кампании — завершение
   студентом потока. Сейчас триггер — событие завершения потока (`stream.completed`):
   кампания «зацепляет» всю группу сразу, скоуп — поток. В будущем триггер
   переносится на личное событие студента (`student.completed` — уже существует):
   приглашения по горячим следам (техдолг §4.1). Имя контекста — о студенте, а не
   о факте закрытия потока: смена триггера не меняет имя и семантику. Каркас
   кампании общий, специфика контекстов — в payload (дискриминант `context`);
   `exit`, сессионные, курс — добавляются без смены каркаса.
3. **Отзыв — отдельная запись на пару** (кампания, автор, адресат), перезапись
   в пределах окна; правила адресатов — доменная политика по статусу автора.
4. **Окно жизни хранится, не вычисляется на лету**: `expiresAt` фиксируется при
   создании кампании; константы окон — в домене пакета, свои значения по контекстам
   (7 дней для `stream_completed` — утверждено).
5. **Создание кампаний — доменная фабрика** по образцу анкет
   (`QuestionnaireFactory` в `questionnaire`): фабрика с create-методами по типу
   кампании и `restore(state)` по дискриминанту. UC вызывает фабрику.
6. **Анкетная фиксация (будущее) — не движок.** Результат анкеты по мероприятию
   фиксируется записью (кто, кого, контекст, баллы) из события
   `questionnaire.completed`; движок анкет — `questionnaire`, не дублируется.

## 3. Статусы и признаки студента: единый API

Решение владельца (v3): терминальные исходы студента выражаются **статусом +
признаками**, а знания о них инкапсулируются API агрегата студента — клиенты
(снапшоты кампаний, UI-лейблы, досье) не разбирают состояние сами:

| Статус (хранение, без изменений) | Категория | Признаки |
|---|---|---|
| `advanced` | завершил | прошёл |
| `not_advanced` | завершил | не прошёл |
| `abandoned` (+`abandonDetails`: `who`, `cause`) | забросил | не начал (нет завершённых шагов) · ушёл сам (`voluntary`) · снят ментором (`by_mentor`, `inactivity`) |

- Схема хранения статусов **не меняется** (гейтинг, события, существующие
  переходы); новый слой — read-API: категория исхода, признаки, словарь
  продуктовых меток («окончил», «окончил, не прошёл», «забросил», «не начал»,
  «покинул сам», «снят ментором») — единый источник для UI и снапшотов.
- **Инвариант терминальности при завершении потока** (обнаружен при обследовании:
  UC блокировал только `active`, студент `enrolled` мог «зависнуть» навсегда):
  завершение потока требует терминального статуса у каждого студента; `active` и
  `enrolled` блокируют — ответственность агрегата потока. До завершения ментор
  разрешает судьбу каждого.
- Реализация — отдельный трек `student-status` (зона `stream`), до треков
  peer-review: их снапшоты и лейблы пользуются готовым API.

## 4. Техдолг модуля (осознанные deferred-решения)

1. **Перенос триггеров на персональные события.** Сейчас кампания
   `stream_completed` создаётся по `stream.completed` — «зацепляем» всех студентов
   завершающихся потоков (включая давно ушедших), а exit-кампаний нет вовсе.
   После отработки текущих потоков: `stream_completed` → триггер `student.completed`
   (студент завершил поток — приглашение сразу), `exit`-кампания → триггер
   `student.abandoned` (ушёл — сразу). При переносе переосмыслить форму: групповое
   окно потока может уступить персональным кампаниям по горячим следам. Открытые
   вопросы: дубль отзывов о менторе при пересечении с кампанией потока, окна.
2. **Анкеты в кампании.** Кнопка «Заполнить анкету» рядом с отзывами: запуск
   анкет через фасад `questionnaire` с ownerInfo кампании; фиксация результатов
   (см. §2.6) событием; пулы вопросов по контекстам. Делается после этапа
   «отзывы»; имя агрегата фиксации и место пулов — при планировании того этапа.
3. **Приглашения — задачи.** Доставка приглашений (сейчас временная механика
   `invite`, ФР-6 bot-ui) заменяется задачами модуля `task` после его появления;
   домен peer-review при этом не меняется.
4. **Сессионные кампании.** Контексты по завершению сессий (парное
   программирование, код-ревью) — после модуля `sessions`.
