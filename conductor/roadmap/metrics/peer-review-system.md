## 1. Видение

По каждому **мероприятию** школы (завершение модуля, сессия код-ревью, парное
программирование, выход из учёбы) школа собирает **досье**: кто участвовал, что
участники сказали друг о друге (текстовые отзывы) и как оценили (анкеты). Досье —
основа метрик студента и его цифрового паспорта.

Каркас — **кампания**: событие-триггер → снапшот участников → окно жизни →
сбор. Отзыв всегда виден всем участникам; анкета — раздельная точка входа
(«Написать отзыв» / «Заполнить анкету»).

Ответственность модуля по слоям карты модулей — [roadmap](../../roadmap.md):
peer-review отвечает на вопрос «**что люди сказали друг о друге?**» — сбор фактов
по мероприятиям; агрегация цифр — `metrics`, предъявление — `passport`, реестр
самих мероприятий — `sessions`.

## 2. Ключевые решения

1. **Кампания — «досье мероприятия», не агрегатор.** Хранит снапшот участников,
   окно, собранные отзывы и (в будущем) анкетные оценки. «Все цифры по модулю»
   для паспорта — композиция фасадов peer-review / sessions / metrics; сам
   peer-review формулы агрегации не содержит.
2. **Один каркас кампании, специфика — в данных контекста** (дискриминант
   `context`: `stream_completed` сейчас; `exit`, сессионные, курс — добавляются
   без смены каркаса). Новые типы кампаний не меняют репозиторий и сериализацию.
3. **Отзыв — отдельная запись на пару** (кампания, автор, адресат), перезапись
   в пределах окна; правила адресатов — доменная политика по статусу автора.
4. **Окно жизни хранится, не вычисляется на лету**: `expiresAt` фиксируется при
   создании кампании; константы окон — в домене пакета, свои значения по контекстам
   (7 дней для потока — утверждено).
5. **Создание кампаний — доменная фабрика** по образцу анкет
   (`QuestionnaireFactory` в `questionnaire`): фабрика с create-методами по типу
   кампании и `restore(state)` по дискриминанту. UC вызывает фабрику.
6. **Анкетная фиксация (будущее) — не движок.** Результат анкеты по мероприятию
   фиксируется записью (кто, кого, контекст, баллы) из события
   `questionnaire.completed`; движок анкет — `questionnaire`, не дублируется.

## 3. Статус «не начал» (enrolled): завершение потока блокируется

Обнаружено при обследовании: UC завершения потока блокировался только статусом
`active` — студент, не начавший учёбу (`enrolled`), мог навсегда остаться
«зависшим» в завершённом потоке.

**Решение:** завершение потока требует **терминального статуса у каждого**
студента (`abandoned` / `advanced` / `not_advanced`). Студенты `active` и
`enrolled` блокируют завершение — это инвариант агрегата потока: до завершения
ментор разрешает судьбу каждого (снятие с учёбы или завершение). Так снапшот
кампании всегда однозначен.

**Различать ли «не начал» и «забросил»?** Шестой статус не вводим: студент,
не начавший, уходит через снятие с учёбы (`abandoned`). Различие при этом
**сохраняется как выводимый признак** — нет ни одного завершённого шага — и
фиксируется в снапшот кампании (`neverStarted`):

- утверждённые тексты спеки различают диалог («Почему так и не начали учёбу?»
  против «Почему забросили?») — им нужен признак, а не статус;
- для школы это разные воронки: «не начал» — проблема ожиданий/онбординга,
  «забросил» — проблема удержания; цифровой паспорт показывает их по-разному;
- цена признака нулевая (вычисляется из данных студента при создании кампании).

Если владелец позже решит упростить — признак убирается одной правкой снапшота
и склейкой текстов, статусная модель не меняется.

## 4. Техдолг модуля (осознанные deferred-решения)

1. **Exit-кампании: перенос триггеров на персональные события.** Сейчас реакция
   кампаний висит на `stream.completed` — так «зацепляются» все студенты текущих
   завершающихся потоков (включая давно ушедших). После отработки текущих
   потоков логика переносится на **личные события** студентов
   (`student.abandoned`, `student.completed` — оба уже существуют): ушёл или
   завершил — приглашение сразу, отзывы по горячим следам. Вопросы к переносу:
   дубль отзывов о менторе при пересечении с кампанией потока, окно exit-кампании.
2. **Анкеты в кампании.** Кнопка «Заполнить анкету» рядом с отзывами: запуск
   анкет через фасад `questionnaire` с ownerInfo кампании; фиксация результатов
   (см. §2.6) событием; пулы вопросов по контекстам. Делается после этапа
   «отзывы»; имя агрегата фиксации и место пулов — при планировании того этапа.
3. **Приглашения — задачи.** Доставка приглашений (сейчас временная механика
   `invite`, ФР-6 bot-ui) заменяется задачами модуля `task` после его появления;
   домен peer-review при этом не меняется.
4. **Сессионные кампании.** Контексты по завершению сессий (парное
   программирование, код-ревью) — после модуля `sessions`.
