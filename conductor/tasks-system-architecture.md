# Система задач — Архитектура модуля (Этап B)

> v1 (2026-09-03). Выдержки и решения сессии проработки концепции: архитектурное
> решение по «кнопкам в задачах» и черновая декомпозиция на треки. Бизнес-обоснование
> — в [tasks-system.md](./tasks-system.md) (не дублируется). Проработка по слоям
> состоялась — [tasks-system-scenarios.md](./tasks-system-scenarios.md) и
> [tasks-system-layers.md](./tasks-system-layers.md).

---

## Контекст

Этап A (трек `user-notify_20260902`) реализовал механизм чистых уведомлений:
`userFacade.notify` → событие `user.notified` → `NotifyStory`. На миграцию остались
кнопочные проактивы: бездействие (#1/#2 — InactivityStory), «Следующий модуль»
(#3 — HubStory), приглашения в анкеты (#4 — InviteStory). Плюс новая сущность —
«возможность меню» «Покинуть учёбу» (#5, без ожидания 5 дней бездействия).

## Развилка: кто рендерит кнопки задач

Рассмотрены варианты:

1. **Центральный switch в модуле задач** — типы задач в enum, ветки рендера в одном
   месте. Отвергнут: каждый новый источник задач требует правки центрального файла —
   точка знания раздувается (пакетные зависимости при этом не растут: всё в `apps/u7-bot`).
2. **Полностью абстрактные задачи + стандартные кнопки** («Выполнено»/«Пропустить») —
   задача как инструкция, действие выполняется вне модуля задач. Отвергнут как
   единственный режим: «Выполнено» для системных действий — дыра в инварианте
   (UC не выполнен → студент висит в группе; обратный рассинхрон — сделал через
   инструменты, задача висит), флоу-переходы без кнопки — высокая плата действия,
   развилки («Снять/Оставить») не выражаются.
3. **Доменная задача + рендер-контракт по kind (выбран)** — стандартный рендер
   (вариант 2) остаётся как fallback и тип «внешнее действие».

**Ключевая опора:** маршрутизация колбеков `UiApp.handleCallback`
(`packages/core/src/ui/bot/ui-app.ts`) уже диспетчеризирует нажатия по префиксу
контроллера (`cbFor`) — обработчики кнопок не нужно «передавать» в модуль задач,
они живут у владельцев (confirm, UC, флоу — уже написаны).

## Архитектура: четыре слоя

### Слой A — домен `task`: чистые данные + конверт

`Task { id, assigneeId, kind: '<domain>.<name>' (строка, не enum), title, description?,
ownerInfo, status, mandatory, dedupeKey, окно жизни, createdAt/updatedAt }`.

- `ownerInfo` — прозрачный конверт владельца (паттерн анкет:
  `packages/questionnaire/src/domain/facade.ts`), возвращается владельцу в событиях
  завершения; модуль задач не знает содержимого.
- Тексты title/description — от владельца (как тексты UC в этапе A: «тексты — в
  домене, UI рендерит»).

### Слой B — движок обогащения (TaskTypeMeta, домен-уровень)

Домен-владелец регистрирует при сборке API-приложения
`TaskTypeMeta { kind, resolveRenderInfo(task) → TaskRenderInfo }`. Рендер-контракт —
канало-независимые данные: `actions: [{ id, label, style, confirm? }]`. UC
`get-my-tasks` обогащает DTO контрактом **на лету** (не персистится — тексты всегда
свежие; деградация по образцу этапа A: fallback на id). Нет меты → стандартный
контракт: текст + [Пропустить]/[Готово] (по mandatory) — здесь живёт вариант 2.

Выигрыш для web-ui (горизонт): контракт декларативен, новый канал не дублирует знаний.

### Слой C — канало-рендереры (UI-уровень)

- Дефолтный рендерер бота: стандартные действия task-модуля
  (`cbFor('tasks', 'skip', id)` и т.п.).
- Kind-рендерер: регистрируется контроллером-владельцем в UI-приложении, превращает
  `action.id` контракта в колбек своей стори (confirm, captureInput, делегирование
  во флоу) — дальше штатная маршрутизация UiApp.
- Сопоставление: публичный контракт — **kind с префиксом домена**; предикат —
  внутренняя реализация резолвера/рендерера (один рендерер на `questionnaire.*`).
  Fail-fast на дубликаты kind при сборке.

### Слой D — завершение: по критерию «кто выполняет действие»

- Действие владельца: кнопка → сторя владельца → UC владельца →
  `taskFacade.close(dedupeKey)` (stream → task, как wish → stream в этапе A).
- Стандартное действие: UC task-модуля → событие `task.skipped` / `task.completed`
  `{ kind, ownerInfo }` → ER владельца (память об отказе — «не долбить повторно»).
- Ручное «Готово» — только для задач без системного действия (определяется
  обязательностью и наличием actions в контракте); запрещено на уровне UC.
- Повтор ситуации (бездействие 7→9 дней) → `upsert` по dedupeKey — обновление,
  не дубликат.

### Касания пользователя — централизованы в task-модуле

Уведомление о новой задаче («есть дело — /tasks», текст без кнопок), напоминания,
дайджест-склейка, окно жизни — сам task-модуль через `userFacade.notify`. Владелец
создаёт задачу — и всё, доставка его не касается.

### Цикл (пример: кандидат на снятие)

```
job бездействия (stream) → taskFacade.upsert({ kind: 'stream.inactivity-candidate',
  assignee: mentorId, dedupeKey, ownerInfo: { studentId, streamId, days } })
→ task-модуль: notify ментору «🛑 есть дело — /tasks»
→ /tasks: UC get-my-tasks + TaskTypeMeta(stream) → контракт [⚠️ Снять danger+confirm][✅ Оставить]
→ бот-рендерер streams → cbFor('inactivity', 'mark-abandoned', …) → confirm с именем → UC
→ кик из группы, notify студенту, taskFacade.close(dedupeKey)
[✅ Оставить] → UC stream → close + task.skipped → ER: не предлагать до нового повода
повтор sweep (7→9 дней) → upsert по dedupeKey
```

## Зависимости модулей

- `task` ни о ком не знает (кроме `user` — notify, как все).
- Владельцы (stream, questionnaire, …) → `task`: фасад + импорт типов событий для ER.
- UI: контроллеры-владельцы регистрируют рендереры; контроллер tasks о владельцах
  не знает.

## Карта миграции касаний

| # | Триггер | Адресат | Будет |
|---|---------|---------|-------|
| 1 | `student.inactivity-warning` (5+ дн) | студент | задача `stream.inactivity-warning` + [Продолжить]/[Покинуть]; «Продолжить» — осознанный сигнал, сброс каскада |
| 2 | `student.inactivity-remove-candidate` (7+ дн) | ментор | задача `stream.inactivity-candidate` + [Снять]/[Оставить] |
| 3 | `student.module-completed` (7a/7b) | студент | флоу-задача [Продолжить] (открывает хаб / следующий модуль) |
| 4 | `questionnaire:invite` | студент | опциональная задача + память об отказе (до нового повода) |
| 5 | «Покинуть учёбу» без 5 дней | студент | **возможность меню** в хабе «Учеба» (не задача) |

Стори-обработчики бездействия переиспользуются: умирают проактивные подписки с
кнопками, вместо них — создание задач + текстовое уведомление.

## Продуктовые вопросы (не закрыты, есть рекомендации)

Из [tasks-system.md](./tasks-system.md), с рекомендациями сессии (ждут решения):

1. Напоминания: только обязательные, раз в 3 дня, максимум 2, далее окно жизни;
   опциональные не напоминать вовсе.
2. Повторные окна: отказ закрывает задачу навсегда; новое предложение — только по
   новому поводу.
3. Дайджест: без отложенного; склейка нескольких задач одного sweep в одно
   «Появилось N дел — /tasks» (точка склейки — task-модуль).
4. Сортировка списка: (обязательность, свежесть); поля приоритета — отложить.
5. Брошенная анкета: задача-продолжение, опциональность наследуется (сверить с
   активным треком `questionnaire-robustness_20260903`).
