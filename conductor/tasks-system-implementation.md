## Этап A — Механизм уведомлений `userFacade.notify` (трек `user-notify_20260902`)

> **✅ Статус: реализовано (трек user-notify_20260902 завершён).** Перенесены
> чистые уведомления #3, #4, #7c/7d, #8; дубль зачисления устранён
> (FR-5/FR-6). Кнопочные проактивы #1/#2, 7a/7b и анкеты — без изменений до
> этапа B. См. `summary.md` трека и обновлённые ui-spec (streams S11/SIN-A,
> learning S05n).

### Проблема

Сегодня уведомление — цепочка из четырёх артефактов: UC/job публикует событие
(payload тащит `telegramId` — канальный концепт в домене) → стори подписывается →
стори резолвит данные через `appApi` → стори рендерит текст и шлёт через
`proactiveSender`. Итог: тексты уведомлений (доменное знание) живут в UI-слое,
telegramId протекает в события, каждое новое уведомление требует новую стори.

### Решение: событие `user.notified` + контроллер `user`

```
UC / ER / Job (владелец контекста — знает «что» и «кому»)
  → userFacade.notify(userId, text)            — доменные модули
    (UI-клиенты: appApi.execute('notify-user'))
      → UC 'notify-user' (модуль user)         — ничего не мутирует,
        публикует событие 'user.notified' {userId, text}
          → EventBus (существующий механизм)
            → подписка контроллера user (bot-ui)
              → стори notify: резолвит telegramId (get-user), рендер канала (🔔,
                экранирование), proactiveSender.notify → transport
```

### Принципы механизма (зафиксированные решения)

1. **«Что и кого уведомить» — доменно; «как доставить» — инфраструктура.**
   Событие `user.notified` — канал-агностичный интеграционный шов: каждый фронт
   (бот сегодня; web/mobile завтра) подписывается и доставляет своим каналом.
   UC при появлении новых фронтов не переписываются.
2. **Адресат — `userId`.** Маппинг «пользователь → канал» — ответственность
   подписчика доставки. `telegramId` исчезает из событий, переносимых на механизм.
3. **Текст — plain.** Разметка, экранирование, 🔔 — рендер канала (стори).
4. **Best-effort, ephemeral.** `InProcEventBus` изолирует ошибки подписчиков —
   сбой доставки логируется шиной, UC не падает. Уведомление не хранится и не
   имеет статусов. Сообщению, которому нужно «жить» (окно, напоминания, кнопка
   действия), место в задачах этапа B, не здесь.
5. **Механизм доставки не меняется.** UiApp-подписки контроллеров, стори,
   `proactiveSender`, очередь per-chat в транспорте — всё существующее. Новый
   только владелец доставки: контроллер `user` со стори notify.
6. **Клиенты UC:** доменные модули — через фасад (`userFacade.notify`),
   UI-слой — через `appApi.execute('notify-user')`.
7. **Без подписчиков — тихий no-op.** В u7-cli событие `user.notified` никем не
   обрабатывается и игнорируется. Заглушки не нужны.

## Этап B — Модуль задач (заготовка, отдельная сессия)

Состав (по концепции [tasks-system.md](./tasks-system.md)):

- **Домен задач** (`packages/tasks`): Task = тип (кнопка-действие / флоу /
  развилка-решение) × обязательность (политика напоминаний); окно жизни; статусы
  (открыта / выполнена / отказана / истекла); upsert при повторе ситуации
  (бездействие 7→9 дней — та же задача); память об отказе («не в этот раз»).
- **API**: UC create-or-update / complete / decline / list-by-user; job истечения
  окон; ER, создающие задачи из доменных событий других модулей.
- **UI**: команда `/tasks` + «Мои задачи» в главном меню; список с кнопками
  быстрых действий; опасные — confirm; флоу-задачи (анкеты) — переход во флоу.
- **Миграция сценариев**: бездействие (студенту [Продолжить]/[Покинуть], ментору
  [Снять]/[Оставить]), закрытие потока ([Следующий модуль]/[Пройти снова]),
  анкеты-приглашения → опциональные задачи с окном.
- **Чистка**: смерть оставшихся кнопочных подписок и takeover-кнопок.

Черновая декомпозиция: B1 ядро (домен + API) → B2 UI списка задач → B3 пилот на
бездействии → B4 остальные сценарии. Архитектурная концепция и декомпозиция на
треки — отдельная сессия (дополнит этот документ).

Открытые вопросы концепции (напоминание): политика напоминаний, повторные окна
после отказа, дайджесты, сортировка списка, брошенная анкета — таск или уведомление.
