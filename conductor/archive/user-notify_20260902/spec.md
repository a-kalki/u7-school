# Спецификация — Трек: Механизм уведомлений userFacade.notify (user-notify_20260902)

## Обзор

Единый механизм уведомлений: любой UC / ER / Job отправляет уведомление одним действием — `userFacade.notify(userId, text)` (UI-клиенты: `appApi.execute('notify-user')`). UC `notify-user` (модуль user) публикует событие `user.notified {userId, text}` без мутаций; подписчик — новый контроллер `user` (bot-ui) со стори `notify`, которая резолвит telegramId, рендерит и доставляет через `proactiveSender.notify` → transport (очередь per-chat сохраняется).

На механизм переносятся только чистые уведомления (4 сценария + чистка дубля зачисления). Кнопочные проактивные сообщения остаются на подписках до модуля задач (этап B). Рамка: [tasks-system-implementation.md](../../tasks-system-implementation.md), этап A.

## Функциональные требования

**FR-1. Механизм.** UC `notify-user` (user, api): `{userId, text}` → publish `user.notified {userId, text}`, без мутаций. `UserFacade.notify(userId, text)` — для доменных модулей; `appApi.execute('notify-user')` — для UI-слоя.

**FR-2. Доставка.** Контроллер `user` (bot-ui) со стори `notify`: подписка на `user.notified` (существующий механизм UiApp), резолв `get-user` → `telegramId`, рендер plain-текста (экранирование, MarkdownV2), доставка `proactiveSender.notify`. Без кнопок — уведомление не перехватывает ввод.

**FR-3. Ошибки доставки.** Пользователь не найден / нет `telegramId` → лог-ошибка, пропуск, приложение не падает. Сбой транспорта изолирует шина (существующее поведение InProcEventBus).

**FR-4. Перенос уведомлений.**

| # | Сценарий | Отправитель |
|---|---|---|
| 3 | самовыход студента → ментору | UC `drop-student` |

| 7c/7d | закрытие потока: последний модуль / место неизвестно → студенту | UC `complete-student` (место модуля — `courseFacade.getModulePlace`; кнопочные ветки 7a/7b остаются в HubStory) |

Флоу-ответ дополняется инструкцией: «Теперь вы можете получить функционал по учёбе, набрав /start и перейдя по кнопке «Моя учёба»». Событие `student.enrolled` остаётся (слушает ER `fulfill-wish`).

**FR-6. Тексты переносимых уведомлений.** Формулировки — с контекстом (имя, поток), чтобы адресат всегда понимал, о ком/о чём речь:

## Нефункциональные требования

- Тексты — plain, разметка/экранирование — в стори `notify`.
- Порядок доставки серии уведомлений — существующая очередь per-chat.
- u7-cli: `user.notified` без подписчиков — тихий no-op.

## Критерии приёмки

- **Unit**: UC `notify-user` реализован и опубликован в apiApp; `UserFacade.notify(userId, text)` реализован и делегирует в UC; UC публикует событие с корректным payload; стори `notify` доставляет и логирует ошибку при отсутствии пользователя/telegramId.
- **Интеграционные**: доступ через `appApi.execute('notify-user')` публикует событие; сценарии #3, #4, #7c/7d, #8 — от триггера до доставки правильному адресату с текстом FR-6; зачисление даёт одно сообщение с инструкцией (без дубля); кик из группы работает.
- **E2E (финальная фаза)**: уход студента, снятие за бездействие, закрытие потока, открытие набора, зачисление.
- **Регресс**: анкеты не затронуты; `biome check` + `tsc --noEmit` чистые.
