# Решения (ADR-список)

**Назначение:** короткий реестр принятых архитектурных решений. Новое решение — новая строка `D-NN`; пересмотр — пометка «заменено D-NN», старое не удаляется.

---

**D-01. Манифест — единый источник истины.** Каждая доменная сущность объявляется один раз декларативным объектом. Типы, схемы, свойства базовых классов, транспорт, документация, MCP и контрактные тесты выводятся из него. *Почему:* сейчас одна команда описывается в 5–6 местах, а связи (кто эмитит, кто слушает) скрыты в коде.

**D-02. Пакет `@u7-scl/domain` — вся предметка и все манифесты.** Сущности, агрегаты, политики, ошибки, события, сервисы и **контракты** UC/ER/Job/фасадов/модулей лежат в одном пакете. Реализации UC/ER/Job, репозитории и wiring остаются в модульных пакетах. *Почему:* домен полностью тестируем, нет вопросов с межмодульными импортами, граф строится из одного пакета без запуска приложения.

**D-03. Домен чистый и синхронный.** Никакого IO, eventBus, репозиториев. Асинхронность — только через `Loader<T>` (D-06). *Почему:* тривиальная тестируемость и предсказуемость.

**D-04. `app` — технический слой всего приложения.** Замыкает дженерики уровня приложения (`AppMeta`, тип актора, `appApi`), импортирует `domain`. Доменных сущностей не содержит: `User` и роли уезжают в `domain/user`.

**D-05. Состояние (entity) — внутреннее дело агрегата.** Доступ к данным entity имеют только Ar, реализация репозитория (restore/snapshot) и UI-зона (данные компонента). Остальные работают с API доменных объектов. Репозитории возвращают и принимают Ar. Контракты (input/output UC, payload событий, DTO фасадов) — не entity. *Почему:* знание о структуре состояния сосредоточено в одном месте.

**D-06. Три уровня API домена: Ar → Policy → Service.** Ar — бизнес-операции и вопросы к состоянию. Policy — декларативные права (роль + владение + контекст) с текстами отказов. Service: `ApiService` (координация агрегатов для UC, может мутировать) и `UiService` (только чтение, UI-термины). Сервисам разрешены ленивые `Loader`-колбэки.

**D-07. `Result<T, E>` вместо `throw` для штатных отказов.** Агрегат, сервисы и UC возвращают `Result`. `throw` — только баг, нарушение инварианта, системный сбой. Подробно — [errors-result.md](./errors-result.md).

**D-08. Ошибки — объекты `defineError` с `kind`.** UC ссылается на ошибки агрегата без переименования; базовые ошибки (`NOT_FOUND`, `ACCESS_DENIED`, `INPUT_VALIDATION`, …) подмешивает ядро. `kind` задаёт HTTP-статус.

**D-09. Декларация + верификация.** Каждая декларация манифеста проверяется: типом, рантайм-ассертом в test/dev или контрактным тестом. Правило без проверки — пожелание. См. [manifests.md](./manifests.md), [rules.md](./rules.md).

**D-10. Время — `Timestamp` (number, мс, UTC).** Строковые даты уходят. Схемы на переходный период читают и ISO-строку, пишут число; пакетная миграция данных — отдельный трек с бэкапом и подтверждением.

**D-11. MCP генерируется из манифестов.** UC → MCP tools (query → `readOnlyHint`), доменный граф → resources. Старт: только query, dev-окружение, явно заданный актор.

**D-12. Мультиагентный процесс.** Оркестратор + domain-author, api-author, migrator, reviewer (ui-author — позже). Автор ≠ ревьюер; правила имеют ID. См. [agents.md](./agents.md).

**D-13. Поэтапный переход (strangler).** Старое и новое сосуществуют; модули мигрируют по одному. См. [migration.md](./migration.md).

**D-14. Одно место для архитектуры.** Концепция из бывшего `roadmap/domain-manifest-graph.md` поглощена этой папкой; файл удалён (история — в git).
