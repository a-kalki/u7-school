# Система сбора метрик студента — Глобальная задача

**Назначение:** объединяющий документ для всей системы сбора и анализа метрик студента. Связывает три дочерних документа, каждый из которых делится на треки.

---

## Видение

К окончанию курсов мы соберём статистику о том, как студент проявлялся: профессионализм (качество работы, алгоритмическое мышление, владение инструментарием), командные навыки (коммуникативность, инициативность, честность, взаимовыручка), личностные качества (энтузиазм, ответственность, регулярность). Данные собираются через:

- **Анкеты при завершении модуля** — студенты оценивают друг друга, ментор оценивает студентов, студенты — ментора
- **Анкеты парного программирования** — «смотревший» оценивает «программировавшего»
- **Анкеты код-ревью** — ревьюер оценивает автора
- **Инициативные анкеты** — вне плановых контекстов

Итог: профиль студента с числовыми метриками + личные рекомендации ментора и студентов → заявка на трудоустройство.

### Порядок реализации

```
Документ 2 (EventBus + Aggregate API)  ──┐
                                         ├──> Документ 3 (пайплайн + модули)
Документ 2 (questionnaire модуль) ───────┘
                                          
Документ 1 (концепция) — параллельно, задаёт структуру metricMapping
```

Документ 2 должен быть реализован первым, так как даёт инфраструктуру (EventBus, Aggregate API, questionnaire), на которой строится Документ 3. Документ 1 можно прорабатывать параллельно — он не зависит от кода.

## Ключевые архитектурные решения (приняты в обсуждении)

1. **Модуль `questionnaire`** — чистый движок анкет. Не знает о метриках, но вопросы в пуле содержат метаданные `metricMapping: { category, subcategory, weight }`. При завершении анкеты возвращает не только ответы, но и предвычисленные баллы по категориям.

2. **Иерархия анкет:** `QuestionnaireAr` (абстрактный) → `MetricQuestionnaireAr` (для метрик, умеет выдавать `MetricScore[]`). Онбординг-анкета использует `QuestionnaireFacade` напрямую, без наследования агрегата.

3. **Модель данных анкеты:** `subjectId` (о ком), `respondentId` (кто заполняет), `context` (module_completed/pair_programming/code_review/initiative/onboarding), `role` (student_student/mentor_student/student_mentor), `triggerEvent` (что породило).

4. **События генерирует агрегат, публикует UseCase.** Агрегат в `ArMeta.events` объявляет возможные события, метод `addEvent()` кладёт их внутрь. UseCase после вызова агрегата и сохранения вызывает `publishEvents(ar)`.

5. **EventBus** — в `core`, интерфейс + `InProcEventBus`. Подписка по типу события (строка). Публикация синхронная в цикле.

6. **Запуск анкеты — Intention-паттерн.** Фасад создаёт «намерение» → возвращает ID и сообщение → пользователю показывается кнопка «Заполнить анкету» → пользователь сам решает.

7. **Новые модули:**
   - `questionnaire` — выделяется из `onboarding` (который остаётся как потребитель)
   - `peer-review` — парное программирование, код-ревью, кросс-оценки, оркестрация анкет при событиях
   - `metrics` — хранение и агрегация метрик, витрина профиля студента

8. **Поток для кейса «завершение модуля»:**
   `stream` (ModuleCompleted) → `peer-review` (оркестрирует intentions) → `questionnaire` (анкеты, QuestionnaireCompleted) → `metrics` (агрегация)
