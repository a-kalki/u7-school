# Спека: Модуль «Алгоритмика: прикладное» — бизнес-утилиты и HTTP-сервис

## 1. Обзор

Модуль **«Алгоритмика: прикладное»** (`uuid fe37c988-13b8-4c80-964a-5d0d98e86885`,
каталог `data/fullstack-js/m3-algorithm-applied`, `status: draft`, вне `course.phases`)
наполняется учебным материалом двух проектов:

- **П1 «Бизнес-утилиты»** — разбор входных данных и сериализация в строку
  (`getQueryParams`, `parseUrl`, `groupBy`, файлы и форматы, `toCSV`, `fromCSV`).
- **П2 «HTTP-сервис»** — CRUD-сервис заказов: слои и архитектура, хранение в файле,
  моки, валидация, сервер на `Bun.serve`, обработчики, запуск и ручная проверка.

Инфраструктурный код и учебный материал создаются **в одном треке**.
Модуль остаётся `draft`. **Аркада** (движок, рендереры, игры, FSM) — отдельный будущий трек.

**Предусловие.** Трек `m2-content-sync` закрыт: ветка `main` (`v0.2.0`), весь контент
m2 в `data/courses/*.json`, md `p12-*` перенесены в `m3-algorithm-applied`. Трек
ведётся в отдельной ветке от текущего `main`; работа соло, мердж локальный, без PR.
В рабочем дереве есть незакоммиченные правки владельца — их не смешивать с работой трека.

### 2.2 Серверная заготовка и контракт

- Сервер — **`Bun.serve`** (нативный, без сторонних библиотек), пять GET-роутов:
  `list`, `get`, `create`, `update`, `delete` (CRUD + list).
- **Централизованная обработка ошибок на уровне сервера**: `server.js` содержит
  единый перехватчик исключений (try/catch):
  - `NotFoundError` (выбрасывается обработчиком, если запись не найдена) -> `{ error: err.message }` с HTTP-статусом `404 Not Found`;
  - `OrderValidationError` (ошибка входных данных/правил валидации) -> `{ error: err.message }` с HTTP-статусом `400 Bad Request`;
  - отсутствие зарегистрированного роута в таблице -> `{ error: 'Маршрут не найден' }` с HTTP-статусом `404 Not Found`;
  - неожиданные исключения -> `{ error: err.message }` с HTTP-статусом `500 Internal Server Error`.
- **Выдаётся студенту готовым** (инфраструктура — на нас):
  - `infra/file-storage.js` — `saveToFile`/`loadFromFile` (разбирается шагами в уроке моков);
  - `server/server.js` — `runServer` на `Bun.serve`, централизованный обработчик ошибок в JSON, передаёт обработчику сырой url строкой;
  - `server/route.js` — **заготовка** таблицы «path → обработчик» (студент вставляет роуты);
  - `server/main.js` — регистрация роутов и запуск сервера.
- **Пишет студент** (бизнес-логика, без типов):
  - `app/entity/order.js` — фабрика `createOrder` (сборка валидного заказа для обработчиков);
  - `app/entity/validator.js` — доменные валидаторы (приведение типа + проверка правил + выброс `OrderValidationError`) и класс `OrderValidationError`;
  - `app/repo/order-repo.js` — простое CRUD-хранилище заказов поверх `infra`; `id` назначает repo; сохраняет и выдаёт то, что передали (без валидации);
  - `app/handler/` — тонкие обработчики-оркестраторы пяти роутов: по файлу на роут (`list-orders.js`, `get-order.js`, `create-order.js`, `update-order.js`, `delete-order.js`), рядом с каждым — тест; класс `NotFoundError` в `errors.js`.
- Обработчик оркестрирует выполнение запроса: получает сырой URL, парсит параметры через `getQueryParams`, валидирует входные данные (напрямую через `validateId` или через фабрику `createOrder`), передаёт чистые данные в репозиторий и возвращает JSON-строку (`JSON.stringify`). Обработчик не возвращает объект `Response` (исключая утечку сетевого транспорта в слой приложения) — оборачивание в `Response` со статусом `200 OK` выполняет сервер `server.js`. При ошибке валидации выбрасывается `OrderValidationError` (сервер возвращает `400`), при отсутствии записи в репозитории выбрасывается `NotFoundError` (сервер возвращает `404`).
- **Задание формулируется человеческим языком** (бизнес-язык для бизнес-файлов,
  технический — для технических): ответственность, вход/выход, крайние случаи,
  критерии приёмки. **TDD:** студент пишет тесты сам; в уроке — только общие правила
  (что проверять, что мокать, что чистить), **без готовых тестовых случаев**.

### 2.3 Моки и инфра

Урок `p2-l3-mocks` совмещает выдачу и разбор `infra` с глубоким погружением в тему моков:

- шаги про хранение в файле: зачем файл, синхронный `node:fs`, готовый `file-storage.js`,
  round-trip на реальном файле;
- почему тесты бизнес-логики не должны писать на диск (скорость, изоляция, надёжность);
- концепции Test Doubles: Dummy, Stub (заглушка), Spy (шпион), Mock (проверка взаимодействия);
- API `bun:test`:
  - автономный `mock()`: вызовы, матчеры `toHaveBeenCalledTimes`/`toHaveBeenCalledWith`, настройка поведения `mockReturnValue`/`mockImplementation`;
  - `spyOn(object, method)`: наблюдение за методом существующего объекта, вызов оригинала по умолчанию, временная подмена, снятие через `mockRestore()`;
  - `mock.module(path, factory)`: подмена ES-модулей по путям импорта;
- гигиена тестов и очистка состояния: `mockClear()`, `mockReset()`, `mockRestore()`, роль `beforeEach`/`afterEach`;
- матрица выбора «что и в какой момент использовать»;
- практика — закрепление применения `mock`, `spyOn` и `mock.module` в изолированных тестах без обращения к диску.

Урок `p2-l4-order-repo` начинает практическую работу над репозиторием:
- разбор проблемы путей к данным (`process.cwd()` vs `import.meta.dirname`) и оба варианта решения;
- паттерн Read-Modify-Write и генерация уникального `id`;
- реализация всех 5 операций CRUD (`getOrder`, `listOrders`, `addOrder`, `updateOrder`, `deleteOrder`);
- изолированное TDD-тестирование репозитория через `mock.module`.

### 2.6 Укладка в БД

- **Укладка — проектом целиком.** Проект (все его уроки и шаги) попадает в json за один
  заход и только после вычитки его md. Нельзя уложить сначала `l1`, а остальные уроки —
  в другой фазе. За один заход — один или несколько проектов.
- Проекты П1/П2 и уроки/шаги укладываются в `data/courses/{modules,lessons,steps}.json`
  (модуль `draft`, вне `course.phases`).
- Инструменты — с обязательным **dry-run**; перед правкой `data/courses/*.json` — бэкап
  или опора на git (по решению владельца).
- **Временные скрипты укладки в коммиты не попадают**: либо добавляются в `.gitignore`,
  либо удаляются до коммита.

### 2.8 Структура учебного проекта и слои

Учебный материал ведёт студента к **единому проекту** `fullstack-js/` со слоями
(стандарт — [course-project-structure.md](../../guides/course-project-structure.md)).
Это дерево **студента**, а не репозитория: в треке меняются только `*.md` уроков и
`*.json` контента, папки `data/fullstack-js/p2-*` — md-контент уроков.

Дерево проекта П2 (внутри `m2-m3-algorithms/`):

```
fullstack-js/
  m2-m3-algorithms/
    utils/business/          # getQueryParams, parseUrl, groupBy, toCSV, fromCSV
    m3-p2-http/
      infra/                 # file-storage.js — технология, о заказах не знает
      app/
        entity/              # order.js — тип Order и фабрика createOrder; validator.js — доменные правила
        repo/                # order-repo.js — CRUD заказов поверх infra
        handler/             # по файлу на роут: list-orders.js, get-order.js,
                             # create-order.js, update-order.js, delete-order.js
      server/                # server.js, route.js, main.js — Bun.serve и маршрутизация
      data/                  # orders.csv
```

Ответственности и зависимости:

| Слой | Отвечает за | Не знает о |
|---|---|---|
| `utils` | чистые функции | об остальном |
| `infra` | технологию (файл), обобщённые операции | о заказах, HTTP |
| `app/entity/order.js` | фабрику `createOrder` (сборка валидного заказа для обработчиков) | infra, server |
| `app/entity/validator.js` | доменные валидаторы (приведение + проверка + throw) и `OrderValidationError` | infra, server |
| `app/repo` | простое CRUD-хранилище поверх `infra`; назначает `id`; сохраняет и выдаёт переданные данные без валидации | server, handler, validator |
| `app/handler` | оркестрацию запроса: разбор URL, валидация входов (`validateId`/`createOrder`), вызов repo, HTTP-ответ | server (запуск) |
| `server` | `Bun.serve`, маршрутизация, централизованная обработка ошибок валидации в JSON | — |

**`order.js` vs `validator.js`.** `validator.js` содержит **доменные валидаторы**: функции
проверяют правила (имя не пустое, сумма > 0, статус из списка), делают приведение типов и
при нарушении правил **бросают `OrderValidationError`**. Все поля **обязательны**, кроме `review`.
`order.js` содержит **фабрику `createOrder`**, которая вызывается в обработчиках (`create`, `update`),
прогоняет параметры через валидаторы и собирает готовый объект заказа.

Иерархия импортов: `utils ← infra ← repo ← handler → entity (order/validator) ← server`.
Верхний слой знает нижний, обратное запрещено. Репозиторий о валидаторах не знает. Пути относительные (`../../utils/business/to-csv.js`), тесты рядом с кодом.

Поток вызова: `HTTP → server → handler (валидация: validateId / createOrder → validators) → repo → infra → utils`.

Вводный урок `p2-l1-architecture` объясняет слои, дерево, ответственности и поток вызова;
файлы пишутся в этой раскладке.

### 2.9 Контракты сущности и репозитория (чистый JS, без типов)

**Заказ и поля:**
- Объект заказа: `id` (целое > 0), `customer` (непустая строка), `amount` (число > 0),
  `isPaid` (boolean), `status` (`'new'` | `'completed'` | `'canceled'`), `review` (строка или undefined).
- **Все поля обязательны, кроме `review`**. Если обязательное поле отсутствует или невалидно — ошибка.

**Валидаторы (`app/entity/validator.js`):**
- Функции: `validateId`, `validateCustomer`, `validateAmount`, `validateIsPaid`, `validateStatus`, `validateReview`.
- Каждая функция принимает сырое значение (строку или приведённое), приводит тип и проверяет доменные правила.
- При успехе — возвращает приведённое валидное значение.
- При ошибке — **бросает `OrderValidationError(message)`**. Никаких промежуточных объектов `{ isValid, error }`.

**Фабрика (`app/entity/order.js`):**
- `createOrder(data)` — вызывается в обработчиках (`create`, `update`). Принимает сырой объект параметров, прогоняет поля через валидаторы, отсекает посторонние поля и возвращает валидный объект заказа. Если передан `data.id`, валидирует его через `validateId`.

**Репозиторий (`app/repo/order-repo.js`):**
- Простое CRUD-хранилище данных поверх файла, без валидации:
  - `listOrders()`: читает файл через `loadFromFile`, возвращает массив объектов (или `[]`).
  - `getOrder(id)`: находит запись в массиве файла по `id`, возвращает объект или `null`.
  - `addOrder(data)`: читает файл, вычисляет следующий свободный `id`, добавляет `{ ...data, id }` в массив, сохраняет через `saveToFile` и возвращает созданный объект.
  - `updateOrder(id, data)`: находит запись по `id`, объединяет поля `{ ...existing, ...data, id }`, сохраняет и возвращает обновлённый объект (или `null`, если не найден).
  - `deleteOrder(id)`: находит запись по `id`, удаляет из массива, сохраняет и возвращает удалённый объект (или `null`, если не найден).

**Поток обработки ошибок:** обработчик оркестрирует вызовы; если при валидации брошен `OrderValidationError`, ошибка всплывает на уровень `server` и возвращается клиенту как `{ error: err.message }` с HTTP-статусом `400`.

- **Q23.** Импорты — относительные (без алиасов); тесты рядом с кодом (colocate).
- **Q24.** Пилот новой структуры — П2 (этот трек); П1 мигрируется отдельным треком.
- **Q25.** Выдаётся: `infra/file-storage.js`, `server/server.js` (с централизованным обработчиком ошибок в JSON), `server/route.js` (заготовка), `server/main.js`. Остальное пишет студент.
- **Q26.** `id` нового заказа назначает `repo`.
- **Q27.** Ручная проверка — три способа: `curl`, браузер, `fetch` в консоли браузера.
- **Q28.** Все уроки П2 генерируются за один заход, после чего — вычитка владельцем.
- **Q29.** Слой `handler` разбит по роутам: один файл на роут (`list-orders.js`, `get-order.js`,
  `create-order.js`, `update-order.js`, `delete-order.js`), рядом с каждым — свой тест.
  Handler оркестрирует запрос: разбирает URL, валидирует данные (`validateId`/`createOrder`), вызывает repo.
- **Q30.** Фабрика `createOrder` (`app/entity/order.js`) используется обработчиками для валидации
  и сборки объекта заказа. Валидаторы приводят типы и бросают `OrderValidationError` при ошибках.
  Все поля обязательны, кроме `review`.
- **Q31.** Репозиторий — простое CRUD-хранилище поверх файла: сохраняет и возвращает переданные данные
  без валидации. `id` назначает репозиторий. Ошибки валидации перехватываются на сервере и возвращаются в JSON со статусом `400`.
