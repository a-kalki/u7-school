# План: «Алгоритмика: прикладное» — бизнес-утилиты и HTTP-сервис

> Читать вместе со `spec.md`. Поток проекта П2: **сгенерировать все уроки за один заход →
> вычитка/правка владельцем в md → укладка проекта целиком в json → коммит.** Укладка —
> только проектом целиком (все уроки и шаги сразу), после вычитки. Временные скрипты
> укладки в коммиты не попадают.

### Решения владельца (актуальные)

- **П2 = 9 уроков** (финальная сетка — `spec.md` §2.1). Логика: сначала архитектура и модель,
  затем инфра+моки, repo, сервер, первый обработчик (с юнит- и интеграционными тестами),
  затем самостоятельная реализация остальных обработчиков, ручное тестирование и финал.
- **Выдаём инфраструктуру**, бизнес-логику пишет студент. Выдаётся: `infra/file-storage.js`,
  `server/server.js`, `server/route.js` (заготовка), `server/main.js`. Студент пишет:
  `app/entity/order.js`, `app/entity/validator.js`, `app/repo/order-repo.js`,
  `app/handler/list-orders.js`, `app/handler/get-order.js`, `app/handler/create-order.js`,
  `app/handler/update-order.js`, `app/handler/delete-order.js` (по файлу на роут, рядом с каждым — тест).
- **Инфра — не отдельный урок.** `saveToFile`/`loadFromFile` разбираются шагами в уроке
  моков (`p2-l3-mocks`), там же — мок модуля (`node:fs`) и мок функции (`loadFromFile`),
  а в практике реализуется первая repo-функция `getOrder(id)` (простой поиск по id в файле).
- **Валидатор — в `app/entity/validator.js`** (рядом с `order.js`), чистый JS без типов.
  Приводит тип, проверяет доменные правила и бросает исключение с понятным текстом при ошибке.
  Все поля обязательны, кроме `review`.
- **Фабрика `createOrder` используется обработчиками** для валидации входных данных и сборки
  чистого объекта заказа перед передачей в репозиторий.
- **Репозиторий — простое CRUD-хранилище поверх файла**: не валидирует, сохраняет и возвращает
  то, что передали. Назначение `id` — за репозиторием.
- **Обработчики — оркестраторы запроса**: разбирают URL, валидируют параметры (`validateId` / `createOrder`),
  вызывают repo, возвращают `200` или `404`.
- **Сервер — централизованная обработка ошибок**: `server.js` ловит исключения валидации
  (`OrderValidationError`) и возвращает валидный JSON `{ error: err.message }` с HTTP-статусом `400`.
- **`id` нового заказа назначает `repo`.**
- **Задания — человеческим языком** (бизнес-язык для бизнес-файлов, технический — для
  технических): ответственность, вход/выход, крайние случаи, критерии приёмки.
  **TDD, но без готовых тестовых случаев** — только общие правила (что мокать, что чистить).
- **API-роуты — пять:** `list`, `get`, `create`, `update`, `delete` (CRUD + list).
  В финале П2 явно объяснить студенту, что он сделал CRUD.
- **Ручная проверка — три способа:** `curl`, браузер, `fetch` в консоли браузера.
- **П1, `p1-l7` переработан** (историческое, уже сделано): задание из 4 шагов вместо
  готового сценария; тесты студент пишет сам.
