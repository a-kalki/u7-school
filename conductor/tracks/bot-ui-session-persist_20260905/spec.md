# Спецификация — Трек: Персистентность сессий (bot-ui-session-persist_20260905)

> **Материнский документ:** [bot-ui-session-architecture.md](../../bot-ui-session-architecture.md) — утверждённая целевая архитектура bot-ui v3 (сессия §4, TTL §7, решения §10.4, открытый вопрос §12.3). Трек 6 декомпозиции §9.

## Обзор

Сессии переживают перезапуск сервиса. После трека 5 `BotSession` и shortId-маппинг живут в памяти транспорта: рестарт сбрасывает `seq`, теряет `ScreenState.messageId` и разворот shortId → UUID — старые кнопки мертвы, диалоги пользователей обнуляются (решение 4 §10 было временным компромиссом «лечится треком 6»). Структуры сериализуемы по построению (§4).

**Решения владельца (2026-09-05):**
- Хранилище — JSON-файл через `JsonFileRepo`/`BaseJsonDb` (как все репозитории проекта).
- shortIds включаются в этот трек (персистентность маппинга `hexKey → UUID`).
- Запись — синхронно после каждого обработанного апдейта.

## Функциональные требования

- Порт `BotSessionRepo` в `packages/core/src/ui/bot` (загрузка всех сессий, сохранение, удаление; интерфейс без деталей хранилища). Транспорт получает repo через конструктор; без repo — режим in-memory (текущее поведение, тесты).
- Реализация `JsonBotSessionRepo` на `JsonFileRepo`/`BaseJsonDb` в `apps/u7-bot/src/infra`: коллекция сессий (ключ — chatId) с Valibot-схемой `BotSession`; коллекция shortId-маппинга (`hexKey → UUID`, с суффиксами коллизий).
- **Синхронная запись после каждого обработанного апдейта** (await до завершения handle-пути; per-chat очередь сериализует записи). `notify`/`info` сессию не пишут (И3).
- ShortId-маппинг: транспорт при `shrink` пишет в repo, при старте восстанавливает `Map`; `expandAction` работает после рестарта.
- Загрузка при старте **до** запуска polling/webhook.
- Повреждение файла — fail-fast (`JsonFileRepoError`): падение старта с явной ошибкой, никаких молчаливых пересозданий.
- Ошибка записи — warn-лог, работа продолжается в памяти (повтор на следующем апдейте), не глушится.

## Нефункциональные требования

- Цена — одна запись JSON после апдейта, приемлемо при текущем трафике.
- Формат файлов валидируется Valibot при чтении.

## Критерии приёмки

- Сценарий: пользователь посреди fill-анкеты → рестарт сервиса → нажимает кнопку старого экрана → штамп валиден, shortId разворачивается, анкета продолжается с того же вопроса (`dialog.path`, `seq`, `input.context`, `messageId` восстановлены).
- Тесты: round-trip сериализации `BotSession`, восстановление shortId-маппинга, поведение при битом файле, in-memory-режим без repo.
- `bun run check` весь репозиторий зелёный.
- Обновлена `bot-ui-session-architecture.md`: трек 6 в таблице §9 без пометки «опциональный», §10.4 и §12.3 закрыты решением (`BotSessionRepo` на JsonFileRepo, shortIds в треке).

## За рамками

- TTL ввода (§7 не возвращаем).
- Ротация/чистка shortId-записей (маппинг растёт монотонно, записи крошечные).
- Несколько инстансов/кластер; миграция на СУБД.
