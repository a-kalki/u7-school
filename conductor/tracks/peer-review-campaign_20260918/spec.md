# Спецификация: Кампании судьбы студента (peer-review v4)

> Реализует концепцию v4 (решения владельца 2026-09-18): кампания — окно судьбы
> студента (субъекта), ментор — соавтор в кампании субъекта, создание кампаний —
> мультисобытийный ER. Поглощает незавершённые фазы трека
> [peer-review-domain_20260916](../../archive/peer-review-domain_20260916/spec.md):
> зона stream (событие `stream.completed`, инвариант терминальности, read-API
> студента) в силе без изменений; домен peer-review переделывается.
> Спека экранов — [ui-spec.md](../../../apps/u7-bot/src/controllers/peer-review/ui-spec.md)
> (обновляется треком peer-review-ui).

## Обзор

Кампания = окно судьбы студента (субъекта) в потоке: личное событие
(`student.completed` | `student.abandoned`) → персональное окно 7 дней →
снапшот окружения → сбор «по горячим следам». Авторы окна: субъект (о своём
окружении по исходу) и ментор (только о субъекте). Кампании ментора и
`create-campaign-uc` — нет: создание кампаний — мультисобытийная реакция.
Трек также достраивает пользовательский API (UC отзывов, фасад) и
инфраструктуру (json-репо, bootstrap) — фазы 4–6 поглощённого трека.

## Функциональные требования

### Зона core: мультисобытийная подписка ER

- **ФР-1. `EventReaction` на несколько событий.** `eventNames: readonly
  TMeta['event']['eventName'][]` (вместо `eventName`); `ErMeta` объявляется по
  точному юниону событий (`StudentCompletedEvent | StudentAbandonedEvent`) —
  `handle(event: A | B)` без деградации до `DomainEvent`; подписка модуля на
  каждое имя; `ErDocType.eventNames: string[]`. Разбор внутри `handle` —
  сужение по дискриминанту `eventName` с exhaustive-веткой (`never`-контроль),
  если у событий есть своя логика. Миграция 4 ER модуля `wish` (механическая);
  правило — в styleguide `event-reaction.md`.

### Зона peer-review: домен

- **ФР-2. Каркас кампании.** + `subjectId` (uuid — студент, чьё событие открыло
  окно); контекст `stream_ended` (переименование `stream_completed`: данных и
  репозиториев нет, миграция бесплатна); `participants[]` — снапшот окружения
  субъекта на момент события: `{ userId, role: 'student' | 'mentor', outcome }`;
  исход у студентов обязателен, 4 значения: `completed` / `in_progress`
  («ещё учился на момент события субъекта») / `dropped` / `never_started`;
  ментор — без исхода. Инварианты: субъект присутствует в participants с
  терминальным исходом; userId участников уникальны.
- **ФР-3. Фабрика.** `createStudentCampaign({ scopeId, subjectId, participants,
  now })` — окно 7 дней от now (константа домена); `restore(state)` по
  дискриминанту контекста.
- **ФР-4. Политика адресации `ReviewPolicy`.** Субъект `completed` → ментор +
  соученики `completed`/`in_progress` (по снапшоту); субъект
  `dropped`/`never_started` → только ментор; ментор → только субъект; никогда —
  отзыв о себе.
- **ФР-5. Событие `student-campaign.created`**: payload `{ campaignId, context,
  scopeId, subjectId }` — получатели приглашений UI: субъект и ментор.

### Зона peer-review: API

- **ФР-6. ER `create-student-campaign-er`** (подписка `student.completed` +
  `student.abandoned`): идемпотентность по `(scopeId, subjectId)`; сбор состава
  фасадом stream; проекция исходов (4 значения, read-API студента); фабрика;
  save; публикация событий агрегата через `eventBus`; ошибки — лог-warn
  (шина изолирует). Удалить `create-campaign-uc`, `stream-completed-er`,
  команды/меты (`create-campaign-cmd.ts`); `module.ts`: `useCases: []`,
  `reactions: [CreateStudentCampaignEr]`.
- **ФР-7. Пользовательские UC** (ошибки доменные, тексты пользовательские).
  Роль автора (`subject` | `mentor`) UC выводит из кампании — параметром на
  входе не является (истина о роли — в кампании, дубль запрещён):
  - `get-my-campaigns(query)` — кампании, где пользователь субъект или ментор;
    записи с `myRole: 'subject' | 'mentor'`; `only_lives` (хаб S02: прогресс
    M/K, остаток дней) и `filter` (live, context?, scopeId?);
  - `get-campaign-recipients` — адресаты по политике по роли автора + признак
    «мой отзыв уже есть»;
  - `create-review` — кампания из репо, `ensureLive(now)`, адресат политикой,
    create/overwrite; уникальность пары — инвариант репо;
  - `list-scope-reviews` — отзывы скоупа, группировка по адресатам, снапшоты
    ролей/исходов для рендера.
- **ФР-8. Фасад** (для UI-трека и других модулей) — **только делегирование в
  UC**, логики не содержит (допустима тривиальная адаптация результата):
  `hasLiveCampaigns(userId)`, `hasReviews(scopeId)`, `listScopeFacts(scopeId)`.
  Под фасадные операции заводятся query-UC или переиспользуются существующие;
  прямой работы фасада с репо/агрегатами нет.

### Инфраструктура

- **ФР-9.** json-репозитории по образцу существующих: кампаний
  (`findBySubject(scopeId, subjectId)` — идемпотентность ER;
  `findActiveBySubject(userId)`; `findActiveByMentor(userId)` — раздельные
  выборки «как субъект»/«как ментор»), отзывов (уникальность пары, выборки по
  кампании/скоупу); bootstrap (подписка ER) + регистрация модуля в
  `create-api-app.ts`.

## Зафиксированные решения (сессия 2026-09-18)

1. Кампания — окно судьбы студента, ключ `(scopeId, subjectId)`: момент
   готовности писать есть только у автора; ментор — соавтор в окне субъекта
   (свежий отзыв и о покинувшем, в момент события). Альтернативы «окно
   мероприятия» (остывание данных ушедших) и «окно адресата» (окно ментора
   открывалось бы последним) — отклонены владельцем.
2. `stream.completed` peer-review не потребляет: инвариант терминальности
   гарантирует, что к закрытию потока все кампании уже созданы.
3. `in_progress` — 4-е значение проекции исхода (фильтрация адресации явным
   значением лучше `undefined`); только у адресатов-соучеников; исход субъекта
   всегда терминален.
4. Создание кампаний — ER, не UC: операция реактивная, UI её не вызывает;
   канон содержательных ER (модуль `wish`); UC — только пользовательские
   операции. Инъекция UC в ER (как было в `stream-completed-er`) — запрещена.
5. Роль автора — не параметр UC: выводится из кампании; раздельные выборки
   репо (`findActiveBySubject`/`findActiveByMentor`) и `myRole` в ответах.
6. Контекст `stream_completed` → `stream_ended`: имя обязано покрывать оба
   триггера (завершил и покинул); переименование бесплатно (данных нет).
7. Мультисобытийный ER — с точной типизацией: юнион событий в `ErMeta`,
   явный список `eventNames`, сужение по `eventName` с exhaustive-веткой.

## Критерии приёмки

- `student.completed`/`student.abandoned` → ровно одна кампания на
  `(scopeId, subjectId)` (идемпотентность при повторе события), снапшот с
  4-значными исходами, субъект с терминальным исходом.
- Отзыв пишется/перезаписывается в окне; после окна — «возможность закрыта»;
  все ветки адресации ФР-4 (в т.ч. ментор — только субъект).
- `get-my-campaigns` различает `myRole`; фасады не содержат логики.
- `CI=true bun test`, `bun run lint`, `bun run tslint` — чисто по скоупу трека.
