## Архитектурные решения

1. **Стори — только через `appApi`.** Все доменные чтения (9 UC:
   get-campaign-recipients, get-my-campaigns, create-review, get-my-review,
   list-scope-reviews, get-stream, get-user, get-users-by-ids,
   list-scope-facts) идут через `appApi.execute`; фасад модуля удалён за
   ненадобностью (ревью 2026-09-21).
2. **Приглашения — `ProactiveSender.invite`** с ПОЛНЫМИ кодами кнопок
   (транспорт проактивы не префиксует контроллером). Пропуск при отсутствии
   `telegramId`/профиля — молчаливый.
3. **Пагинация S07 — готовый пагинатор** (`pagedScreen` → `BotPaginator` +
   `DialogCache`): блок = отзыв, кеш эпохи диалога, build только при промахе.
4. **Исход автора — скрытый:** `myOutcome`/`subjectOutcome` никогда не
   рендерятся, только выбирают текст (S01, S05); в просмотре лейбл — только
   у автора-студента из снапшота `authorOutcome`.

## Отклонения от плана

Существенных нет. Уточнения по ходу:
- S02: кнопка ментора — `отзыв о {Имя}` вместо `{N} дн.`-формата одной кнопки
  для всех (спека ФР-3 предусматривала разделение по `myRole` — реализовано
  как в ФР-3, ui-spec приведён в соответствие).
- Имена адресатов S03 добываются UC `get-user` в цикле (не batch) — список
  адресатов кампании мал; batch оставлен для S02/S07 (большие списки).
- Фаза 6: «заглушка возможность закрыта» для истёкшей кампании уточнена —
  из списка/приглашения истёкшая даёт «⚠️ Кампания не найдена» (истёкшие не
  попадают в `get-my-campaigns`); «⌛ уже закрыта» — путь гонки истечения при
  вводе. Оба экрана покрыты e2e (`4f236df5`).
- Фаза 6, e2e S07: блок = отзыв, но несколько коротких блоков умещаются на
  одной странице (лимит ~3976 симв); ≥3 страницы собраны длинными отзывами
  (~3300 симв) в рантайме; порядок страниц createdAt-недетерминирован
