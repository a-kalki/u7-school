# Спецификация: Исходы и форма кампании peer-review (+предусловия UI)

> Трек `peer-review-outcomes_20260920`. Подготовительный перед продолжением
> [peer-review-ui_20260916](../peer-review-ui_20260916/spec.md): домен
> peer-review приводится к целевой форме (решения сессии 2026-09-20), read-API
> stream и событие расширяются, UI получает недостающие данные, core и user
> дают предусловия экранов. Экраны и тексты — утверждённый
> [ui-spec.md](../../../apps/u7-bot/src/controllers/peer-review/ui-spec.md)
> (обновлён 2026-09-20).

## Обзор

Домен-выравнивание + предусловия UI: (1) 4-значная проекция исходов судьбы
студента, (2) форма кампании — `subjectOutcome`/`mentorId` в payload,
`participants` без статусов и ролей, (3) `direction` в отзыве вместо пары
ролей, (4) read-API stream отдаёт статусы, (5) событие несёт полные данные для
приглашений, (6) UC возвращает `myOutcome` для текстов-подсказок,
(7) асинхронные `menuButtons` в core, (8) batch-UC пользователей в user.

## Функциональные требования

- **ФР-1. Проекция исходов (4 значения).** `completed_passed` |
  `completed_not_passed` | `dropped` | `never_started`; лейблы: «завершил и
  прошел», «завершил и не прошел», «забросил», «не начал». «Ещё учится» не
  хранится вовсе. Значение `in_progress` из домена удаляется.
- **ФР-2. Read-API stream.** `StreamFacade.getMembers` отдаёт по студенту
  статус (различающий `advanced`/`not_advanced`/`abandoned`/…, без склейки
  «прошёл/не прошёл») + `neverStarted`. Фильтрацию состава и проекцию исходов
  делает ER peer-review: событие «завершил» → в `participants` завершившиеся
  и ещё учащиеся (без субъекта); «забросил»/«не начал» → пустой список.
- **ФР-3. Форма кампании.** Ядро: `uuid`, `context: 'stream_fate'`, `scopeId`,
  `subjectId`, `participants: uuid[]` (только адресуемые соученики, без
  статусов и ролей), `createdAt`/`updatedAt`/`expiresAt` (`updatedAt` —
  контракт базового агрегата core, остаётся). Payload специфики контекста:
  `{ subjectOutcome, mentorId }`. Списочная модель участников с ролями и
  исходами удаляется; `ReviewPolicy`/`assertCanWrite`/`reviewTargets`
  упрощаются: автор — субъект или ментор; адресаты субъекта — `participants` +
  ментор (пустой список — только ментор); адресат ментора — субъект.
- **ФР-4. Отзыв.** Пара `authorRole`/`recipientRole` заменяется на
  `direction: 'student_student' | 'student_mentor' | 'mentor_student'`
  (невозможная пара исключена типом). `authorOutcome` остаётся — 4-значный
  снапшот исхода автора-студента (рендер «статуса автора» в S07, будущие веса
  в досье; ментору исхода нет — optional). `recipientOutcome` не вводится:
  статус адресата нигде не показывается.
- **ФР-5. Событие** `student-campaign.created` — payload пополняется:
  `mentorId`, `subjectOutcome` (агрегат — владелец данных). Заголовок потока в
  событии нет — UI берёт сам (`get-stream`).
- **ФР-6. UC `get-campaign-recipients`**: вернуть `myOutcome` (4-значный
  исход автора — выбор текстов-подсказок S05, включая «завершил, но не
  прошел»); `deliverables` удалить (до появления анкет).
- **ФР-7. Core: асинхронные `menuButtons`.** Проблема: сбор меню строго
  синхронный (`U7BotController.menuButtons`, `U7BotUiStory.menuButtons`,
  сбор в `ui-app.ts`), а видимость «💬 Отзывы» требует асинхронного фасада
  `hasLiveCampaigns`. Решение: сигнатуры `Promise<MenuButton[]>`, сбор меню
  параллельно (`Promise.all`), упавшая проверка скрывает свою кнопку + warn-лог
  (меню в целом живо). Обновить все реализации: streams, learning, app,
  mentor, courses (+ тесты).
- **ФР-8. User: batch-UC `get-users-by-ids`.** Проблема: стори резолвят имена
  одиночными запросами (N+1). Решение: query-UC — вход `{ userIds: uuid[] }`
  с лимитом (~100), выход — карточки пользователей (поля как у одиночного
  get-user); дубли id — дедуп; ненайденные — пропускать (+ warn), UI рендерит
  запасной вариант; `requiresAuth: true`.
- **ФР-9. Синхронизация с UI-треком и чистота репозитория.** Довести висящие
  правки Фазы 1 UI-трека (стори/тесты/домен — 11 файлов в рабочем дереве) до
  целевого состояния (тексты S05: 4 варианта «о менторе» по `myOutcome`) и
  закоммитить; обновить spec/plan трека peer-review-ui_20260916 и концепцию
  peer-review-system.md (§2/§5) под новые решения; ✅-пометки ui-spec.
  Временные файлы сессии (заметки, черновики) — удалены, в git не попадают.

## Нефункциональные требования

- TDD; `bun run check` чисто по скоупу трека.
- Миграция dev-данных/фикстур кампаний и отзывов под новую форму.

## За рамками

- Экраны UI (Фазы 2–4 трека peer-review-ui), приглашения-сторя, пагинация S07.
- Анкеты (likert), задачи-приглашения (task-модуль), досье/веса отзывов.

## Критерии приёмки

- Событие судьбы студента (все 4 исхода) → кампания новой формы
  (`participants` — id адресуемых, payload с `subjectOutcome`/`mentorId`) →
  событие с полными данными → UC отдаёт `myOutcome`.
- Отзыв хранит `direction` + `authorOutcome`; перезапись в окне работает.
- `getMembers` отдаёт статусы; async-меню не ломает существующие кнопки;
  batch-UC пользователей работает (лимит/дедуп/пропуск).
- Трек peer-review-ui обновлён и готов к продолжению; висящие правки
  закоммичены; временных файлов в репозитории нет.
