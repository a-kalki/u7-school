# Спецификация: UX анкет — маркировка выбора, редактирование на месте

## Обзор
Движок анкет написан до внедрения стандартных UI-возможностей бота (`editMessage`, удаление клавиатур у предыдущих сообщений, паттерны `editOrSend`/`respondInContext`). Сейчас каждый выбор порождает новое сообщение, радио-варианты не маркируются, история «вопрос–ответ» замусоривается. Трек приводит заполнение анкет к стандартному UX транспорта.

## Функциональные требования

### FR-1: Маркировка одиночного выбора (radio)
- При выборе варианта в вопросе с одиночным выбором сообщение с вопросом **редактируется** (editMessage): у выбранного варианта появляется маркер `(x)`, клавиатура вариантов **удаляется**.
- Затем следующий вопрос отправляется **новым сообщением** (sendMessage) — пользователь видит историю «вопрос → выбранный ответ».
- Автопереход сохраняется: кнопка «Далее» для одиночного выбора не появляется.

### FR-2: Мультивыбор — редактирование на месте
- Тоггл варианта (выбор/снятие) **редактирует то же сообщение**: маркеры `[x]`/`[ ]` обновляются, клавиатура остаётся.
- Кнопка «Далее» рендерится **только если выбран хотя бы один вариант**; если пользователь снял все варианты — кнопка «Далее» исчезает из отредактированного сообщения.
- Кнопка «Далее»: текущее сообщение редактируется — финальные маркеры `[x]`, **клавиатура удаляется**; следующий вопрос отправляется новым сообщением.

### FR-3: Унификация с возможностями BotResponse
- Сторя анкеты использует стандартные механизмы: комбинированный `BotCommand` (`editMessage` + `sendMessage` в одной команде), `session.lastBotMessage` — вместо унаследованных собственных решений.
- Поведение соответствует описанию из /help: после выбора кнопки клавиатура убирается, экран остаётся чистым.
- Проактивные сценарии (старт по событию, приглашение, resume после таймаута) — без регрессий: где `messageId` недоступен, остаётся `sendMessage`.

### FR-4: Job продолжения брошенных анкет
- Интервал запуска — **3 часа**; ступени простоя: **3ч → приглашение**, **6ч → предупреждение** (как сейчас), **9ч → закрытие** (abandoned, сейчас 8ч).
- Приглашение (3ч): «Вы начали заполнять анкету — продолжим?» + кнопка **«▶️ Продолжить анкету»** с takeover-флагом (см. FR-5); «⏭️ Прервать».
- Каждая ступень отправляется один раз: новое поле `continueInvitedAt` в агрегате анкеты (аналог `warnedAt`, с обходом safeUpdate — таймер простоя не сбрасывается).
- Все пороги и интервал — **именованные константы в файле job'а**: `INVITE_AFTER_HOURS = 3`, `WARN_AFTER_HOURS = 6`, `ABANDON_AFTER_HOURS = 9`, `INTERVAL_MS`.

### FR-5: Takeover — явный перехват ввода
- Опциональное свойство кнопки `{ text, code, takeover?: true }` в `KeyboardDescription` — доступно всем сторям.
- **Кодирование/снятие маркера — уровень uiApp**: при отправке uiApp добавляет маркер-префикс в `code` кнопок с `takeover: true`; при приёме первым делом снимает маркер и получает флаг. Транспорт, контроллер и стори работают с «нативным» кодом и маркера не знают.
- **Решение о блокировке — uiApp**: при активном чужом `activeHandler` и takeover-флаге callback НЕ блокируется alert'ом «Сначала завершите текущее действие»; захват ввода перезаписывается новой стори.
- **Уведомительная строка — транспорт (execute)**: если в команде есть кнопка с `takeover === true` (структурное поле, не маркер) и `session.activeHandler != null`, вниз текста добавляется абстрактная строка: «⚠️ Нажатие на кнопку приведёт к окончанию вашего текущего действия.» Формулировка не привязана к анкетам — код переиспользуемый.
- Причина разделения уровней: `SessionData` доступна транспорту всегда (интерактив + проактив из sessionMap), а uiApp получает сессию только в интерактивном потоке.

## Критерии приёмки
1. Радио: выбор → `(x)` в отредактированном сообщении, кнопки убраны → новый вопрос новым сообщением.
2. Мульти: тогглы редактируют сообщение на месте (кнопки живы); «Далее» только при ≥1 выбранном варианте; при «Далее» кнопки убраны, маркировки видны → новый вопрос новым сообщением.
3. Takeover: при активном действии (например, уроке) нажатие «▶️ Продолжить анкету» перехватывает ввод без alert-блокировки; внизу сообщения с takeover-кнопкой — предупреждение об окончании текущего действия; без активного действия строка не добавляется.
4. Job: 3ч → приглашение (с takeover-кнопкой), 6ч → предупреждение, 9ч → закрытие; каждая ступень один раз; возобновление заполнения сбрасывает цепочку.
5. `/cancel`, приглашения, завершение — работают как раньше.
6. Likert-анкеты — проверить на регрессии (если используют общий рендер — адаптировать аналогично).
