# Спецификация: Домен и API отзывов (peer-review)

> Трек 2 из трёх ([концепция](../../roadmap/metrics/peer-review-system.md), §5; порядок:
> `student-status` → этот трек → `peer-review-ui`).
> Зависимость: API статусов и признаков студента — трек
> [`student-status`](../../archive/student-status_20260916/index.md).
> Спека экранов — [ui-spec.md](../../../apps/u7-bot/src/controllers/peer-review/ui-spec.md) (утверждена владельцем).

## Обзор

Доменная основа системы отзывов: по завершению потока (триггер события
`stream.completed`) создаётся кампания сбора отзывов контекста `stream_completed`
— «студент завершил поток» (снапшот участников, окно 7 дней),
участники пишут текстовые отзывы друг о друге по правилам адресации. UI не
входит — трек `peer-review-ui` (зависит от этого трека).

Проектные решения перенесены из сессии проектирования (см. «Зафиксированные
решения»).

## Функциональные требования

### Зона `packages/stream`

- **ФР-1. Событие `stream.completed`.** `StreamAr.complete()` кладёт событие
  (payload: `streamId`); `CompleteStreamUc` публикует его через `publishEvents`
  после сохранения. Модель — существующие события пакета (`stream.created`).
- **ФР-2. Инвариант терминальности при завершении потока.** Завершение потока
  блокируется, пока у любого студента статус `active` **или `enrolled`** —
  координация двух агрегатов модуля в `StreamDs.completeStream(stream,
  students)`: гвард по `StudentAr.isTerminal()` (терминальные: `abandoned`,
  `advanced`, `not_advanced`), при нарушении — доменная ошибка `STREAM_CONFLICT`
  со списком нетерминальных (`{ userId, status }[]`), затем `StreamAr.complete()`
  (переход статуса + событие ФР-1). UC — оркестрация без доменных знаний.
  До завершения ментор разрешает судьбу каждого студента (снятие/завершение).
- **ФР-10. Вычистка разбора статусов студента из чужих зон.** Сырой разбор
  `status` студента вне зоны Student (кроме контрактов входа команд/событий)
  заменяется read-API `StudentAr` (`isTerminal()` — ФР-2, `isInProgress()`,
  `isEnrolled()`, `isPassed()`):
  - домен: `StreamAr.enroll()` (конфликт активных записей),
    `StreamPolicy.canEnrollNextModule()` (признак «прошёл»),
    `StreamDs.categorizeStudents()` (активные);
  - api: `GetStudentByUserUc` (выбор активной/завершённой записи),
    `ActivateStreamUc` (активация зачисленных);
  - ui: `view-stream.story`, `monitor` (блоки отставания/активности).
  Словарь статусов знает только зона Student (трек `student-status`).

### Зона `packages/peer-review`

- **ФР-3. Агрегат `ReviewCampaign`** — кампания сбора фактов, каркас +
  типизированный payload по `context` (дискриминант; сейчас только
  `stream_completed`):
  - каркас: `uuid`, `context`, `scopeId`, `createdAt`, `expiresAt`, `participants[]`;
  - `expiresAt` вычисляется при создании и **сохраняется** (константа окна в домене
    пакета: 7 дней для `stream_completed`); методы `isExpired(now)`, `daysLeft(now)`,
    `ensureLive(now)` (доменная ошибка «возможность закрыта») читают состояние;
  - `participants[]` — снапшот на момент создания: `{ userId, role: 'student' |
    'mentor', outcome }`; `outcome` — исход автора в терминах модуля (собственная
    проекция, не копия статусов студента): `completed` «завершил» / `dropped`
    «забросил» / `never_started` «не начал»; проекция вычисляется при создании
    кампании через API статусов и признаков студента (трек `student-status`:
    категория исхода + признак «не начал»); сырые статусы (`advanced`,
    `abandoned`, …) в кампанию и UI не попадают;
  - фабрика **`ReviewCampaignFactory`** по образцу `QuestionnaireFactory`
    (`packages/questionnaire/src/domain/questionnaire/questionnaire-factory.ts`):
    `createStreamCompleted(scopeId, participants, now)` (по имени контекста),
    в будущем — create-методы по типам кампаний;
    `restore(state)` по дискриминанту `context` для репозитория. UC вызывает
    фабрику (агрегат не создаёт агрегат).
- **ФР-4. Агрегат `Review`** — текстовый отзыв: `campaignId`, `authorId`,
  `authorRole`, `authorOutcome` (снапшот кампании), `recipientId`, `recipientRole`,
  `text` (10–3500), `createdAt`, `updatedAt`. Уникальность пары `(campaignId,
  authorId, recipientId)` — инвариант репозитория; перезапись — `overwrite(text)`
  в пределах окна.
- **ФР-5. Политика адресатов** `ReviewPolicy`: автор `completed` («завершил») →
  все студенты кампании + ментор; `dropped`/`never_started` → только
  ментор; ментор → все студенты. Никогда — отзыв о себе.
- **ФР-6. UseCase'ы** (все ошибки — доменные, тексты пользовательские):
  - `create-campaign` — по событию/команде: сбор участников фасадом stream,
    проекция исходов — через API статусов студента (трек `student-status`),
    фабрика, сохранение, публикация события
    `campaign.created` (payload: campaignId, context, scopeId — основа приглашений
    UI-трека);
  - `get-my-campaigns(query)` — кампании с участием пользователя; `query` — юнион:
    `{ kind: 'only_lives' }` — живые кампании + прогресс (мои отзывы M /
    доступные адресаты K) + остаток дней (сценарий хаба S02); и
    `{ kind: 'filter', live: boolean, context?, scopeId? }` — выборка с
    параметрами (история, будущие потребности). Живость в выборке — критерий
    репозитория («дай активные»), прогресс и дни — домен;
  - `get-campaign-recipients` — адресаты автора по политике + признак «мой отзыв
    уже есть» (✅ в UI);
  - `create-review` — создать/перезаписать: UC берёт кампанию из репо по id и
    проверяет адресата политикой и текст — валидацией; живость окна подтверждает
    агрегат (`ensureLive(now)` — доменная ошибка «возможность закрыта», отличает
    «окно закрыто» от «кампания не найдена»). UC не сравнивает даты сам;
  - `list-scope-reviews` — все отзывы по скоупу (группировка по адресатам, с
    снапшотами ролей/исходов для рендера).
- **ФР-7. ER `stream-completed-er`**: на `stream.completed` (триггер завершения
  потока) → `create-campaign` контекста `stream_completed` (идемпотентность:
  повторное событие не создаёт дубль). В будущем триггер переносится на личное
  событие `student.completed` — техдолг концепции §4.1, каркас не меняется.
- **ФР-8. Инфраструктура**: `PeerReviewApiModuleMeta`/Resolver, json-репозитории
  кампаний и отзывов (по образцу существующих); критерий «активная кампания» —
  часть контракта репозитория: `findActiveByUser(userId)` для списков и фасада
  `hasLiveCampaigns` (репо знает, как отобрать активные в хранилище — это
  условие выборки, не бизнес-правило), bootstrap с подпиской ER,
  регистрация модуля в приложении. Старый код пакета: `peer-review-question-pool.ts`
  остаётся (основа будущего этапа анкет — реальные данные вопросов);
  `assessment.ts` (папка `peer-review/`) удалён (решение владельца, Фаза 3):
  контракт старого дизайна до кампаний, поглощён новой кампанией
  (context/роли-исходы/triggerEvent — `ReviewCampaign` и ER); при этапе анкет
  `ownerInfo` будет формироваться из кампании. `scores.ts`/`categories.ts`
  перенесены в пакет-заготовку `packages/dossier`
  (модуль агрегации «досье», README рядом) — в peer-review осталось только
  то, что нужно этому модулю.
- **ФР-9. Фасад** (для UI-трека и других модулей): `hasLiveCampaigns(userId)`,
  `hasReviews(scopeId)`, `listScopeFacts(scopeId)` — только чтение.

## Нефункциональные требования

- TDD (workflow проекта), покрытие нового кода >80%.
- `bun run lint` (biome) и `bun run tslint` — чисто по скоупу трека.
- Интеграционный тест вертикали: событие → ER → кампания → отзыв → чтение.

## Зафиксированные решения (из сессии проектирования)

1. Кампания — каркас + payload (вариант C), не подклассы и не «всё в одном».
   Контекст — `stream_completed` в семантике «студент завершил поток» (о студенте,
   не о факте закрытия потока: смена триггера с потокового события на личное не
   меняет имя). Отклонена владельцем
   альтернатива «агрегирующая кампания модуля с дочерними досье сессий» —
   агрегация в `dossier`, сессии к модулю привязывает `sessions` (концепция §2.1).
2. `expiresAt` хранится; истёкшость — метод агрегата, не вычисление на лету в UC.
3. Шестой статус студента НЕ вводится; `enrolled` блокирует завершение потока,
   «не начал» — признак `neverStarted` из API студента (трек `student-status`);
   в снапшот кампании попадает проекция-исход, а не сырой признак (решение 6).
4. Фабрика — доменный объект по образцу анкет (create-методы + restore).
5. `campaign.created` публикуется доменом: приглашения (S01) — подписка UI-трека,
   домен о доставке не знает.
6. Исходы участников — собственная проекция peer-review из трёх значений
   (`completed`/`dropped`/`never_started`), вычисляемая при создании кампании
   через API студента; не копия студенческих статусов и их словаря меток
   (решение владельца): политике адресации и текстам UI достаточно трёх
   исходов, знание «прошёл/не прошёл» остаётся в зоне stream.
7. Живость кампании: выборка живых — контракт репозитория (`findActiveByUser`,
   критерий «активная» — условие выборки, репо вправе его знать); подтверждение
   живости конкретной кампании — агрегат (`ensureLive`, различает «окно
   закрыто» и «не найдено»); UC — оркестрация без доменных знаний (решение
   владельца: «UC просто оркестрирует доменными объектами»).
8. Время (`now`) передаётся в агрегат/фабрику явно: агрегат — чистая модель,
   отвечает на вопросы относительно момента T; взятие «сейчас» — зона
   ответственности вызывающего (UC/ER). Даёт детерминированные тесты (границы
   окна без моков часов) и единый T на всю транзакцию.
9. Инвариант терминальности завершения потока — координация двух агрегатов
   модуля (Stream + Student), поэтому живёт в `StreamDs.completeStream()`, а не
   в `StreamAr.complete()`: агрегат Stream не знает словарь статусов студента,
   терминальность спрашивает у `StudentAr.isTerminal()` (решение владельца,
   сессия 2026-09-17: «UC не принимает решения; пересечение двух агрегатов —
   зона DS»). Попутный найденный баг: текущий `CompleteStreamUc` блокирует
   только `active` — `enrolled` не блокирует (закрыт этим треком).
10. Попутный баг-фикс трека (решение владельца): вычистка разбора сырых
    статусов студента из чужих зон (домен/api/ui) на read-API `StudentAr` —
    отдельная фаза плана (ФР-10), включая обновление примера в
    `conductor/code_styleguides/domain-boundaries.md` §3.
8. Время (`now`) передаётся в агрегат/фабрику явно: агрегат — чистая модель,
   отвечает на вопросы относительно момента T; взятие «сейчас» — зона
   ответственности вызывающего (UC/ER). Даёт детерминированные тесты (границы
   окна без моков часов) и единый T на всю транзакцию.

## За рамками

- Весь UI отзывов (экраны S01–S07, приглашения, меню, пагинация) — трек
  `peer-review-ui`. Исключение — минимальные правки существующих сторис в ФР-10
  (замена предикатов на read-API `StudentAr` без изменения поведения).
- API статусов и признаков студента, словарь меток — трек `student-status`
  (этот трек только потребитель).
- Анкеты в кампании, exit-кампании, сессионные контексты — техдолг концепции (§4).
- Агрегация метрик (`metrics`), цифровой паспорт (`passport`).
- Приглашения-задачи (task-модуль) — после его появления.

## Критерии приёмки

- Завершение потока с `active`/`enrolled` студентом невозможно (тест DS и UC).
- Вне зоны Student нет сравнений `status` студента с литералами, кроме
  контрактов входа команд/событий (grep-контроль, ФР-10).
- После завершения потока публикуется `stream.completed`; ER создаёт ровно одну
  кампанию (идемпотентно), участники — снапшот с исходами-проекциями.
- Отзыв пишется/перезаписывается в окне; после окна — отказ «возможность закрыта».
- Адресация по исходам автора соответствует ФР-5 (тесты политики).
- `CI=true bun test`, `bun run lint`, `bun run tslint` — чисто по скоупу трека.
