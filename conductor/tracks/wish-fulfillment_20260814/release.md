# Релиз: wish — реализация желания при зачислении + удаление роли CANDIDATE

> **Для агента, выполняющего выкатку в прод.** Выполняй пункты по порядку.
> После каждого пункта — проверь результат. Если пункт не удался — остановись
> и сообщи владельцу. Все команды выполнять из корня репозитория на проде.

## Контекст

Студент при зачислении на поток теперь автоматически реализует своё желание
на курс (статус wish → `fulfilled`) через событие `student.enrolled`.
Роль `CANDIDATE` удалена из системы — информация о желаниях живёт в
`data/wishes/wishes.json`, информация о зачислениях — в `data/streams/students.json`.

Изменения кода подхватятся обычным способом (git pull + перезапуск бота).
Ниже — то, что **не делается кодом**: миграция данных и ручная верификация.

## 1. Миграция данных: удаление роли CANDIDATE

**Где данные:** каталог прод-данных задаётся env-переменной `DB_DIR`
(по умолчанию `data/`). Ниже `<dbDir>` — этот каталог.

**Шаг 1.1. Бэкап.**

```bash
cp <dbDir>/users/users.json <dbDir>/users/users.json.bak-$(date +%Y%m%dT%H%M%S)
```

**Шаг 1.2. Удалить роль CANDIDATE из всех записей пользователей.**

Файл: `<dbDir>/users/users.json` — JSON-массив записей вида
`{ ..., "roles": ["CANDIDATE", ...] }`.

Правило:
- убрать `"CANDIDATE"` из массива `roles` каждой записи;
- если после этого массив `roles` **пуст** — удалить запись пользователя
  целиком: схема `User` требует минимум одну роль, а пользователь с единственной
  ролью CANDIDATE — кандидат без других статусов; его желания сохранены в
  `wishes.json` и реализуются при следующем зачислении.

```bash
python3 - <<'EOF'
import json

path = '<dbDir>/users/users.json'  # подставь реальный путь
with open(path) as f:
    users = json.load(f)

result = []
removed_users = 0
removed_roles = 0
for u in users:
    roles = [r for r in u.get('roles', []) if r != 'CANDIDATE']
    removed_roles += len(u.get('roles', [])) - len(roles)
    if not roles:
        removed_users += 1
        continue  # пользователь терял единственную роль — удаляем запись
    u['roles'] = roles
    result.append(u)

with open(path, 'w') as f:
    json.dump(result, f, ensure_ascii=False, indent=2)

print(f"roles removed: {removed_roles}, users removed: {removed_users}, users left: {len(result)}")
EOF
```

**Шаг 1.3. Проверка миграции.**

```bash
grep -rn "CANDIDATE" <dbDir>/ && echo "НАЙДЕНЫ ОСТАТКИ — остановись" || echo "OK: CANDIDATE отсутствует"
python3 -c "import json; json.load(open('<dbDir>/users/users.json')); print('OK: JSON валиден')"
```

**Шаг 1.4. Запуск и проверка загрузки.**

Запусти бота (обычный прод-процедуру). Проверь:
- бот стартует без ошибок валидации пользователей;
- команды, читающие пользователя (например, «Моя учёба»), работают.

При ошибке валидации — восстанови из бэкапа (Шаг 1.1) и сообщи владельцу.

## 2. Ручная верификация: событие student.enrolled (Фаза 1)

Проверяется «на живом» боте. Понадобится: аккаунт студента с подтверждённым
желанием на курс (wish в статусе `expressed` или `confirmed` в `wishes.json`)
и enrollmentKey потока этого курса.

| # | Действие | Ожидаемый результат |
|---|----------|---------------------|
| 1 | Запиши студента на поток (кнопка «Записаться» / enrollKey) | Зачисление успешно |
| 2 | Проверь `<dbDir>/users/users.json` | У пользователя появилась роль `STUDENT`, роль `CANDIDATE` **не** тронута (её больше нет в системе) |
| 3 | Проверь `<dbDir>/streams/students.json` | Новая запись студента со статусом `enrolled` |
| 4 | Проверь `<dbDir>/wishes/wishes.json` | Желание пользователя на этот курс — статус `fulfilled` |
| 5 | Telegram | Студенту пришло сообщение «🎓 Ты зачислен в поток „<название>“! Начинай учёбу: Моя учёба.» |
| 6 | Повтори зачисление другого студента с желанием при выключенном интернете у бота (или недоступном Telegram) | Зачисление всё равно проходит (сбой уведомления не мешает) |

Пункты 4–5 можно проверять с задержкой: событие обрабатывается синхронно сразу
после зачисления.

## 3. Ручная верификация: fulfill-wish (Фаза 2)

Понадобится: два студента, курс с опубликованной программой и активный поток
этого курса.

| # | Действие | Ожидаемый результат |
|---|----------|---------------------|
| 1 | Студент A выражает желание на курс (каталог → «Хочу пройти») | В `wishes.json` появилось желание в статусе `expressed` (или `confirmed` после анкеты) |
| 2 | Студент A записывается на поток этого курса | Зачисление успешно; желание A стало `fulfilled` |
| 3 | Студент B с желанием на ДРУГОЙ курс записывается на поток первого курса | Зачисление успешно; желание B осталось активным (`expressed`/`confirmed`) — не реализовалось |
| 4 | Студент с уже `fulfilled`-желанием записывается на другой поток того же курса | Без ошибок; статус не меняется (идемпотентность, ER молча пропускает) |
| 5 | Админ архивирует курс, в котором у студента активное желание; студент записывается на поток курса-форка с тем же moduleId | Желание реализуется: архивный курс найден через `filterCoursesContainingModule` (история) |
