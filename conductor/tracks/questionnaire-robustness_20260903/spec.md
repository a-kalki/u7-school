# Спецификация — Трек: questionnaire-robustness_20260903

**Тип:** bugfix
**Название:** Устойчивость анкеты: graceful-обработка неактуальных ответов, MarkdownV2-мины, честный прогресс и condition на multiple

## Обзор

Инцидент 2026-09-03 15:14 (36 критических ошибок за 5 секунд в Logger Bot, пользователь telegramId 5528270576) вскрыл хрупкость флоу анкеты:

1. **Первичный баг:** нажатие кнопки устаревшей клавиатуры (после двойного `/start` гонка сессий оставила старые кнопки) передаёт в агрегат код ответа, не принадлежащий текущему вопросу. `BaseQuestionnaireAr.#submitCurrentQuestion` (`packages/questionnaire/src/domain/questionnaire/a-root.ts:381`) превращает провал valibot-валидации в `throwInternal` → `AR_INTERNAL_ERROR` (kind=internal).
2. **Мультипликатор:** fallback-текст внутренней ошибки (`packages/core/src/ui/bot/bot-ui-story.ts:277`) содержит неэкранированную точку → `MarkdownV2ValidationError` в fail-fast валидаторе (`apps/u7-bot/src/infra/bot-transport.ts:332`) → сообщение об ошибке не отправляется вовсе → пользователь без обратной связи спамит кнопками (18 кликов → 36 ошибок).

Дополнительно в движке анкет найдены латентные дефекты: condition на multiple-вопрос не срабатывает никогда; прогресс «Вопрос N из 11» считает чужие ветки; `inviteText` вставляется в MarkdownV2 без экранирования.

Проверено на реальном коде: все «свои» варианты ответов обоих вопросов «Какое время занятий…» (`base_time` — 8, `intensive_time` — 4) проходят валидацию; падают только чужие коды кнопок, пустой «Далее» и произвольный текст.

## Функциональные требования

### FR-1. Graceful-обработка неактуального ответа (P0-A, вариант A — контрактный)

- Домен (`packages/questionnaire`): в `types.ts` добавляется новый вариант ответа `'stale_answer'` с полями текущего вопроса (`questionnaireId`, `question`, `selectedAnswers`, `progress`, `cancelWarning`, `reason`) и причиной:
  - `'stale_button'` — код ответа не принадлежит текущему вопросу (устаревшая клавиатура);
  - `'empty_selection'` — «Далее» без единого выбора на multiple-вопросе.
- `BaseQuestionnaireAr.#submitCurrentQuestion`: провал valibot-валидации → **не** `throwInternal`, а `stale_answer` с соответствующим reason.
- `BaseQuestionnaireAr.#toggleDraftAnswer`: код ответа проверяется против `answers` вопроса **до** записи в драфт; чужой код → `stale_answer` (`'stale_button'`), драфт не изменяется. Существующие протекшие драфты **не чистим** (решение зафиксировано пользователем).
- UI (`apps/u7-bot`, fill.story + render): `stale_answer` рендерится как перерисовка актуального вопроса с коротким пояснением по reason («Эта кнопка относится к предыдущему вопросу…» / «Сначала выбери хотя бы один вариант»). `releaseInput` не выполняется — флоу продолжается, `captureInput` сохраняется.
- Наблюдаемость: story логирует `logger.warn` (не error) с нажатым и актуальным questionCode — сигнал сохраняется, но не попадает в критические ошибки Logger Bot.

### FR-2. MarkdownV2-мины (P0-B + смежные)

- `packages/core/src/ui/bot/bot-ui-story.ts` (`handleError`): fallback-текст внутренней ошибки — заэкранировать точку (по образцу `bot-controller.ts:376` — `обратитесь к администратору\\.`).
- Там же, ветка `validation`: экранировать `field`/`message` через `escapeMarkdown` (сейчас склеиваются в MarkdownV2-текст как есть).
- `apps/u7-bot/src/controllers/questionnaire/stories/invite.story.ts`: экранировать `inviteText` в `#handleInviteEvent` и `#handleInvite` (по образцу `#handleWhy`, где `whyText` уже экранируется).

### FR-3. Condition на multiple-вопрос (движок)

- `QuestionnaireEngine.getNextQuestion`: сравнение через разбиение `answerCode` по запятой и any-of (`some`) — для одиночных ответов поведение не меняется (split даёт тот же один код).
- Инвариант в `QuestionnaireEngine.validate()`: `condition.questionCode` должен ссылаться только на вопрос, стоящий **раньше** в пуле; иначе — ошибка валидации пула при загрузке. Инвариант гарантирует разрешимость всех условий на момент показа вопроса.

### FR-4. Честный прогресс

- `QuestionnaireEngine.getProgress(questionCode, answers)`: маршрут считается с начала пула с применением условий по уже известным ответам; `total` = число активных вопросов маршрута, `index` — позиция текущего среди них.
- Агрегат (`#progress`) передаёт `state.answers`.
- Ожидаемый результат на реальном пуле: intensive-ветка — «N из 9», base-ветка — «N из 10» вместо нынешних «N из 11».

### FR-5. Гонка сессии при двойном /start (P1)

- Исследовать перезапись `session.lastBotMessage` при параллельных работах одного чата (двойной `/start` + answer-callback в одной пачке апдейтов); механику задокументировать в плане трека.
- Реализовать минимальный guard: `editMessage` не должен применяться к сообщению, не относящемуся к активному флоу; при коллизии — пропустить edit (остаётся fallback-sendMessage). Детальный дизайн фиксируется в плане перед реализацией.

## Критерии приёмки

1. Клик по кнопке устаревшей клавиатуры не создаёт записей CRITICAL в логе Logger Bot; пользователь получает перерисованный актуальный вопрос с пояснением и продолжает анкету.
2. «Далее» без выбора не создаёт CRITICAL; вопрос перерисовывается с подсказкой.
3. Чужой код ответа не попадает в `draftAnswers`.
4. Условие ветвления на multiple-вопрос срабатывает при пересечении выбранных кодов (тест).
5. Пул с condition «вперёд» отвергается при загрузке (тест).
6. Прогресс показывает позицию и total по реальной ветке (тесты на обе ветки: base=10, intensive=9).
7. Fallback-текст ошибки и сообщения валидации проходят `assertMarkdownV2Safe` (тест).
8. `inviteText` с точками/спецсимволами отправляется корректно (тест экранирования).
9. `bun run check` чистый по всему монорепо.
