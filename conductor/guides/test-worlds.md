# Тестовые миры — концепция

**Назначение:** определяет подход к тестовым данным проекта: декларативные «миры» вместо ручных JSON-фикстур. Документ — основа для трека миграции; конкретные решения фиксируются в его spec.md.

---

## 1. Зачем миры

Сейчас фикстуры (`apps/u7-bot/tests/fixtures/templates/*.json`, сид — `apps/u7-bot/scripts/seed-fixtures.ts`) — набор независимых JSON-ов. Согласованность между модулями держится на ручной склейке и ломается: кампания peer-review существует о студенте, который в потоке ещё учится; роли пользователей противоречат их статусам. В проде такие состояния невозможны — кампания рождается из события судьбы студента, поэтому её данные всегда согласованы.

**Мир** — декларативное описание согласованного состояния всех модулей («три курса, два активных потока, студент завершился 2 дня назад…»). Все JSON-фикстуры — артефакты генерации из этого описания. Неконсистентный мир не генерируется: инварианты проверяются конструкторами.

## 2. Принципы

1. **Один источник правды.** Правится описание мира; файлы фикстур руками не правятся никогда.
2. **Консистентность по построению.** Инварианты (судьба кампании == исход студента, роль пользователя == статус в потоке) живут в конструкторах world-kit. Команда `world:check` валидирует мир.
3. **Продуктовое качество контента** — см. раздел 6.
4. **Детерминированность.** UUID выводятся из ключей сущностей (стабильны между генерациями — на них завязаны тесты). Время описывается относительно (`T-2д`), при генерации превращается в полные абсолютные даты — без заглушек и переменных.
5. **Минимальная достаточность.** Каждая сущность мира существует, потому что покрывает конкретный проверочный сценарий.

## 3. Два слоя

- **world-kit** — общая библиотека: конструкторы сущностей (`person`, `course`, `stream`, `student`, `campaign`, `application`…), инварианты, реестр персон dev-режима (из него генерируется список `/persona`), генератор: в JSON-файлы (для сида) и в память (для тестов).
- **Миры** — композиции примитивов под конкретную цель. Стартовый набор:
  - `core-education` — основной: курсы; завершённый поток (живая кампания «по построению» + истёкшая), активный поток со студентами без исходов (E2E «роль-судьба»), поток в приёме; два ментора (изоляция и мульти-поточность);
  - `onboarding` — воронка гость → кандидат → студент (questionnaire, wish);
  - `minimal` — только dev-персона, для дымовых прогонов.

## 4. Потребители и запуск

Один генератор, два потребителя:

- **Ручной прогон бота:** `WORLD=<имя> bun run dev:fixtures` (без `WORLD` — дефолтный мир). В `data/fixtures/` кладётся манифест `world.json` (имя, хеш исходников) — бот при старте пишет, какой мир заряжен.
- **Автотесты (integration/E2E):** `buildWorld('<имя>')` в `beforeAll` — мир строится в память или временный каталог; заменяет текущий `loadFixtures()` (см. `conductor/code_styleguides/bot-test.md`).

Граница: юнит-тестам домена миры не нужны — там in-memory стабы дешевле.

## 5. Как править и создавать

- **Правка мира:** исходники мира → `world:check` → регенерация → коммит исходников и артефактов вместе.
- **Новый мир создаётся**, только если: (а) сценарий нельзя выразить существующим миром без его искажения, или (б) это другой домен/воронка по смыслу. Иначе — расширяем существующий мир.
- **Новая сущность/модуль** — расширение world-kit: конструктор + инварианты + правило генерации файла.
- **Миграция** (детали — в спеке трека): фаза 1 — генератор воспроизводит текущие templates 1:1 (контрольный тест эквивалентности); фаза 2 — тесты и dev-persona переводятся на `buildWorld`; фаза 3 — ручные templates удаляются.

## 6. Реалистичность: правило продуктового качества

Мир должен быть неотличим от прода **глазами пользователя** — это условие осмысленности ручных проверок и демо.

- Уроки и шаги: не «Урок 1 / пара слов», а осмысленные названия + **один-два связных абзаца** (что это, зачем, как изучать) — как реальный контент курса.
- Имена людей, названия курсов/потоков — человеческие и согласованные между модулями.
- URL и внешние ссылки — полные, без заглушек и переменных-заменителей (см. AGENTS.md).
- Тон текстов — как в проде (обращение на «ты», без канцелярита).

**Критерий:** скриншот экрана из dev-бота не должен отличаться от прод-скриншота. Если контент выглядит «по-тестовому» — это дефект мира, а не допустимая условность. При наполнении уроков руководствоваться `conductor/guides/lesson-design.md`.
