## 1. Позиция в курсе и прейреквизиты

Курс Fullstack-js (модули):

1. **М1 «Синтаксис»** — язык: переменные, типы, операторы, ветвления, циклы, функции, области видимости, модули (import/export), рекурсия. Практика: расчёт зарплаты (ИПН, ОПВ), TDD-порог.
2. **М2 «Алгоритмика»** — алгоритмическое мышление: ~60 функций-аналогов String/Array/Object API, сортировки, поиск, O-нотация, Git/GitHub, ветки, Pull Request, код-ревью, JSDoc.
3. **М3 «HTML & CSS»** — вёрстка UI портала с жёсткими данными.
4. **М4 «DOM»** — логика портала на чистом JS поверх свёрстанного HTML.

**Что студент уже умеет к началу М3** (использовать в уроках, не переучивать):

- промисы, async/await, fetch, события браузера (до М4)
- замыкания как термин, каррирование, паттерны проектирования

## 2. Сквозной продукт: приложение «Портал предприятия»

Оба модуля строят **одно приложение** — развитие домена проекта 3 модуля 1 (функции `calcEmployee` / `calcDepartment`): расчёт зарплаты сотрудников предприятия, но уже как веб-приложение в браузере.

### 2.1. Ключевой принцип: HTML — источник данных

Все данные приложения **жёстко вшиты в HTML** на этапе вёрстки (М3). В М4 JavaScript читает данные прямо из DOM, считает и выводит результат; затем разделы по очереди получают ввод — JS правит DOM и сохраняет изменения. Схема намеренно примитивна («DOM как база данных»): она даёт прямое понимание того, как устроены HTML, CSS, JS и DOM и как они взаимодействуют, и знакомит с browser API. Почему так не делают в больших приложениях и как правильно — разбирается в финальном этапе М4 (§7).

### 2.2. Зоны интерфейса

```
┌──────────────────────────────────────────────────────┐
│ [лого]     ТОО «Дала Технолоджи»                    │  ← шапка: только
├────────────┬─────────────────────────────────────────┤    лого и имя
│  Сайдбар   │  Основной раздел (main)                 │
│  (разделы  │  Секции: данные предприятия и таблицы   │
│  ввода +   │  расчёта; в М3 — сплошным потоком       │
│  Результат)│                                         │
└────────────┴─────────────────────────────────────────┘
```

Каждый пункт сайдбара отвечает за **ввод определённых данных** (в М3 — за их отображение).

### 2.3. Разделы портала

| Пункт сайдбара | Назначение | Представление |
|---|---|---|
| Штат | штатное расписание: отделы, должности и оклады | таблица: отдел — должность — оклад |
| Календарь | параметры расчёта | название компании + таблица месяцев с нормой рабочих дней |
| Сотрудники | список сотрудников компании | таблица: имя, фамилия, должность, отдел, дата приёма |
| Табель | отработанные дни за месяц | таблица: месяц — сотрудник — отработанные дни |
| Результат | расчёт зарплаты | таблица по сотрудникам по выбору месяца и отдела: начислено, ИПН, ОПВ, на руки + строка ИТОГО |

Секции в main идут сплошным потоком: все разделы видимы при прокрутке (М3). В М4 JS добавляет скрытие неактивных секций и переключение по выбору в сайдбаре.

### 2.4. Эволюция приложения (драматургия двух модулей)

| Этап | Где | Что происходит |
|---|---|---|
| 1. Жёсткая вёрстка | М3, все проекты | Портал свёрстан целиком, все данные вшиты в HTML, включая посчитанный «Результат». Все секции видимы, идут сплошным потоком. Ничего не работает, но выглядит цельно |
| 2. Навигация | М4, проект 1 | Первый живой JS: скрываем неактивные секции; клик по сайдбару переключает видимый раздел |
| 3. Результат из страницы | М4, проект 2 | «Результат» вытаскивает данные из HTML остальных разделов (парсит таблицы), считает функциями и выводит. Дальше логика вывода **не меняется**: всегда парсит из HTML |
| 4. Ввод по очереди | М4, проекты 3–4 | Разделы по очереди переводятся на ввод: кнопка изменения → форма → submit → правка DOM → автопересчёт результата → сохранение в localStorage. Первые разделы — вместе с ментором, остальные — самостоятельно по аналогии |
| 5. Сохранение | М4, проект 3–4 (по мере ввода) | Правки сохраняются в localStorage и восстанавливаются при загрузке; сброс к исходным |
| 6. «Как правильно» | М4, проект 5 | Теория: домен и ui, данные как источник правды. Самостоятельная работа: студент пробует перестроить приложение, как считает нужным. Ретроспектива модуля |

**Мы даём (контракт):**

- нормы оформления: конкретные значения по элементам и группам (цвета, отступы, размеры — едины с референсами; перечень — в плане модуля 3 §7.1)

- формулы расчёта (§4)
- последовательность теории и мини-заданий

**Студент решает сам (свобода):**
- как применить нормы: сам находит нужный элемент в своей странице, подбирает селектор/класс и свойство, вешает указанное значение
- как разбить вёрстку на блоки, как назвать классы, как организовать CSS
- детали, не охваченные нормами: конкретный шрифт, скругления, декор
- способ открытия формы ввода (модалка или inline-панель) и её устройство (М4)
- какие написать функции, как их назвать, как разложить по файлам (в рамках гигиены §6, М4)

Следствие: у студентов получаются **разные работающие решения** — это сознательно; на ревью обсуждаем вариативность, а не «единственный правильный код».

## 4. Домен и расчёт

Базовые правила — наследие М1 (проект 3: `calcEmployee`/`calcDepartment`; ставки из М1: **ИПН 10%, ОПВ 2%**). Валюта — тенге (₸).

### 4.1. Где живут данные

- В М3 все данные вшиты в HTML (эталонный набор — §5).
- В М4 вход расчёта — данные, **распарсенные из DOM** (textContent таблиц и карточек). Прямых «источников данных в JS» до финального этапа нет.
- Расчёт — чистые функции: на входе — распарсенные структуры данных, на выходе — результаты. Функции расчёта живут в отдельном файле (например `calc.js`) и подключаются import'ом; они не трогают DOM.

### 4.2. Расчёт зарплаты сотрудника за месяц

1. **Окладная часть:** `salary × workedDays / workingDays` (пропорция отработанных дней)
2. **Премия за полный месяц:** если `workedDays >= workingDays` → +10% от окладной части
3. **Надбавка за выслугу лет** (полные годы от даты приёма до 1-го числа расчётного месяца): ≥ 3 лет → +5% от окладной части; ≥ 5 лет → +10%. Пороги не суммируются, применяется больший
4. **Начислено (gross):** сумма пунктов 1–3
5. **Удержания:** ИПН = 10% от gross; ОПВ = 2% от gross
6. **На руки (net):** gross − ИПН − ОПВ
7. **Итог по предприятию с разбивкой по отделам:** суммы gross, ИПН, ОПВ, net по всем сотрудникам — эволюция `calcDepartment` из М1

**Округление:** расчёт ведётся по точным значениям; округление до целого ₸ (`Math.round`) — только при выводе в интерфейс.

### 4.3. Функции расчёта (эволюция кода М1)

- `calcEmployee(employee, salary, workedDays, workingDays, seniorityYears)` → `{ gross, ipn, ops, net }` — расширенная версия функции М1
- `calcDepartment(employeesCalc)` → итоговые суммы по отделу; итоги по предприятию — с разбивкой по отделам
- Входные структуры собираются парсером DOM (М4, проект 2): `{ firstName, lastName, position, department, hiredAt }`, `{ department, position, salary }`, `{ month, employee, workedDays }`, `{ month, year, workingDays }`

## 6. Технологические ограничения и гигиена (для всех уроков М3 и М4)

- **Ванильные технологии:** HTML + CSS (М3), + чистый JS (М4). Никаких фреймворков, библиотек, сборщиков, npm.
- **Без ООП:** классы, `this`, методы в объектах — не используем. Только функции + литералы объектов/массивов. ООП — будущие модули.
- **Данные — в HTML** (до финального этапа М4): никаких JS-констант с данными приложения; источником всегда выступает DOM (кроме localStorage как бэкапа правок).
- **Функции расчёта — отдельно от DOM-кода:** файл расчётов (например `calc.js`) подключается import'ом и не трогает DOM. Это единственное обязательное структурное требование (гигиена, а не «слои»).
- **События — персональные:** предпочтения на обработчики конкретных элементов (кнопка, форма, поле) через `addEventListener`. Глобальные событийные шины и CustomEvent по необходимости. Обновление результата после изменений — прямым вызовом функции перерасчёта.
- **localStorage:** появляется вместе с первым вводом (М4, проект 3): правка → сохранить; загрузка страницы → восстановить правки в DOM; отдельное действие — сброс к исходным (очистка хранилища и перезагрузка).
- **Запуск в браузере, не в Bun/Node:** ES-модули требуют локального сервера (Live Server) — инструкцию дать в первом уроке М4.
- **Валидация:** в М4 формы проверяются перед применением (required + js-проверка перед записью в DOM).
- **Адаптивность — не обязательна** (десктоп). Доступность — вкраплениями: label у полей, alt, контраст, видимый focus.
- **Формы:** теория форм проходится в М3 (на мини-заданиях вне приложения); формы приложения вёрстаются в М4 при переводе разделов на ввод.

## 7. «Как правильно» (финальный этап М4 — теория и свободное плавание)

В конце М4 студенту даётся теория правильной организации **в рамках этого приложения**: **двухслойная архитектура — домен + ui** — и основы проектирования приложений через **путь пользователя: ui → домен → ui**.

- **Домен (domain)** — данные приложения (единственный источник правды; загружаются один раз — исходные значения / localStorage) и чистые функции расчёта: данные → данные. Домен не знает о DOM.
- **UI (ui)** — рендер (данные → DOM) и обработчики событий (ввод в DOM → изменение данных + вызов расчёта + перерисовка).
- **Путь пользователя:** действие в интерфейсе (ui) → изменение данных и расчёт в домене → перерисовка интерфейса (ui). Каждый проход по этому пути — одно действие пользователя.
- **Направление зависимостей:** `ui → домен`. Никогда наоборот.
- Сравнение с пройденным путём: «DOM как база» работала, но парсинг хрупок (изменил вёрстку — сломался расчёт), данные размазаны по разметке, состояние неявное.

**Самостоятельная работа (свободное плавание):** студент пробует перестроить приложение по этой концепции (или своему варианту) — как считает нужным. Модуль уже пройден, вся база есть; ведение за руку отсутствует, ошибки допустимы и обсуждаются на защите. Это мостик к будущим модулям об ООП и архитектуре.

## 9. Правила проектирования и генерации уроков

Полные правила: `conductor/guides/lesson-design.md` (обязателен к прочтению перед генерацией шагов). Ключевое:

### 9.1. Структура урока

Папка урока: `data/fullstack-js/<модуль>/p<N>-l<M>-<kebab-name>/`. Нумерация `l` — с 1 в каждом проекте. Файлы:

- `lesson.md` — полный конспект урока: для теории на базе внешнего ресурса (w3) — структурированный пересказ с нашим контекстом; для собственной теории (М4) — полный конспект материала шагов-теорий
- `summary.md` — выжимка 10–15 строк (ключевые понятия; нужна следующим сессиям для проверки «изученного»)
- `steps.md` — генерируется отдельно (этап после утверждения конспектов)
- `mentor-files/` — только по явному запросу владельца; 20–30 строк / 10–15 `console.log`; `manifest.json`

### 9.2. Требования к контенту уроков

- **Язык — русский.** Код, имена, команды — английский, kebab-case для файлов студента (`calc-employee.js`, `payroll-portal/`).
- **Только изученное:** перед генерацией шагов читать `summary.md` всех предыдущих уроков; ничего не использовать раньше его урока. В М3 — порядок HTML/CSS-концепций по таблицам плана; в М4 — DOM/JS-концепции не опережают свои уроки; запрещены классы, this, промисы, fetch, компоненты.
- **Минимум один шаг формата «напиши/сделай по текстовой задаче»** в уроке.
- **Студенческие шаги:** одна концепция, 1–3 минуты, без пограничных случаев (пограничное — ментору).
- **Проектный урок** (`p<N>-l<последний>`) — сборка части портала по чек-листу; постановка на естественном языке («сделай так, чтобы...»), без готового кода.
- **Не подрывать драматургию:** до ретроспективы финала М4 не критиковать схему «данные в HTML» в шагах и конспектах; она — осознанный этап пути.
- **Теория без видео:** видеозаписи не используются. Теория — ссылка на страницу w3 (первый шаг урока) либо собственный шаг-теория. Собственная теория **всегда** закрепляется дополнительным заданием; для w3-теории закрепление опционально, если источник сам даёт упражнения.
- **Запрещены шаблонные переменные** (`$T1` и т.п.) — все URL и строки полностью.
- Числа в данных — без форматирования; формат вывода (пробелы-разделители, ₸) — только в полировке финала М4, единообразно внутри модуля.

### 9.3. Особенности проверки для М3/М4 (специфика веб-контента)

- Мини-задания М3: маленькие HTML/CSS-фрагменты (страничка-песочница); проверка — глазами и DevTools (Elements). Вопросы вида «что произойдёт со вёрсткой, если...».
- Мини-задания М4: короткие js-фрагменты + страница в браузере; проверка через DevTools Console.
- DevTools (Elements, Console) — вводим в М3-П1 и используем как основной инструмент проверки в обоих модулях.

### 9.4. Порядок работы над контентом (этапы)

1. Этот файл (концепция) — утверждается владельцем.
2. `module-plan.md` М3 и М4 — утверждается владельцем.
3. Генерация `lesson.md` + `summary.md` по всем урокам (по таблицам планов).
4. Генерация `steps.md` (шаги) — отдельная задача, по `lesson-design.md`.
5. `mentor-files/` — только по явному запросу.
6. Регистрация модулей в `data/courses/modules.json` + `lessons.json` — отдельная задача через скрипты платформы (не вручную).
