# Шаги урока: Архитектура сервиса: слои и зоны ответственности

### Задача проекта: локальный HTTP-сервис заказов

**kind:** `text`

В этом проекте мы построим настоящий локальный HTTP-сервис для интернет-магазина. Сервер будет работать на твоем компьютере, слушать сетевой порт и отвечать на запросы из браузера или терминала.

Сервис должен уметь выполнять пять базовых действий с заказами:
1. Выдать список всех заказов.
2. Найти конкретный заказ по его номеру.
3. Оформить новый заказ.
4. Изменить данные существующего заказа.
5. Удалить заказ из базы.

Если посмотреть на то, что происходит внутри программы при обработке хотя бы одного запроса, становится ясно: это не монолитная операция, а цепочка совершенно разнородных задач:
- **Сеть:** принять входящее TCP-соединение, извлечь URL, заголовки и параметры.
- **Безопасность и целостность:** проверить, корректны ли входные данные (не прислал ли клиент пустую строку вместо имени или отрицательную сумму).
- **Бизнес-правила:** сформировать объект заказа, назначить ему уникальный идентификатор (`id`), установить статус по умолчанию.
- **Хранение данных:** прочитать данные с жесткого диска, модифицировать их в памяти и записать обратно в файл `orders.csv`.
- **Формирование ответа:** упаковать результат в формат JSON, выставить правильный HTTP-код ответа (`200 OK` или `400 Bad Request`) и вернуть клиенту по сети.

Каждая из этих задач требует своего подхода, своих инструментов и может изменяться независимо от остальных.

### Почему код больше 200 строк требует организации

**kind:** `text`

Когда программа умещается в 30–50 строк, её легко держать в голове. Но как только размер приложения переваливает за 200 строк, отсутствие структуры может стать проблемой:

- **Смешение ответственностей:** в одном файле переплетаются парсинг сетевого запроса, манипуляции с файловой системой и валидация строк.
- **Невозможность изолированного тестирования:** чтобы протестировать валидацию имени клиента, разработчику приходится поднимать реальный веб-сервер и записывать тестовый мусор в реальный файл на диске.
- **Хрупкость изменений:** желание поменять формат хранения (например, перейти с CSV на JSON) ломает логику обработки сетевых роутов.

В индустрии такой код называют «спагетти-кодом». Любое исправление в одном месте неожиданно ломает функционал в трёх других.

Чтобы программа оставалась надёжной, расширяемой и простой для понимания, код организуют по двум осям:
1. **Сущности (Entities):** вокруг каких ключевых понятий предметной области крутится приложение (в нашем случае — «Заказ»).
2. **Слои (Layers):** на каких уровнях абстракции решаются технические и прикладные задачи программы.

---

### Понятие слоя и закон однонаправленности

**kind:** `text`

**Слой** — это горизонтальный пласт приложения с единой, строго очерченной зоной ответственности.

Главное правило слоистой архитектуры: **зависимости имеют строгую иерархию и направлены в одну сторону — сверху вниз**.

```text
[ Server ]      (точка входа и сетевой транспорт)
    ↓
[ Handler ]     (разбор HTTP-запроса, вызов доменной логики)
    ↓
[ Entity ]      (бизнес-модели, правила валидации данных)
    ↓
[ Repository ]  (операции сохранения и извлечения сущностей)
    ↓
[ Infra ]       (низкоуровневая работа с файловой системой)
    ↓
[ Utils ]       (чистые функции общего назначения)
```

Каждый слой может импортировать и использовать только то, что находится **ниже** него по иерархии:
- Обработчик (`Handler`) может вызывать Валидатор (`Entity`) и Репозиторий (`Repository`).
- Но Репозиторий (`Repository`) **никогда не знает** о существовании обработчиков или HTTP-сервера. Он просто умеет сохранять и доставать заказы.
- `Entity` — доменные валидаторы и фабрика `createOrder`: используются обработчиками для проверки входных данных и сборки заказа.
- `Repository` — хранилище данных: сохраняет и достаёт записи, но ничего не знает о сетевых обработчиках или правилах валидации.
- Инфраструктура (`Infra`) умеет читать и писать файлы на диск, но **ничего не знает про заказы**. Для неё это просто абстрактные массивы данных.
- Утилиты (`Utils`) — это чистые функции, которые вообще не имеют внешних зависимостей.

Обратные импорты снизу вверх и циклические зависимости (`A` импортирует `B`, а `B` импортирует `A`) категорически запрещены.

### Архитектура индивидуальна: поиск баланса

**kind:** `text`

Важно понимать: архитектура — это не догма и не слепое следование шаблонам из умных книжек.

В каждом реальном проекте архитектура выстраивается **индивидуально под конкретную решаемую задачу**:
- Если задача решается скриптом на 50 строк, разбивать его на 6 файлов и 4 слоя — грубейшая ошибка (оверинжиниринг). Сложность структуры превысит пользу.
- Чем больше в проекте слоев, тем больше файлов, связующего кода и промежуточных вызовов. Это плата за гибкость.
- Однако когда у проекта появляется хранилище, сеть, валидация и несколько сценариев отказа, отсутствие слоёв гарантированно превратит кодовую базу в болото.

Качественная архитектура держит **баланс**: ровно столько слоёв, сколько необходимо для ясного разделения ответственностей и лёгкого написания изолированных тестов, и ни одного лишнего слоя.

### Раскладка проекта `m3-p2-http`

**kind:** `text`

В ходе проекта мы выстроим внутри каталога `m2-m3-algorithms/m3-p2-http/` следующую структуру:

```text
fullstack-js/
  m2-m3-algorithms/
    utils/business/              # готовые утилиты: getQueryParams, toCSV, fromCSV
    m3-p2-http/
      infra/
        file-storage.js          # работа с файлами на диске (node:fs)
      app/
        entity/
          order.js               # фабрика createOrder
          validator.js           # проверка входных данных заказа
        repo/
          order-repo.js          # репозиторий: операции CRUD над заказами
        handler/
          list-orders.js         # обработчик GET /list
          get-order.js           # обработчик GET /get
          create-order.js        # обработчик GET /create
          update-order.js        # обработчик GET /update
          delete-order.js        # обработчик GET /delete
      server/
        server.js                # обёртка запуска сервера Bun.serve
        route.js                 # таблица маршрутизации path -> handler
        main.js                  # точка входа: сборка и запуск сервиса
      data/
        orders.csv               # файл базы данных
```

Обрати внимание на изоляцию:
- Каталог `infra/` — техническая реализация персистентности.
- Каталог `app/` — наше приложение, сердце бизнес-логики.
- Каталог `server/` — транспортный уровень запуска сервиса.
- Каталог `data/` — физическое хранение данных.

### Поток вызова: путь HTTP-запроса сквозь слои

**kind:** `text`

Давай проследим, как проходит запрос от момента, когда пользователь нажал Enter в браузере, до момента записи на диск.

Представим запрос: `GET /create?customer=Анна&amount=5000&isPaid=true`:

1. **Сетевой уровень (`server/server.js`):** Нативный движок `Bun.serve` ловит входящий запрос и передаёт управление в функцию диспетчеризации.
2. **Маршрутизация (`server/route.js`):** По совпадению пути `/create` выбирается соответствующая функция-обработчик `handleCreate`.
3. **Обработчик (`app/handler/create-order.js`):** Принимает сырой URL строкой, через `getQueryParams` разбирает параметры в объект сырых данных `{ customer: 'Анна', amount: '5000', isPaid: 'true' }` и вызывает фабрику `createOrder(params)`. Фабрика прогоняет поля через доменные валидаторы из `app/entity/validator.js`. Валидаторы приводят типы и проверяют правила. Если хотя бы одно правило нарушено, валидатор бросает `OrderValidationError`. Это исключение перехватывается централизованным обработчиком ошибок на уровне сервера, который возвращает клиенту валидный JSON с ошибкой и статусом `400`.
4. Если данные валидны, обработчик передаёт готовый заказ в репозиторий: `addOrder(orderData)`.
5. **Репозиторий (`app/repo/order-repo.js`):** Вычисляет следующий свободный `id`, добавляет новый заказ в массив и сохраняет на диск через инфраструктурный слой. Репозиторий работает с переданными данными без валидации.
6. **Инфраструктура (`infra/file-storage.js`):** Функция `saveToFile` сериализует массив объектов в CSV-строку через утилиту `toCSV` и с помощью модуля `node:fs` физически перезаписывает файл `data/orders.csv`.
7. **Ответ клиенту:** Обработчик оборачивает возвращённый репозиторием заказ в HTTP-ответ `Response` с форматом JSON и кодом статуса `200 OK`.

Каждый участник этой цепочки занимается строго своим делом!

В итоге, все приложение можно разделить на три больших слоя по ответственности:
- слой сервера: принимать сетевые вопросы, передавать слою приложения и возвращать ответ этого слоя в "сетевом формате";
  - main.js, server.js: чистые работники этого слоя;
  - route.js: промежуточный подслой, связывает уровень сервера и приложения;
- слой приложения: бизнес логика нашего приложения;
  - handler/: обработчик оркестратор, разбирает URL, валидирует данные, координирует вызовы;
  - entity/: validator.js хранит доменные правила, order.js — фабрику `createOrder`, которая собирает заказ для обработчика;
  - repo/: хранилище данных, сохраняет и возвращает переданные данные в файл csv;
- слой персистентности: слой сохранения в жесткий диск;
  - не знает ничего, принимает массив объектов и сохраняет его в компактном виде;

### Термины урока

**kind:** `text`

Пройдись по ключевым понятиям урока. Убедись, что ты можешь объяснить каждое из них своими словами.

**Термины:**
* **Архитектура** — способ организации частей программы и связей между ними для решения поставленной задачи.
* **HTTP-сервис** — программа, предоставляющая свои функции по сети: принимает HTTP-запросы, обрабатывает их и возвращает HTTP-ответы.
* **HTTP-сервер** — процесс, который слушает сетевой порт и принимает входящие HTTP-запросы (в проекте эту роль выполняет `Bun.serve`).
* **Спагетти-код** — плохо структурированный код со смешанными ответственностями, который тяжело читать, тестировать и изменять.
* **Слой** — пласт кода с единой зоной ответственности. Верхние слои используют нижние, обратное запрещено.
* **Инфраструктурный слой** — слой, который работает с конкретной технологией (например с файловой системой), не знает о других частях приложения.
* **Фабрика (Factory)** — функция сборки сущности: применяет валидаторы и либо возвращает валидный объект, либо бросает ошибку.
* **Репозиторий** — слой, который сохраняет и извлекает сущности (заказы), связывая предметную область с инфраструктурой хранения.
* **Зона ответственности (Separation of Concerns)** — принцип, по которому каждый модуль отвечает только за одну конкретную задачу.
* **Инвариант** — обязательное условие целостности данных, которое программа гарантирует соблюдать.
* **Однонаправленная зависимость** — иерархический поток импортов сверху вниз без циклических связей.
* **Поток вызова (Call Flow)** — путь передачи управления сквозь слои от момента получения запроса до отправки ответа.
