# Архитектура сервиса: слои и зоны ответственности — краткая выжимка

- В проекте строим локальный HTTP-сервис интернет-магазина для пяти операций с заказами: список, поиск, создание, обновление, удаление.
- Разделение на слои решает проблему сложности: в коде от 200 строк смешение работы с сетью, файлами и валидацией приводит к спагетти-коду и хрупкости.
- **Слой** — пласт кода с единой ответственностью. Зависимости направлены строго сверху вниз: `server → app/handler → app/entity → app/repo → infra → utils`.
- Архитектура не догма: она выстраивается под конкретную задачу. Важен баланс: слоёв должно быть ровно столько, сколько нужно для изоляции и тестирования.
- Структура проекта `m3-p2-http`:
  - `infra/` — техническая реализация персистентности (`file-storage.js`);
  - `app/entity/` — бизнес-модели (`order.js`, включая фабрику `createOrder`) и валидация (`validator.js`);
  - `app/repo/` — хранилище заказов (`order-repo.js`, CRUD);
  - `app/handler/` — тонкие обработчики, по файлу на роут (`list-orders.js`, `get-order.js`, `create-order.js`, `update-order.js`, `delete-order.js`);
  - `server/` — запуск (`server.js`), маршрутизация (`route.js`) и точка входа (`main.js`);
  - `data/` — физический файл `orders.csv`.
- Поток вызова при HTTP-запросе: сеть → маршрутизатор → обработчик (валидация: `validateId` / `createOrder`) → репозиторий (сохранение без валидации) → файл → ответ клиенту. Ошибки валидации перехватываются сервером и возвращаются в виде `400 Bad Request`.
- В следующем уроке приступаем к коду: создаём слой сущности — доменные валидаторы в `app/entity/validator.js` и фабрику `createOrder` в `app/entity/order.js`.
