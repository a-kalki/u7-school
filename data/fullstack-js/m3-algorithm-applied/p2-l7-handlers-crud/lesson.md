# Реализация обработчиков API: самостоятельная практика

**Краткое содержание:**
Самостоятельно реализуем оставшиеся четыре обработчика API: получение списка (`/list`), создание (`/create`), обновление (`/update`) и удаление (`/delete`). Опираемся на бизнес-требования, сценарии поведения системы и инженерные контракты функций. Каждый обработчик покрываем изолированным модульным тестом с моками репозитория по TDD и самостоятельно регистрируем в таблице маршрутизации `server/route.js`.

**Время:** ~30 мин

**Основные темы:**
- Самостоятельная разработка тонких обработчиков
- Реализация `list-orders.js` (чтение коллекции)
- Реализация `create-order.js` (создание, присвоение ID)
- Реализация `update-order.js` (обновление по ID)
- Реализация `delete-order.js` (удаление по ID)
- Регистрация всех маршрутов в `server/route.js`
- Полный прогон модульных тестов обработчиков
- Термины урока

**Термины:**
* **CRUD** — четыре базовые операции работы с данными: Create (создание), Read (чтение), Update (обновление), Delete (удаление).
* **Оркестрация запроса** — последовательное соединение валидации, вызовов репозитория и форматирования результата в единый сценарий обработки.
* **Детерминированный тест** — тест, результат которого зависит только от проверяемого кода и не меняется от внешних факторов или порядка запуска.

### Архитектурный паттерн: тонкие обработчики без магии

В предыдущем уроке мы подробно разобрали конвейер обработчика на примере `handleGetOrder`:
1. Принять входящий URL запроса.
2. Разобрать параметры через `getQueryParams`.
3. Провалидировать входные данные (`validateId`, `createOrder`).
4. Вызвать метод репозитория (`listOrders`, `addOrder`, `updateOrder`, `deleteOrder`).
5. Если данных нет — бросить исключение `NotFoundError`.
6. При успехе — вернуть результат в виде строки JSON (`JSON.stringify`).

Обработчик не должен содержать низкоуровневых операций с диском, ручных циклов поиска или генерации сетевых ответов `new Response(...)`. Он остаётся чистым дирижёром (оркестратором), соединяющим валидацию, доменные правила и хранилище.

### Самостоятельная реализация четырёх оставшихся ручек

В этом уроке ты выступаешь в роли полноценного разработчика сервиса. Опираясь на бизнес-требования и инженерные контракты:
1. Создавай файл теста в `app/handler/<имя-ручки>.test.js`.
2. Мокай методы репозитория с помощью `mock.module('../repo/order-repo.js', () => repoMock)`.
3. Пиши тестовые сценарии (успешный путь, ошибка валидации, отсутствие записи).
4. Создавай файл обработчика `app/handler/<имя-ручки>.js` и пиши код функции.
5. Запускай модульный тест через `bun test`.
6. Регистрируй маршрут в таблице `server/route.js`.

Когда все четыре обработчика будут готовы, полный тестовый набор `bun test app/handler/` должен подтвердить 100% работоспособность логики API.
