# Шаги урока: Реализация обработчиков API: самостоятельная практика

### Реализация обработчиков: самостоятельная практика

**kind:** `text`

В предыдущем уроке мы подробно разобрали полный цикл разработки обработчика на примере `handleGetOrder`: бизнес-ТЗ, модульный тест с моком репозитория, реализация, регистрация в таблице маршрутов `server/route.js` и интеграционный тест.

Теперь твоя очередь применить этот подход самостоятельно для оставшихся четырёх обработчиков API.

**Организация тестов:**
- **Модульные тесты** пиши для каждого обработчика в отдельном файле: `app/handler/<имя>.test.js`, используя моки репозитория.
- **Интеграционные тесты** дописывай новыми блоками `test(...)` в общий файл `server/server.integration.test.js`, созданный в прошлом уроке. В нём уже настроены тестовый сервер, подмена пути к файлу заказов и автоматическая уборка — тебе нужно лишь добавить `test(...)` с проверкой реального вызова через `fetch()` для каждого нового роута.

Каждое задание ниже сформулировано в виде бизнес-требований и инженерного контракта.

### ТЗ: Получение реестра всех заказов (`list-orders.js`)

**kind:** `text`

**Бизнес-задача:**
Фронтенд запрашивает список всех существующих заказов магазина для отображения в таблице заказов.

**Сценарии поведения системы:**
1. **В магазине есть заказы:** система запрашивает коллекцию в репозитории и возвращает массив всех сохранённых заказов в виде JSON-строки.
2. **Хранилище пусто:** если ни одного заказа ещё нет, система не падает с ошибкой, а возвращает валидную JSON-строку пустого массива (`"[]"`).

**Инженерный контракт: `handleListOrders(requestUrl)`**
- **Вход:** URL запроса (дополнительные параметры не требуются).
- **Выход:** строка JSON с массивом сохранённых заказов.
- **Критерии приёмки:**
  - Возвращает сериализованный JSON-массив.

**Задание:**
1. Реализация обработчика.
2. Регистрация в таблице роутинга.
3. Написание интеграционного теста.

### ТЗ: Создание нового заказа (`create-order.js`)

**kind:** `text`

**Бизнес-задача:**
Покупатель оформляет покупку. Фронтенд отправляет запрос с данными нового заказа: имя покупателя, сумма, статус оплаты, статус выполнения и опциональный отзыв.

**Сценарии поведения системы:**
1. **Успешное оформление:** при валидных данных заказ сохраняется в системе с присвоением уникального числового `id`. Система возвращает созданный объект в формате JSON.
2. **Ошибка в данных:** если обязательные поля отсутствуют или не соответствуют типам, запрос отклоняется ошибкой валидации.

**Инженерный контракт: `handleCreateOrder(requestUrl)`**
- **Вход:** URL запроса с query-параметрами черновика заказа.
- **Выход:** строка JSON с созданным объектом заказа.
- **Критерии приёмки:**
  - Создает и сохраняет заказ в БД.
  - Возвращает созданный заказ в JSON.
  - Проводит валидацию всех полей входных данных.

**Задание:**
1. Реализация обработчика.
2. Регистрация в таблице роутинга.
3. Написание интеграционного теста.

### ТЗ: Обновление заказа (`update-order.js`)

**kind:** `text`

**Бизнес-задача:**
Менеджер магазина вносит изменения в существующий заказ.

**Сценарии поведения системы:**
1. **Успешное обновление:** если заказ существует, система обновляет его данные и возвращает обновлённый объект в виде строки JSON.
2. **Заказ не найден:** если указан несуществующий номер заказа, система сообщает об этом ошибкой `NotFoundError`.
3. **Некорректные данные:** если передан невалидные поля, система отклоняет запрос ошибкой валидации `OrderValidationError`.

**Инженерный контракт: `handleUpdateOrder(requestUrl)`**
- **Вход:** URL запроса с обязательным параметром `id` и обновляемыми полями заказа.
- **Выход:** строка JSON с обновлённым объектом заказа.
- **Критерии приёмки:**
  - Обновляет поля заказа и сохраняет в БД.
  - Возвращает обновленный объект заказа в JSON.
  - Выполняет валидацию входных данных.
  - Отказывает в обновлении если такого заказа нет.

**Задание:**
1. Реализация обработчика.
2. Регистрация в таблице роутинга.
3. Написание интеграционного теста.

### ТЗ: Удаление заказа (`delete-order.js`)

**kind:** `text`

**Бизнес-задача:**
Менеджер магазина удаляет отменённый или ошибочный заказ из системы по его номеру.

**Сценарии поведения системы:**
1. **Успешное удаление:** если заказ с таким номером есть в базе, система удаляет его и возвращает подтверждение успеха.
2. **Заказ не найден:** если такого номера нет, система сообщает об ошибке `NotFoundError`.
3. **Некорректный номер:** если `id` невалиден, запрос отклоняется ошибкой `OrderValidationError`.

**Инженерный контракт: `handleDeleteOrder(requestUrl)`**
- **Вход:** URL запроса с query-параметром `id` удаляемого заказа.
- **Выход:** строка JSON с подтверждением удаления (`{"success":true}`).
- **Критерии приёмки:**
  - Удаляет и сохраняет в БД.
  - Возвращает ответ об успехе.
  - Выполняет валидацию входных данных.
  - Отказывает в удалении если такого заказа нет.

**Задание:**
1. Реализация обработчика.
2. Регистрация в таблице роутинга.
3. Написание интеграционного теста.

### Проверка всех обработчиков

**kind:** `text`

Убедись, что все тесты проходят:

1. **Модульные тесты обработчиков:**
   ```bash
   bun test app/handler/
   ```
2. **Интеграционные тесты всех пяти роутов:**
   ```bash
   bun test server/
   ```
3. **Выборочная ручная проверка:**
   Запусти сервис:
   ```bash
   bun run server/main.js
   ```
   Открой браузер или выполни `curl` для проверки нескольких роутов (например `http://localhost:3000/list`).

### Термины урока

**kind:** `text`

Пройдись по понятиям урока.

**Термины:**
* **CRUD** — четыре базовые операции работы с данными: Create, Read, Update, Delete.
* **Оркестрация запроса** — последовательное соединение валидации, вызовов репозитория и форматирования результата в единый сценарий обработки.
* **Детерминированный тест** — тест, результат которого зависит только от проверяемого кода и не меняется от внешних факторов или порядка запуска.
