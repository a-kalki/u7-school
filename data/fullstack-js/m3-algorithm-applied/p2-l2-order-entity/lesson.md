# Слой сущности: правила валидации и фабрика заказа

**Краткое содержание:**
Создаём сердце бизнес-логики приложения — слой `app/entity`. Определяем правила предметной области для заказа, пишем чистые функции-валидаторы в `validator.js` и фабрику `createOrder` в `order.js`. Разбираемся, как валидаторы приводят типы и проверяют правила, почему все поля кроме отзыва обязательны, как исключения валидации будут обрабатываться на сервере и почему репозиторий опирается на фабрику. Разрабатываем код по методологии TDD.

**Время:** ~25 мин

**Основные темы:**
- Слой `app/entity` — ядро бизнес-логики без внешних зависимостей
- Модель заказа: состав полей, обязательность и допустимые значения
- Архитектурная цепочка: от сырого запроса до валидного объекта
- Класс ошибки `OrderValidationError`
- Валидаторы полей: приведение типа, бизнес-правила и выброс исключений
- Фабрика `createOrder`: сборка гарантированно валидного заказа
- TDD: тестирование позитивных сценариев и путей отказа
- Критерии приёмки и проверка решения
- Термины урока

**Термины:**
* **Сущность (Entity)** — объект предметной области с уникальным идентификатором и жизненным циклом (в нашем сервисе — «Заказ»).
* **Доменное правило (Business Rule)** — требование предметной области к данным (номер — целое больше нуля, имя не пустое, сумма положительна).
* **Приведение типа (Type Coercion)** — преобразование входных сырых данных (например, строк из URL или CSV) к целевому типу JavaScript (`Number`, `Boolean`).
* **Валидатор** — чистая функция, которая проверяет значение поля, при необходимости приводит его тип и бросает исключение при нарушении правила.
* **Фабрика (Factory)** — функция сборки объекта: принимает сырые данные, пропускает каждое поле через валидаторы и возвращает готовый объект.
* **Оркестратор** — компонент, который координирует последовательность шагов (разбор запроса, валидация, вызов хранилища, упаковка ответа).
* **TDD (Test-Driven Development)** — разработка через тестирование: сначала пишем тест на ожидаемое поведение, затем минимальный код реализации.

### Слой сущности: ядро бизнес-логики

В прошлом уроке мы определили слои нашего HTTP-сервиса. Слой `app/entity` — самый независимый и изолированный слой программы:
- Он **ничего не знает о файловой системе** (`node:fs`, пути к файлам).
- Он **ничего не знает о сети и HTTP** (методы запросов, статус-коды, `Bun.serve`).
- Он сосредоточен исключительно на правилах интернет-магазина: какими свойствами обладает заказ и какие значения допустимы.

Если в будущем мы перейдём с CSV на базу данных или заменим сетевой сервер на консольный скрипт, слой сущностей не изменится ни на строчку.

### Архитектурная цепочка: как данные становятся заказом

Давай вспомним, как распределяются ответственности в сервисе:

1. **Сервер (`server`)**: принимает запрос из сети. В нём работает централизованный обработчик исключений: если в процессе обработки возникает ошибка валидации, сервер перехватывает её и возвращает клиенту аккуратный JSON с объектом ошибки `{ error: err.message }` и кодом `400 Bad Request`.
2. **Обработчик (`handler`)**: оркестратор запроса. Принимает URL, разбирает строку параметров через `getQueryParams` и валидирует входные данные:
   - для операций с конкретным заказом (`/get`, `/delete`, `/update`) валидирует `id` через `validateId`;
   - для создания или обновления заказа вызывает **фабрику `createOrder`**.
3. **Валидаторы (`validator.js`)**: чистые функции, каждая из которых отвечает за проверку и приведение типа одного поля. Если правило нарушено — валидатор **немедленно бросает исключение `OrderValidationError`**.
4. **Фабрика (`createOrder`)**: принимает сырой объект параметров из URL, прогоняет поля через валидаторы, отсекает лишние свойства и собирает чистый объект данных заказа для передачи в репозиторий.
5. **Репозиторий (`repo`)**: простое CRUD-хранилище данных. Получает готовые данные от обработчика, присваивает `id` новому заказу и сохраняет в файл. Репозиторий **не валидирует** данные — он сохраняет и выдаёт то, что ему передали.

В результате: если клиент прислал некорректные данные, фабрика или валидатор бросают исключение, оно всплывает на уровень сервера и клиент получает `400 Bad Request`. Если данные корректны — обработчик передаёт их в репозиторий и возвращает успешный ответ `200 OK`.

### Модель заказа

Заказ в нашей системе — это плоский JavaScript-объект со следующими полями:

- **`id` (Уникальный номер заказа):** целое число строго больше нуля. Обязательно.
- **`customer` (Имя покупателя):** непустая строка без лишних пробелов по краям. Обязательно.
- **`amount` (Сумма заказа в рублях):** конечное число строго больше нуля. Обязательно.
- **`isPaid` (Признак оплаты):** булево значение (`true` или `false`). Обязательно.
- **`status` (Состояние заказа):** одно из трёх значений: `'new'`, `'completed'`, `'canceled'`. Обязательно.
- **`review` (Отзыв клиента):** строка с отзывом покупателя. Единственное опциональное поле (может быть пустым или отсутствовать).

**Обрати внимание:** все поля заказа, кроме `review`, **строго обязательны**. Если клиент пытается создать заказ без статуса, без суммы или без отметки об оплате — это ошибка входных данных.

### Класс ошибки и список статусов: заготовка

Для обозначения ошибок предметной области мы используем специальный класс ошибки — `OrderValidationError`. Он наследуется от стандартного `Error`. Это позволяет серверу отличать ошибки неправильного ввода (по вине клиента) от непредвиденных сбоев программы.

Создай файл `app/entity/validator.js` со следующей базовой заготовкой:

```javascript
export class OrderValidationError extends Error {
  constructor(message) {
    super(message);
    this.name = 'OrderValidationError';
  }
}

export const ORDER_STATUSES = ['new', 'completed', 'canceled'];
```

Это единственная заготовка, которую мы выдаём готовым кодом. Все остальные функции ты спроектируешь и напишешь самостоятельно по контрактам и бизнес-требованиям.

### Доменные валидаторы: правила и контракты

В файле `app/entity/validator.js` тебе предстоит реализовать шесть функций валидации.

Каждый валидатор устроен по единому принципу:
- Принимает одно сырое значение (может быть строкой, числом, `undefined`, `null` и т.д.).
- Выполняет **приведение типа** к правильному виду.
- Проверяет **доменные правила**.
- Если проверка успешна — возвращает очищенное приведённое значение.
- Если проверка провалена или обязательное поле отсутствует — **бросает `OrderValidationError`** с понятным описанием проблемы.

#### 1. `validateId(raw)`
* **Ответственность:** проверка идентификатора заказа.
* **Бизнес-правило:** номер заказа обязан быть целым числом больше нуля.
* **Приведение типа:** сырое значение переводится в число через `Number(raw)`.
* **Краевые случаи:** строки `'42'` приводятся к числу `42`; дробные числа (`3.14`, `'3.14'`), отрицательные числа (`-1`), ноль (`0`), нечисловые строки (`'abc'`), а также `undefined` и `null` — приводят к ошибке.
* **Текст ошибки:** `'Некорректный ID заказа'`.

#### 2. `validateCustomer(raw)`
* **Ответственность:** проверка имени покупателя.
* **Бизнес-правило:** имя клиента должно быть непустой строкой.
* **Обработка:** строковое значение обрезается от концевых пробелов (`raw.trim()`).
* **Краевые случаи:** пустая строка `''`, строка только из пробелов `'   '`, нестроковые типы (`null`, `undefined`, числа) — приводят к ошибке.
* **Текст ошибки:** `'Укажите имя клиента'`.

#### 3. `validateAmount(raw)`
* **Ответственность:** проверка суммы заказа.
* **Бизнес-правило:** сумма должна быть конечным положительным числом (больше нуля). Допускаются дробные рубли/копейки (например, `99.90`).
* **Приведение типа:** преобразуется в число через `Number(raw)`.
* **Краевые случаи:** ноль (`0`), отрицательные суммы (`-500`), строки `'abc'`, `NaN`, `Infinity`, `undefined`, `null` — приводят к ошибке.
* **Текст ошибки:** `'Сумма должна быть положительным числом'`.

#### 4. `validateIsPaid(raw)`
* **Ответственность:** проверка статуса оплаты.
* **Бизнес-правило:** обязательное поле, принимающее строго булево значение.
* **Приведение типа:**
  - Значения `true` или строка `'true'` приводятся к логическому `true`.
  - Значения `false` или строка `'false'` приводятся к логическому `false`.
* **Краевые случаи:** пустая строка `''`, `undefined`, `null`, числа, любые другие строки (например, `'yes'`) — приводят к ошибке.
* **Текст ошибки:** `'Некорректное значение оплаты'`.

#### 5. `validateStatus(raw)`
* **Ответственность:** проверка состояния жизненного цикла заказа.
* **Бизнес-правило:** обязательное поле, значение обязано строго входить в список `ORDER_STATUSES` (`'new'`, `'completed'`, `'canceled'`).
* **Краевые случаи:** отсутствие значения (`undefined`, `null`), пустая строка `''`, любой другой статус (например, `'in_progress'`) — приводят к ошибке.
* **Текст ошибки:** `'Некорректный статус заказа'`.

#### 6. `validateReview(raw)`
* **Ответственность:** проверка отзыва о покупке.
* **Бизнес-правило:** поле **опциональное**. Клиент не обязан оставлять отзыв.
* **Обработка:**
  - Если передано `undefined`, `null` или пустая строка `''` — возвращается `undefined`.
  - Если передана непустая строка — возвращается строка (с убранными лишними пробелами по краям).
* **Краевые случаи:** если передано нестроковое значение (число, объект), которое не является `null`/`undefined` — приводит к ошибке.
* **Текст ошибки:** `'Отзыв должен быть строкой'`.

### Фабрика `createOrder`: файл `app/entity/order.js`

Создай файл `app/entity/order.js`. В нём размещается функция `createOrder(data)`.

Фабрика используется в слое обработчиков (`app/handler/`): вместо того чтобы в каждом обработчике вручную вызывать валидаторы по отдельности и фильтровать свойства, обработчик вызывает `createOrder(params)`.

Важный архитектурный принцип: **фабрика не навязывает полный состав заказа**. Она не гарантирует, что на выходе обязательно будут присутствовать все поля. Её роль — **нормализация, валидация и санитайзинг**: если во входящих данных было поле-значение, относящееся к заказу, фабрика гарантирует, что оно будет проверено валидатором и приведено к правильному типу. Если поля во входе не было — его не будет и в результате. Это делает фабрику универсальной: её можно использовать и при создании заказа (где ещё нет `id`), и при обновлении (где передаётся только часть изменяемых полей).

#### Контракт фабрики
* **Вход:** объект с сырыми данными заказа из URL (например, `{ customer: ' Анна ', amount: '4500', isPaid: 'true', status: 'new' }` или `{ id: '3', status: 'completed' }`).
* **Выход:** объект только с переданными полями заказа, прошедшими валидацию и приведение типов.
* **Исключения:** если хотя бы одно переданное поле нарушает правила валидатора, выбрасывается `OrderValidationError`.

#### Требования к реализации
1. Фабрика импортирует валидаторы из `./validator.js` и реэкспортирует класс ошибки `OrderValidationError`.
2. Для каждого переданного допустимого поля (`id`, `customer`, `amount`, `isPaid`, `status`, `review`) фабрика вызывает соответствующий валидатор и записывает отвалидированное значение в возвращаемый объект.
3. Если поле отсутствует во входных данных — в возвращаемом объекте этого свойства тоже нет.
4. Фабрика возвращает только допустимые поля заказа. Любые посторонние свойства (случайные query-параметры из адресной строки) отсекаются и не попадают в результат.
5. Исходный переданный объект `data` не мутируется.

### Методология TDD: разработка через тестирование

Пиши код по принципу TDD: **сначала тест на ожидаемое поведение, затем код функции**.

Создай два тестовых файла рядом с реализацией:
- `app/entity/validator.test.js` — тесты валидаторов.
- `app/entity/order.test.js` — тесты фабрики.

#### На что обратить внимание в тестах валидаторов (`validator.test.js`):
1. **Успешные сценарии:**
   - Числа и строковые числа: `validateId(1)` и `validateId('1')` возвращают число `1`.
   - Имена с пробелами: `validateCustomer('  Иван  ')` возвращает `'Иван'`.
   - Дробные суммы: `validateAmount('120.50')` возвращает `120.5`.
   - Булевы значения и строковые флаги: `validateIsPaid(true)` и `validateIsPaid('true')` возвращают `true`; аналогично для `false` и `'false'`.
   - Допустимые статусы: каждый из статусов `'new'`, `'completed'`, `'canceled'` возвращается без изменений.
   - Опциональность отзыва: `validateReview(undefined)` и `validateReview(null)` возвращают `undefined`; текстовый отзыв возвращает строку.
2. **Сценарии отказа (проверка выброса `OrderValidationError`):**
   - Используй метод Bun test: `expect(() => validateId('abc')).toThrow(OrderValidationError)`.
   - Проверяй как невалидные типы данных, так и отсутствие обязательных полей (`undefined`, пустые строки).

#### На что обратить внимание в тестах фабрики (`order.test.js`):
1. **Нормализация и приведение типов:** передай объект со строковыми данными, убедись, что на выходе получается объект с типами `number`, `string`, `boolean`.
2. **Частичный набор полей:** если передать только `{ id: '3', status: 'completed' }`, фабрика возвращает `{ id: 3, status: 'completed' }` без посторонних или непереданных полей.
3. **Фильтрация лишних полей:** если передать `{ customer: 'Анна', amount: '3000', extraField: 'hacker' }`, в возвращаемом объекте свойства `extraField` быть не должно.
4. **Отказ при невалидном значении:** убедись, что передача любого некорректного поля (например, отрицательной суммы `{ amount: '-500' }`) приводит к выбросу `OrderValidationError`.
