# Финал проекта: архитектура CRUD, PR и код-ревью

**Краткое содержание:**
Завершаем проект «HTTP-сервис». Подводим архитектурные итоги: разбираемся, как построенные нами пять роутов складываются в фундаментальную отраслевую концепцию **CRUD**. Проводим полный прогон всех автоматических тестов проекта, проверяем чистоту кодовой базы и статус git. Пушим рабочую ветку, оформляем Pull Request по шаблону, проходим цикл командного код-ревью и выполняем мерж в основную ветку.

**Время:** ~25 мин

**Основные темы:**
- Архитектурные итоги: что мы построили по слоям
- Концепция CRUD: Create, Read, Update, Delete
- Почему CRUD лежит в основе 90% веб-сервисов и REST API
- Полный прогон всех тестов репозитория (`bun test`)
- Проверка чистоты кодовой базы и состояния git
- Оформление Pull Request и описание архитектурных решений
- Командное код-ревью, два апрува и мерж
- Ретроспектива проекта
- Термины урока

**Термины:**
* **CRUD** — акроним четырёх базовых операций управления любыми хранимыми данными: Create (создание), Read (чтение), Update (обновление), Delete (удаление).
* **REST API** — архитектурный стиль взаимодействия систем, в котором операции над ресурсами строятся вокруг концепции CRUD.
* **Pull Request (PR)** — запрос на слияние функциональной ветки в основную ветку репозитория с возможностью рецензирования кода коллегами.
* **Code Review (Код-ревью)** — процесс совместной проверки качества, надёжности и соответствия стандартам написанного кода.
* **Ретроспектива (Ретро)** — инженерная практика анализа проделанной работы: что получилось отлично, с чем возникли трудности и как улучшить процесс в следующем проекте.

### Архитектурные итоги: что мы построили

В начале проекта мы поставили цель: не просто написать скрипт с сервером, а создать приложение с чистой **слоистой архитектурой**.

Взгляни на созданную структуру проекта:
```text
m3-p2-http/
  infra/file-storage.js          # Низкий уровень: персистентность (node:fs + toCSV/fromCSV)
  app/
    entity/order.js              # Бизнес-модель: структура сущности + фабрика createOrder
    entity/validator.js          # Доменные правила: проверка параметров
    repo/order-repo.js           # Хранилище: Read-Modify-Write, автоинкремент ID
    handler/list-orders.js       # Тонкие обработчики: по файлу на роут
    handler/get-order.js
    handler/create-order.js
    handler/update-order.js
    handler/delete-order.js
  server/
    server.js                    # Транспорт: нативный Bun.serve
    route.js                     # Маршрутизация: сопоставление путей с обработчиками
    main.js                      # Точка входа: сборка и запуск приложения
  data/orders.csv                # Физическая база данных
```

Каждый файл выполняет ровно одну роль. Зависимости направлены строго сверху вниз. Ни один слой не протекает в соседний.

### Ты построил полноценный CRUD-сервис

Пять роутов нашего сервера образуют классический каркас **CRUD**:

- **C — Create (создание новой записи):**
  - Наш маршрут в API: `/create?...`
  - Метод в репозитории: `addOrder`
- **R — Read (чтение одной записи):**
  - Наш маршрут в API: `/get?id=...`
  - Метод в репозитории: `getOrder`
- **R — Read (чтение всей коллекции):**
  - Наш маршрут в API: `/list`
  - Метод в репозитории: `listOrders`
- **U — Update (модификация существующей записи):**
  - Наш маршрут в API: `/update?id=...`
  - Метод в репозитории: `updateOrder`
- **D — Delete (удаление записи):**
  - Наш маршрут в API: `/delete?id=...`
  - Метод в репозитории: `deleteOrder`

Обрати внимание: чтение (**Read**) почти всегда разделяют на два действия:
1. Выдать список всех элементов (коллекция).
2. Выдать конкретный элемент по его уникальному номеру `id`.

**CRUD — это фундамент веб-разработки.** Практически любой современный бэкенд, от сервиса заметок до огромного онлайн-банка, по своей сути представляет собой вариацию CRUD над своими сущностями.

### Полный прогон автоматических тестов

Перед тем как отправлять код на проверку коллегам, убедись, что все тесты в репозитории проходят без ошибок:

```bash
bun test
```

В консоли должны успешно выполниться:
- Все тесты первого проекта («Бизнес-утилиты»);
- Тесты фабрики (`order.test.js`) и валидатора (`validator.test.js`);
- Тесты инфраструктуры (`file-storage.test.js`);
- Тесты репозитория через моки (`order-repo.test.js`);
- Тесты обработчиков через моки — по файлу на каждый (`list-orders.test.js`, `get-order.test.js`, `create-order.test.js`, `update-order.test.js`, `delete-order.test.js`).

Ни один тест не должен падать или завершаться по таймауту.

### Оформление PR и код-ревью

1. Проверь статус рабочей ветки: `git status` должен быть чистым.
2. Отправь ветку в удалённый репозиторий: `git push -u origin feat/http-service`.
3. Создай Pull Request в ветку `main` с понятным описанием:
   - какие слои были выделены в проекте;
   - как обработчики через валидаторы и фабрику `createOrder` валидируют данные перед передачей в хранилище;
   - как изолированы тесты репозитория и обработчиков с помощью моков;
   - как запускается сервис и какими способами он протестирован.
4. Отправь ссылку в общий чат курса и получи два одобрения (Approve) от коллег.
5. Выполни мерж ветки в `main`.
