# Проект: Игра реального времени на тиках (PR)

**Краткое содержание:**
Выходим на пик мастерства в разработке консольных аркад. В третьем практическом проекте мир больше не ждёт нажатия клавиш: время непрерывно течёт, объекты движутся сами по таймеру, а реакция игрока решает всё. Мы подробно изучаем механику игровых тиков (tick rate), асинхронное состояние, буферизацию ввода для защиты от разворота на 180°, работу со структурами очередей координат и генерацию случайных объектов без пересечений. Студент самостоятельно выбирает одну из динамических игр («Змейка» или «Космический уворачивальщик»), **с нуля собирает точку входа `run.js`**, реализует логику с тестами и защищает свой Pull Request перед сокурсниками.

**Время:** ~45 мин

**Основные темы:**
- Разница между пошаговым миром и миром реального времени: как работают тики
- Параметр `tickRateMs` в игровом ядре `engine.js` и баланс частоты кадров
- Новая степень свободы: самостоятельная сборка точки входа `run.js`
- Каталог игр реального времени на выбор: «Змейка» и «Космический уворачивальщик»
- Архитектура «Змейки»: очередь координат тела `FIFO`, движение головы и рост при питании
- Проблема разворота на 180°: буферизация намерения движения
- Алгоритм генерации еды: как случайным образом выбрать незанятую клетку без зависаний
- Архитектура «Уворачивальщика»: падающие волны препятствий, удаление вышедших за экран объектов
- Написание тестов для логики на тиках через подачу событий `{ type: 'TICK' }`
- Сдача Pull Request и критерии готовности к peer-review сокурсников

**Термины:**
* **Дискретный такт синхронизации (Heartbeat / Tick)** — квант времени в асинхронной системе, периодический сигнал таймера, инициирующий очередной шаг вычисления состояния.
* **Делитель тактов (Tick Divider)** — архитектурный паттерн разделения непрерывного инфраструктурного таймера (системный тик ядра) и контролируемой логической скорости работы домена (доменный шаг через счётчик `tickCounter`).
* **Буферизация ввода (Input Buffering)** — сохранение входящей команды пользователя в промежуточное поле состояния для устранения состояния гонки (Race Condition) и предотвращения недопустимых резких переходов между тиками.
* **Точка сборки слоёв (Composition Root)** — самостоятельное конструирование файла запуска `run.js`, где разработчик связывает независимые интерфейсные адаптеры, параметры времени и доменную логику без монолитного фреймворка.
* **Определение пересечений (Collision Detection)** — алгоритмическая проверка совпадения координат сущностей в пространстве для фиксации доменного события.
* **Детерминированное тестирование времени** — проверка асинхронных сценариев и динамики времени синхронными юнит-тестами через прямую подачу события `{ type: 'TICK' }` без таймеров `setTimeout` и моков.
* **Холостой такт (Idle Tick)** — такт таймера, в котором состояние системы не изменилось, позволяющий оптимизировать ресурсы и исключить избыточную перерисовку интерфейса.

### Время пошло: Как работают тики в терминале

В предыдущих уроках вызов `update(state, action)` происходил только тогда, когда палец игрока касался клавиши. Если игрок отходил от компьютера на час — игра замирала на месте.

В играх реального времени мир живёт собственной жизнью:
- Змейка ползёт вперёд даже если вы не трогаете клавиатуру.
- Метеориты падают сверху вниз с постоянной скоростью.

Для этого в ядре `engine.js` предусмотрен параметр `tickRateMs`. Если при запуске движка указать этот параметр, движок запускает периодический таймер.

Теперь в игру поступают два независимых потока событий:
1. **Нажатие клавиши игроком:** адаптер ввода мгновенно генерирует экшен управления (например, `{ type: 'MOVE', direction: 'UP' }`) → вызывается `update(state, event)` → экран перерисовывается.
2. **Системный таймер движка:** каждые N миллисекунд (например, 140 мс) движок генерирует экшен тика `{ type: 'TICK' }` → вызывается `update(state, event)` → мир делает автономный шаг вперёд (змейка ползёт, метеорит падает) → экран перерисовывается.

Обратите внимание на ключевой вывод: **функция `update` остаётся совершенно синхронной и детерминированной!** Ей всё равно, откуда пришло событие: от нажатия клавиши пользователем или от таймера ядра с типом `'TICK'`. Это делает тестирование игр реального времени простым и предсказуемым.

### Архитектура точки входа: собираем `run.js` как конструктор

В Уроках 1, 2 и 3 файл запуска `run.js` выдавался в готовом виде. Вы лишь запускали его и наблюдали за тем, как оживает игра.

В Уроке 4 вы делаете качественный шаг вперёд: **создаёте `run.js` самостоятельно с нуля**.

Точка входа `run.js` в нашей архитектуре не содержит игровой логики и не рисует символы в консоли. Её роль — **компоновщик (сборщик слоёв)**. Она собирает воедино три независимых слоя:
1. **Слой 1 (Ядро):** функция `startEngine` из `arcade/engine.js`. Она умеет включать терминал в `raw mode`, крутить игровой цикл и запускать тики по таймеру `tickRateMs`. Ядро абсолютно абстрактно: оно ничего не знает ни о змейках, ни о метеоритах, ни о правилах игры.
2. **Слой 2 (Интерфейс: Адаптеры ввода и вывода):** модули из папки `arcade/tui/`. Они переводят низкоуровневые байты терминала в понятные игре действия (вход) и превращают структуру данных кадра в красивый текст на экране (выход).
3. **Слой 3 (Логика игры):** ваши чистые функции `createState`, `update`, `getView` из папки `arcade/games/<игра>/`.

Ядро `startEngine` работает по строгому абстрактному контракту. Ему не важно, какая именно игра запущена — ему лишь нужны:
- источник начального состояния (`createState`);
- функция перехода состояний (`update`);
- преобразователь состояния в модель кадра (`getView`);
- рендерер, умеющий нарисовать эту модель (`render`);
- адаптер, умеющий превратить нажатие клавиши в событие (`adapter`);
- частота тиков таймера в миллисекундах (`tickRateMs`, если игра реального времени).

### Архитектурный спор: как назвать Слой 2? (`io`, `adapters` или `tui`)

Когда разработчики проектируют структуру проекта, часто возникает вопрос: **как назвать папку для этого промежуточного слоя?**

Все три популярных варианта отражают суть, но каждый из них направляет фокус внимания на свой аспект системы:

1. **`io/` (Input / Output — Ввод / Вывод)**
   - **Фокус внимания:** **Физический мир и железо.**
   - Так мыслят системные инженеры: на вход компьютера приходят сигналы с клавиатуры (`Input`), на экран отправляются символы (`Output`).
   - Имя подчеркивает работу с потоками ввода-вывода, но для новичка может путаться с файловым или сетевым I/O.

2. **`adapters/` (Адаптеры)**
   - **Фокус внимания:** **Архитектура слоёв и независимость логики (Clean Architecture / Ports & Adapters).**
   - **Концептуально это наиболее предпочтительный и глубокий вариант.** Паттерн «Адаптер» означает, что чистая логика игры (Слой 3) изолирована от внешнего мира. Если завтра мы захотим перенести ту же самую «Змейку» или «2048» в веб-браузер (`web-ui`), в мобильное приложение или Telegram-бота, **мы не изменим ни одной строчки правил игры**! Мы просто заменим терминальный адаптер на браузерный. В такой архитектуре папка `adapters/` масштабируется естественно: внутри появляются `adapters/tui/` и `adapters/web/`.

3. **`tui/` (Terminal User Interface — Терминальный интерфейс)**
   - **Фокус внимания:** **Пользовательский интерфейс и конкретная среда взаимодействия.**
   - «UI» — это всё, через что пользователь общается с программой (клавиши управления + картинка на экране). Поскольку наш текущий проект — это именно консольная аркада, мы выбрали самое простое, наглядное и практичное имя: **`tui/`**.

### Структура Слоя 2: почему модули tui/ объединены по смыслу

Хотя Слой 2 решает две разные задачи — **ввод** (клавиатура → Action) и **вывод** (View → экран), мы намеренно не дробим его на подпапки `tui/input/` и `tui/output/`.

Здесь работает фундаментальный инженерный принцип **высокой связности (High Cohesion)**: функции, работающие с одним типом интерфейса, должны жить рядом:
- в `tui/grid.js` адаптеры направлений и рендереры сеток оперируют одной 2D-координатной системой;
- в `tui/turtle.js` адаптер команд робота тесно связан с приборной панелью телеметрии;
- в `tui/hangman.js` буквенный адаптер ввода и экран отгадывания слов решают общую задачу викторины.

Реальная структура проекта выглядит компактно и понятно:

```text
arcade/
├── engine.js                   # Слой 1: универсальное ядро терминала
├── tui/                        # Слой 2: интерфейсный слой (ввод и вывод)
│   ├── grid.js                 # сеточный интерфейс (адаптеры направлений + рендереры сеток)
│   ├── turtle.js               # интерфейс Черепашки (команды робота + телеметрия)
│   └── hangman.js              # интерфейс Виселицы (буквенный ввод + ASCII-арт)
└── games/                      # Слой 3: чистая игровая логика
```

Благодаря этому точка входа `run.js` остаётся максимально лаконичной: всё необходимое для интерфейса вашей игры импортируется из одного модуля:
```javascript
import { createDirectionAdapter, renderGrid } from '../../tui/grid.js';
```

Давайте подробно изучим все доступные реализации, чтобы вы понимали, что именно подключить в свой `run.js`.

### Каталог инструментов Слоя 2: Рендереры и Адаптеры

Главный принцип архитектуры: **у одного абстрактного контракта может быть несколько разных реализаций** — от универсальных до специализированных (принцип расширения и специализации поведения).

---

#### Рендереры экрана (адаптеры вывода)

Контракт любого рендерера:
`render: (view, state) => string | string[]`
Рендерер получает объект `view` (результат вызова `getView(state)`) и возвращает массив текстовых строк для вывода в терминал.

В проекте есть четыре реализации этого контракта:

##### 1. Базовый рендерер двумерной сетки — `renderGrid` (`arcade/tui/grid.js`)
* **Что делает:** Самый универсальный рендерер аркады. Предназначен для любых игр, поле которых можно представить как прямоугольную символьную матрицу.
* **Что ожидает во `view`:**
  - `title` (строка) — заголовок игры;
  - `grid` (двумерный массив символов `[['.', 'A'], ...]`) — поле игры;
  - `score` (число | null) — текущий счёт;
  - `status` (`'PLAYING'` | `'WON'` | `'LOST'` | `'GAME_OVER'`) — текущий статус;
  - `extraInfo` (массив строк) — дополнительные строчки подсказок или характеристик.
* **Принцип работы:** Рисует аккуратную шапку с рамкой, отображает очки, обрамляет игровое поле горизонтальными границами `+---+` и вертикальными перегородками `|...|`. В зависимости от `status` автоматически выводит праздничное поздравление о победе, сообщение о конце игры или строку с подсказкой управления.
* **Где применяется:** «Змейка», «Космический уворачивальщик», «Сокобан», «Сапёр», «Крестики-нолики».

##### 2. Специализированный матричный рендерер — `renderNumberGrid` (`arcade/tui/grid.js`)
* **Что делает:** Специализация идеи сетки под многозначные числа (игра «2048»).
* **Что дополняет к базовой сетке:** В отличие от `renderGrid`, где каждая клетка — ровно один символ, здесь в ячейке может находиться число любой длины (`2`, `64`, `1024`, `2048`). `renderNumberGrid` вводит фиксированную ширину ячейки `cellWidth` (по умолчанию 5 символов), выравнивает каждое число через `.padStart()`, центрирует пустые ячейки и строит полноценную табличную сетку с внутренними ячеечными перегородками `+-----+-----+`.
* **Что ожидает во `view`:** `matrix` (двумерный массив чисел), `score`, `title`, `status`.
* **Где применяется:** Игра «2048».

##### 3. Доменный рендерер исполнителя — `renderTurtle` (`arcade/tui/turtle.js`)
* **Что делает:** Специализированный рендерер для учебного робота-черепашки.
* **Что дополняет к базовой сетке:** Берёт концепцию сетки со следом движения, но дополняет её расширенной «приборной панелью» телеметрии: отображает точные координаты исполнителя `X/Y`, текстовое направление по сторонам света («Север (вверх)», «Восток (вправо)»), состояние инструмента (`[ ОПУЩЕНО (рисует .) ]` / `[ ПОДНЯТО ]`), суммарное число пройденных шагов и памятку команд управления пером.
* **Где применяется:** «Черепашка на сетке».

##### 4. Альтернативный рендерер викторины — `renderHangman` (`arcade/tui/hangman.js`)
* **Что делает:** Полностью альтернативная реализация рендерера для словесной игры без координатной сетки.
* **Принцип работы:** Вместо двумерного поля отображает многострочную псевдографику ASCII-арт виселицы (массив из 7 стадий в зависимости от `errorsCount`), замаскированное слово с отгаданными буквами (`С _ О В О`), перечень неверно названных букв, индикатор текущего языка (`RU / EN`) и финальные экраны победы или поражения.
* **Где применяется:** «Виселица: Термины курса».

#### Адаптеры ввода (преобразование клавиш в события)

Контракт любого адаптера ввода:
`adapter: (rawStr, chunk) => Event | null`
Адаптер принимает сырую строку или байты, пришедшие из потока ввода терминала. Если клавиша имеет смысл для игры — адаптер возвращает готовый объект действия (`Action`), например `{ type: 'MOVE', direction: 'UP' }`. Если клавиша не относится к игре или является системной — адаптер возвращает `null`, передавая право обработки ядру `engine.js` (благодаря этому ядро само обрабатывает `q` для выхода или `r` для рестарта).

В проекте есть четыре реализации адаптеров:

##### 1. Универсальная настраиваемая фабрика направлений — `createDirectionAdapter(options)` (`arcade/tui/grid.js`)
* **Что делает:** Базовый универсальный адаптер для игр с 4 направлениями движения.
* **Принцип работы:** Перехватывает управляющие клавиши в трёх форматах:
  - ANSI-последовательности стрелок клавиатуры (`\x1b[A`, `\x1b[B`, `\x1b[C`, `\x1b[D`);
  - Латинские клавиши `W`, `A`, `S`, `D` (в верхнем и нижнем регистрах);
  - Русскую раскладку `Ц`, `Ф`, `Ы`, `В` (чтобы игра не ломалась, если игрок забыл переключить язык).
* **Гибкость через конфигурацию:** Принимает параметр `{ eventType: '...' }` (по умолчанию `'MOVE'`). Это позволяет адаптировать адаптер под контракт конкретной игры. Например:
  - `createDirectionAdapter()` вернёт событие `{ type: 'MOVE', direction: 'UP' }`;
  - `createDirectionAdapter({ eventType: 'CHANGE_DIRECTION' })` вернёт событие `{ type: 'CHANGE_DIRECTION', direction: 'UP' }`.
* **Что оставляет системному ядру:** Клавиши `Ctrl+C`, `Esc`, `r/R/к/К` (рестарт) и `q/Q/й/Й` (выход) возвращают `null` и отрабатывают в движке штатно.
* **Где применяется:** «Змейка», «Космический уворачивальщик», «Сокобан», «2048».

##### 2. Расширенный адаптер с курсором и действиями — `cursorActionAdapter` (`arcade/tui/grid.js`)
* **Что делает:** Специализация навигации для игр, где на сетке есть активный курсор и клавиши взаимодействия (открытие, флаг, выбор клетки).
* **Что дополняет к базовой навигации:**
  - Стрелки и WASD преобразуются не просто в абстрактное направление, а в относительное смещение курсора: `{ type: 'MOVE_CURSOR', dx: 0, dy: -1 }`;
  - Пробел и Enter преобразуются в событие подтверждения/открытия: `{ type: 'ACTION_OPEN' }`;
  - Клавиши `F` / `А` (рус.) преобразуются в событие маркировки: `{ type: 'ACTION_FLAG' }`.
* **Где применяется:** «Сапёр», «Крестики-нолики».

##### 3. Доменный адаптер команд робота — `inputAdapter` (`arcade/tui/turtle.js`)
* **Что делает:** Специализированный адаптер команд для исполнителя.
* **Принцип работы:** Переводит стрелки и WASD не в абсолютные направления сетки, а в относительные действия робота:
  - стрелка вверх / W → `{ type: 'FORWARD' }` (шаг вперёд);
  - стрелка вниз / S → `{ type: 'BACKWARD' }` (шаг назад);
  - стрелка влево / A → `{ type: 'TURN_LEFT' }` (поворот на месте налево);
  - стрелка вправо / D → `{ type: 'TURN_RIGHT' }` (поворот на месте направо);
  - пробел → `{ type: 'TOGGLE_PEN' }` (поднять/опустить перо);
  - клавиша `C` → `{ type: 'CLEAR_TRAIL' }` (стереть след).
* **Где применяется:** «Черепашка на сетке».

##### 4. Алфавитный адаптер текстового ввода — `inputAdapter` (`arcade/tui/hangman.js`)
* **Что делает:** Адаптер для посимвольного угадывания слов.
* **Принцип работы:** Проверяет ввод через регулярное выражение букв латиницы и кириллицы `/^[a-zA-Zа-яА-ЯёЁ]$/` и формирует событие угадывания `{ type: 'GUESS', char: rawStr.toUpperCase() }`. Перехватывает `Tab` для смены языка (`{ type: 'TOGGLE_LANG' }`), пробел/Enter для подтверждения и комбинацию `Ctrl+R` для рестарта.
* **Где применяется:** «Виселица».

### Архитектурный вывод: как устроена сборка в `run.js`

Посмотрите, как красиво складывается система:
- **Один и тот же движок `startEngine`** может запустить совершенно любую игру: текстовую викторину, пошаговую головоломку на сетке, робота-исполнителя или скоростную динамическую аркаду реального времени.
- **Один и тот же рендерер сетки `renderGrid`** может визуализировать логику пяти разных игр, потому что все они возвращают совместимый объект представления `view` с матрицей `grid`.
- **Один и тот же адаптер ввода `createDirectionAdapter`** может управлять движением ящиков в «Сокобане», сдвигом плашек в «2048» или курсом ракеты в «Уворачивальщике».

Когда вы создаёте `arcade/games/<игра>/run.js`, ваша задача как разработчика:
1. Выбрать из каталога рендерер, подходящий структуре данных вашей игры.
2. Выбрать адаптер ввода, который отправляет именно те события, которые ожидает ваша функция `update(state, event)`. При необходимости настроить `eventType`.
3. Подключить свои чистые функции `createState`, `update`, `getView`.
4. Для игр реального времени задать параметр `tickRateMs`, определяющий скорость игрового ритма.
5. Вызвать `startEngine` с собранной конфигурацией.

Никакой магии — чистая композиция независимых модулей!

#### Вариант А: Классическая «Змейка» (Snake)
* **Эмодзи:** 🐍
* **Сложность:** Выше средней
* **Игровое поле:** Символьная сетка 15×15 или 20×15.
* **Суть правил:** Змейка начинает с длины в 3 сегмента и непрерывно ползёт в выбранную сторону. Игрок меняет направление стрелками или WASD. На поле случайным образом появляется еда `*`. При поедании еды длина змейки увеличивается на 1, начисляются очки, а новая еда возникает на свободной клетке. Столкновение со стеной или собственным хвостом приводит к поражению.

##### Ключевые алгоритмические задачи «Змейки»:

1. **Хранение тела (Очередь точек):**
   Тело змейки — это массив объектов координат `[{ x, y }, { x, y }, ...]`, где нулевой элемент `body[0]` — голова.
   - На каждом тике вычисляются координаты новой головы: `newHead = { x: head.x + dx, y: head.y + dy }`.
   - Новая голова добавляется в начало: `newBody = [newHead, ...body]`.
   - Если еда не была съедена — кончик хвоста отрезается: `newBody.pop()`.
   - Если еда съедена — хвост **не** отрезается (змейка выросла!), а еда создаётся заново.

2. **Защита от разворота на 180° (Буферизация ввода):**
   Если змейка ползёт вправо (`dir = 'RIGHT'`), а игрок быстро нажимает клавишу «Влево» (`dir = 'LEFT'`), змейка врезалась бы в собственный второй сегмент и погибла.
   - Поэтому событие клавиатуры не должно сразу менять текущее направление движения тела; оно лишь обновляет `nextDir` (намерение).
   - При попытке сменить вектор на противоположный (`dir === 'RIGHT'` и нажато `'LEFT'`) команда игнорируется.
   - Применение `dir = nextDir` происходит **только в момент тика `'TICK'`**, когда совершается реальный шаг.

3. **Генерация еды без пересечений:**
   Нельзя просто вызывать `Math.random()` наугад в бесконечном цикле `while`. Когда змейка займёт 80% поля, такой цикл начнёт «буксовать».
   - Правильный алгоритмический подход: сформировать список всех пустых клеток поля, не входящих в `body`, и выбрать случайный элемент из этого списка.

#### Вариант Б: «Космический уворачивальщик» (Space Dodger)
* **Эмодзи:** 🚀
* **Сложность:** Средняя
* **Игровое поле:** Вертикальная полоса 12×15.
* **Суть правил:** Корабль игрока `A` находится в самом нижнем ряду поля и может перемещаться только влево и вправо. Сверху непрерывно появляются метеориты `*` и падают вниз. Игрок должен уворачиваться от падающих угроз. Каждое препятствие, успешно упавшее за нижний край экрана, приносит +10 очков выживания. При столкновении с метеоритом — конец игры.

##### Ключевые алгоритмические задачи «Уворачивальщика»:

1. **Перемещение препятствий на тике:**
   Препятствия хранятся в виде массива объектов: `hazards: [{ x: 3, y: 0 }, { x: 7, y: 2 }]`.
   - На каждом тике координата Y каждого метеорита увеличивается на 1: `hazard.y + 1`.
   - Метеориты, у которых `y >= height`, фильтруются: `hazards.filter(h => h.y < height)`.
   - Число отфильтрованных метеоритов умножается на 10 и добавляется к очкам игрока (`score`).

2. **Генерация новых волн:**
   С заданной вероятностью (например, каждые 2-3 тика) в нулевой строке `y = 0` создаётся новый метеорит со случайной координатой `x` в диапазоне `[0, width - 1]`.

3. **Проверка коллизии:**
   После сдвига проверяется, совпали ли координаты корабля `{ x: playerX, y: height - 1 }` с координатами хотя бы одного метеорита:
   `hazards.some(h => h.x === playerX && h.y === height - 1)`.

### Тестирование игр реального времени

Главная прелесть детерминированной функции `update(state, event)` в том, что для её тестирования **не нужно ждать реального времени**!

Вам не нужны задержки `setTimeout`: вы просто вызываете `update` с событием тика столько раз, сколько шагов хотите смоделировать:

```javascript
// games/snake/snake.test.js
import { describe, expect, it } from 'bun:test';
import { createState, update } from './snake.js';

describe('Змейка на тиках', () => {
  it('двигает голову вперед по направлению на каждом тике', () => {
    let state = createState({ width: 10, height: 10 });
    const initialHeadX = state.body[0].x;
    state.dir = 'RIGHT';

    // Эмулируем один шаг времени
    state = update(state, { type: 'TICK' });

    expect(state.body[0].x).toBe(initialHeadX + 1);
  });

  it('запрещает самоубийственный разворот на 180 градусов', () => {
    let state = createState();
    state.dir = 'RIGHT';

    // Игрок жмет Влево
    state = update(state, { type: 'MOVE', direction: 'LEFT' });
    // Тик времени
    state = update(state, { type: 'TICK' });

    // Направление не должно было смениться на противоположное
    expect(state.dir).toBe('RIGHT');
  });

  it('фиксирует поражение при ударе в стену', () => {
    let state = createState({ width: 5, height: 5 });
    state.body = [{ x: 4, y: 2 }];
    state.dir = 'RIGHT';

    state = update(state, { type: 'TICK' });

    expect(state.status).toBe('lost');
  });
});
```

### Практическое задание и сдача Pull Request

1. Выберите игру («Змейка» или «Уворачивальщик»).
2. Запросите у ментора в чате пакет документации контракта:
   > «Привет! В модуле «Аркада» я выбираю **<Змейку / Уворачивальщика>**. Выдай спецификацию контракта данных.»
3. **Открытие рабочей ветки по Git-flow:**
   - Переключитесь на актуальный `main` и создайте функциональную ветку под выбранную игру:
     ```bash
     git checkout main
     git pull origin main
     git checkout -b feature/<game-name>
     ```
     (например, `feature/snake` или `feature/dodger`).
   - **Важное правило:** разработка раннера `run.js`, логики игры и юнит-тестов ведётся строго в этой ветке! Так любой сокурсник сможет переключиться на вашу ветку и сразу протестировать игру.
4. **Создайте файл точки входа `arcade/games/<game>/run.js`** с настройкой `tickRateMs`.
5. Реализуйте файл игровой логики `arcade/games/<game>/<game>.js` (`createState`, `update`, `getView`).
6. Напишите полноценный набор тестов `arcade/games/<game>/<game>.test.js` с проверкой тиков, коллизий и счёта.
7. Запустите тесты:
   ```bash
   bun test arcade/games/<game>/
   ```
8. Сыграйте в игру в терминале, оцените плавность движения и баланс скорости:
   ```bash
   bun arcade/games/<game>/run.js
   ```
9. **Сдача Pull Request на peer-review сокурсникам:**
   - Проверьте изменённые файлы:
     ```bash
     git status
     ```
   - Закоммитьте изменения в рабочей ветке:
     ```bash
     git add arcade/games/<game>/
     git commit -m "feat(arcade): реализовать игру реального времени <Название> и раннер"
     ```
   - Отправьте ветку на GitHub:
     ```bash
     git push -u origin feature/<game-name>
     ```
   - Откройте **Pull Request** в ветку `main` на GitHub.
   - Отправьте сообщение со ссылкой сокурсникам в общий учебный чат:
     ```text
     🔍 PR на ревью: [Динамическая игра: <Название игры> (логика, раннер и тесты)]
     📎 Ссылка: https://github.com/<твой-username>/fullstack-js/pull/<номер>
     📋 Жду ваших комментариев и проверки в терминале!
     ```

#### Чек-лист готовности к сдаче на peer-review:
- [ ] Точка входа `run.js` создана самостоятельно и корректно передаёт `tickRateMs`.
