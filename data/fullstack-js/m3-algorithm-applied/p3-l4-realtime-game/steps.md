# Шаги урока: Проект: Игра реального времени на тиках (PR)

---

### Время вступает в игру: Переход к реальному времени

**kind:** `text`

В пошаговых играх состояние изменялось только тогда, когда игрок нажимал клавишу. Мир терпеливо ждал.

В играх **реального времени (Real-Time)** всё иначе: мир движется непрерывно, независимо от того, нажимает игрок кнопки или замер в раздумьях. Астероиды падают, змейка ползёт к стене, враги наступают.

Главная цель этого урока — освоить работу с циклическими событиями времени (**тиками таймера**) и написать свою первую динамическую аркаду.

---

### Механика тиков времени: Экшен TICK

**kind:** `text`

Вспомним архитектуру движка `arcade/engine.js`:

```javascript
if (tickRateMs > 0) {
  timerId = setInterval(() => {
    if (!running) return;
    tickCounter += 1;
    const nextState = update(state, { type: 'TICK', tickCounter });
    if (nextState === state) return;
    state = nextState;
    draw();
  }, tickRateMs);
}
```

Если при запуске передан параметр `tickRateMs: 150`, движок каждые 150 миллисекунд генерирует и отправляет в функцию `update(state, action)` системное действие:

```javascript
{ type: 'TICK', tickCounter: 1 } // tickCounter начинается с 1 и инкрементируется движком
```

**Фундаментальный принцип:**
Функция `update` остаётся **100% чистой и синхронной**! В ней **нет** вызовов `setInterval` или `setTimeout`.
- При нажатии клавиши направления приходит экшен `{ type: 'CHANGE_DIRECTION', direction: 'UP' }`;
- По тику таймера приходит экшен `{ type: 'TICK' }` — и змейка делает шаг вперёд на одну клетку.

### Важное отличие проекта: Ты собираешь run.js сам как архитектор!

**kind:** `text`

В пошаговых играх файл запуска `run.js` выдавался готовым.
В **этом проекте ты создаёшь `run.js` самостоятельно с нуля**!

Файл `run.js` не содержит игровой логики. Его задача — **собрать воедино три слоя архитектуры**:
1. **Слой 1 (Ядро):** функция `startEngine` из `arcade/engine.js`. Она управляет сырым вводом терминала, очисткой экрана и таймером тиков реального времени `tickRateMs`.
2. **Слой 2 (Интерфейс: Адаптеры ввода и вывода):** готовые кирпичики из `arcade/tui/`. Они переводят низкоуровневые нажатия клавиш в понятные игре действия и преобразуют кадр в строковый вид.
3. **Слой 3 (Логика):** твои чистые функции `createState`, `update`, `getView`.

Первый слой, для всех игр один и тот же. Третий слой ты пишешь сам. Давай разберем как устроен второй слой.

### Архитектурный спор: как назвать Слой 2?

**kind:** `text`

При проектировании структуры папок у инженеров возникает вопрос: как назвать каталог Слоя 2? Ниже три возможных варианта, все три правильные, но подчёркивают разные вещи:

1. **`io/` (Input / Output — Ввод/Вывод):**
   - **Фокус:** физический мир и железо. Ввод с клавиатуры (Input), вывод на экран терминала (Output).
   - Так называют системные модули ввода-вывода.
   - Название папки `io` было бы правильным, потому что хранит логику обработки ввода-вывода.

2. **`adapters/` (Адаптеры):**
   - **Фокус:** архитектура слоёв (Clean Architecture / Ports & Adapters).
   - **Концептуально это наиболее предпочтительный вариант:** чистая логика (Слой 3) изолирована от внешнего мира. Если завтра мы захотим перенести «Змейку» или «2048» в браузер (`web-ui`) или Telegram-бота, правила игры не изменятся вовсе — мы просто заменим терминальные адаптеры на браузерные. В `adapters/` могли бы сосуществовать `adapters/tui/` и `adapters/web/`.

3. **`tui/` (Terminal User Interface — Терминальный UI):**
   - **Фокус:** взаимодействие с пользовательским интерфейсом в консольной среде.
   - Поскольку вся наша аркада работает строго в терминале, мы взяли самое простое и понятное название: **`tui/`**.

### Структура Слоя 2: модули tui/ объединены по смыслу

**kind:** `text`

Хотя Слой 2 решает две разные задачи — **ввод** (клавиатура → Action) и **вывод** (View → строковый кадр), мы намеренно не дробим его на подпапки `input/` и `output/`.

Здесь работает принцип **высокой связности (High Cohesion)**: функции, обслуживающие один тип интерфейса, живут вместе:
- `arcade/tui/grid.js` — содержит и адаптеры ввода (стрелки, курсор), и рендереры сеток (`renderGrid`, `renderNumberGrid`);
- `arcade/tui/turtle.js` — содержит команды робота и рендерер Черепашки с телеметрией;
- `arcade/tui/hangman.js` — содержит алфавитный ввод и ASCII-рендер Виселицы.

Благодаря этому точка входа `run.js` импортирует всё необходимое для интерфейса всего одной строкой:
```javascript
import { createDirectionAdapter, renderGrid } from '../../tui/grid.js';
```

На самом деле, можно по разному называть и организовывать папки и файлы. Самый "архитектурно правильный" был бы:
```
adapters/
  tui/
    input/
    output/
  web/
    ...
```

Плюс такой организации: она расширяема и читаема;
Минус: пришлось бы каждую реализацию писать в своем файле, даже когда это возможно необосновано.

В нашем приложении мы остановились на шаблоне: `tui/hangman.js`, так как наши адапетрные фунции относительно небольшие и несложные, то мы решили что ложить их в один файл будет обоснованным.

Вывод: нет единственно правильной архитектуры, есть архитектура которая отражает наше приложение и хорошо обслуживает его сложность.

### Каталог инструментов Слоя 2: Рендереры и Адаптеры

**kind:** `text`

Главный принцип архитектуры слоёв: **у одного абстрактного контракта может быть несколько разных реализаций** — от универсальных до специализированных (наследование и расширение поведения).

#### Рендереры (формирование кадра на экране)
Контракт: принимает объект представления `view` и возвращает массив строк кадра `string[]`.

1. **`renderGrid` (`arcade/tui/grid.js`) — Универсальный базовый рендерер 2D-сетки:**
   - **Что делает:** самый общий рендерер аркады. Отрисовывает любую символьную матрицу `grid`: добавляет верхнюю рамку, заголовок игры `title`, счёт `score`, обрамление поля `+---+` и `|...|`, а также экраны завершения (победа, поражение или подсказку управления).
   - **Для какие игр:** «Змейка», «Космический уворачивальщик», «Сокобан», «Сапёр», «Крестики-нолики».

2. **`renderNumberGrid` (`arcade/tui/grid.js`) — Специализированный матричный рендерер:**
   - **Что дополняет к базовому:** расширяет концепцию сетки для отображения многозначных чисел (игра «2048»). В отличие от односимвольных клеток, форматирует ячейки фиксированной ширины (`cellWidth`), выравнивает числа через пробелы (`padStart`) и чертит табличные перегородки между всеми ячейками.
   - **Для чего:** «2048».

3. **`renderTurtle` (`arcade/tui/turtle.js`) — Доменный рендерер исполнителя:**
   - **Что дополняет к базовому:** берёт матрицу поля со следом, но оборачивает её в специальную приборную панель: выводит текущие координаты робота `X/Y`, курс по сторонам света, состояние инструмента (перо поднято/опущено), число шагов и памятку команд.
   - **Для чего:** «Черепашка на сетке».

4. **`renderHangman` (`arcade/tui/hangman.js`) — Альтернативный рендерер викторины:**
   - **Что делает:** полностью альтернативная визуализация без координатной сетки. Рисует фазы ASCII-виселицы по количеству ошибок, замаскированное слово с пропусками, неверные буквы и экран победы/поражения.
   - **Для чего:** «Виселица».

---

#### Адаптеры ввода (преобразование клавиш в игровые действия)
Контракт: функция `(rawStr) => Action | null`. Превращает нажатие клавиши в объект действия, либо возвращает `null` (системные клавиши `q`, `r`, `Ctrl+C` отдаются ядру).

1. **`createDirectionAdapter(options)` (`arcade/tui/grid.js`) — Универсальная настраиваемая фабрика:**
   - **Что делает:** слушает стрелки клавиатуры (ANSI-коды), клавиши WASD и русскую раскладку ЦФЫВ.
   - **Гибкость:** принимает опцию `{ eventType: '...' }` (по умолчанию `'MOVE'`). Позволяет настроить генерируемый тип экшена под контракт твоей игры: вернёт либо `{ type: 'MOVE', direction: 'UP' }`, либо `{ type: 'CHANGE_DIRECTION', direction: 'UP' }`.
   - **Для чего:** «Змейка», «Космический уворачивальщик», «Сокобан», «2048».

2. **`cursorActionAdapter` (`arcade/tui/grid.js`) — Расширенный адаптер с курсором:**
   - **Что дополняет к базовому:** специализирует перемещение под сетку с курсором (генерирует смещения `{ type: 'MOVE_CURSOR', dx, dy }`), а также перехватывает пробел/Enter (`ACTION_OPEN`) и клавиши F/А (`ACTION_FLAG`).
   - **Для чего:** «Сапёр», «Крестики-нолики».

3. **`inputAdapter` (`arcade/tui/turtle.js`) — Доменный адаптер команд робота:**
   - **Что делает:** мапит клавиши не на стороны света, а на относительные команды исполнителя (`FORWARD`, `BACKWARD`, `TURN_LEFT`, `TURN_RIGHT`), а также пробел (перо) и клавишу C (очистить след).
   - **Для чего:** «Черепашка на сетке».

4. **`inputAdapter` (`arcade/tui/hangman.js`) — Алфавитный адаптер буквенного ввода:**
   - **Что делает:** перехватывает буквы латиницы и кириллицы в верхний регистр (`{ type: 'GUESS', char }`), клавишу Tab (`TOGGLE_LANG`) и системные команды.
   - **Для чего:** «Виселица».

### Как сконфигурировать `startEngine` в своём `run.js`

В функции `startEngine` ядро ждёт от тебя объект настроек:
- `title` — текстовое название окна твоей игры;
- `createState`, `update`, `getView` — твои функции логики (Слой 3);
- `render` — выбранная функция рендеринга из Слоя 2;
- `adapter` — выбранная функция или результат вызова фабрики адаптера из Слоя 2;
- `tickRateMs` — интервал системного тика в миллисекундах (например, `150` для комфортного темпа Змейки или `100` для динамичного Уворачивальщика).

Подбери компоненты под свою игру, импортируй их и собери свой файл `run.js`!

### Системный и игровой тик: Управление скоростью и холостые тики

**kind:** `text`

Что делать, если ты хочешь эмулировать нарастающую сложность — например, чтобы змейка ускорялась по мере поедания яблок, или астероиды летели быстрее со временем?

В игровых движках для этого разделяют два понятия:

1. **Системный тик (System Tick):**
   - Непрерывный физический пульс таймера ядра движка `engine.js`, задаваемый параметром `tickRateMs` (например, каждые 30 или 50 мс).
   - На каждый системный тик движок сам увеличивает счётчик `tickCounter` (начиная с 1) и отправляет экшен:
     ```javascript
     { type: 'TICK', tickCounter: 1 }
     ```

2. **Игровой тик (Game Tick):**
   - Логический шаг игрового мира: момент, когда змейка фактически перемещается на следующую клетку поля, а метеориты сдвигаются вниз.

Если игровой тик происходит реже системного (или мир пока не должен двигаться), такой системный тик называется **«холостым»**.

#### Механика делителя тиков (Tick Divider / speedDelay)

Игра хранит только желаемую задержку `speedDelay` (по умолчанию 1 — каждый такт является шагом) и управляем им если хочет убыстрять игру:

```javascript
{
  speedDelay: 4, // игровой тик происходит каждый 4-й системный тик
  score: 0,
  // ...остальные поля
}
```

Так как тики могут быть холостыми (т.е. для пользователя ничего не изменилось), то есть два способа чтобы это указать движку:
1. если состояние для рендерера не изменилось, то вернуть входящий стейт;
2. если стейт изменился, то возвращаем копию, но на уровне движка перед рендерирнгом экрана производится сравнение текущего кадра с предыдущим;

### Каталог игр на выбор (Витрина игр)

**kind:** `text`

Выбери **одну из двух** динамических игр для реализации:

---

#### 1. 🐍 Игра «Змейка» (Snake)
- **Суть и процесс игры:** культовая классика мобильных и аркадных игр. Змейка непрерывно ползёт по прямоугольному полю 20×12. Игрок с помощью клавиш (стрелки или WASD) меняет курс её движения. На каждом тике таймера змейка продвигается на одну клетку вперёд. На поле случайным образом появляется сочное яблоко (`★`). При его съедании змейка удлиняется на один сегмент, а игроку начисляются очки. Столкновение со стеной или собственным телом приводит к мгновенному завершению игры (Game Over).
- **Частота тиков:** `tickRateMs: 150` (плавная, комфортная аркадная скорость).
- **Ключевой алгоритм:**
  - Буферизация направления (`nextDirection`), чтобы избежать ошибки быстрого двойного нажатия;
  - **Защита от разворота на 180°:** змейка, ползущая вправо, не может мгновенно повернуться влево — иначе она сразу врежется в свой же сегмент;
  - Детекция выхода за пределы экрана и самопересечения тела;
  - Случайный спавн еды строго на свободных клетках.

---

#### 2. 🚀 Игра «Космический уворачивальщик» (Space Dodger)
- **Суть и процесс игры:** динамичный аркадный тайм-киллер на реакцию и выживание. Космический истребитель (`▲`) находится у нижнего края экрана. Игрок перемещает его влево и вправо (клавиши A/D или стрелки ← / →). Сверху из глубин космоса непрерывным дождём падают астероиды (`●`). За каждый прожитый тик начисляются очки. Скорость и плотность метеоритов держат в постоянном напряжении: малейшее касание камня приводит к катастрофе.
- **Частота тиков:** `tickRateMs: 100` (динамичные 10 кадров в секунду).
- **Ключевой алгоритм:**
  - Динамический список астероидов: на каждом тике все метеориты сдвигаются вниз;
  - Очистка памяти: астероиды, вылетевшие за нижний край поля, удаляются из массива;
  - Вероятностный спавн: с вероятностью ~35-40% на верхней строке появляется новый метеорит;
  - Проверка коллизии: если координаты корабля совпадают с метеоритом — игра окончена.

### Разработка, тесты и сборка раннера

**kind:** `text`

Перед тем как создавать файлы и писать код, открой функциональную ветку `feature/<game-name>`:

Размести проект в соответствующей папке:
- `arcade/games/<игра>/<игра>.js` — чистая логика правил с обработкой `TICK`;
- `arcade/games/<игра>/<игра>.test.js` — юнит-тесты;
- `arcade/games/<игра>/run.js` — написанный тобой файл запуска.

**Особое внимание при написании юнит-тестов:**
Поскольку функция `update` детерминирована, протестировать ход времени предельно просто:

```javascript
it('TICK перемещает змейку вперед', () => {
  const state = createState({ direction: 'RIGHT' });
  const nextState = update(state, { type: 'TICK', tickCounter: 1 });
  expect(nextState.body[0].x).toBe(state.body[0].x + 1);
});
```

Никаких таймеров в тестах вызывать не нужно! Просто отправляй `{ type: 'TICK' }` и проверяй сдвиг координат. Также и с другими системными событиями.

> В данном типы игры системных событий две: 1. системный тик; 2. действие пользователя;

Запусти тесты:

```bash
bun test arcade/games/<игра>/
```

### Локальная проверка и сдача Pull Request 3

**kind:** `text`

Запусти свою игру в терминале:

```bash
bun arcade/games/<игра>/run.js
```

Проверь:
1. Игра движется плавно без рывков;
2. Управление отзывчиво реагирует на клавиши;
3. При столкновении корректно выводится экран поражения `GAME_OVER`;
4. Клавиша `R` перезапускает игру;
5. Клавиша `Q` чисто завершает процесс без зависания таймера.

### Сдача работы:
1. Проверь статус файлов в репозитории:
   ```bash
   git status
   ```
2. Закоммить изменения в рабочей ветке:
   ```bash
   git add arcade/games/<игра>/
   git commit -m "feat(arcade): реализовать динамическую игру <Название> и раннер"
   ```
3. Отправь ветку в свой репозиторий:
   ```bash
   git push -u origin feature/<game-name>
   ```
4. Открой **Pull Request** на GitHub из рабочей ветки в `main`;
5. Пришли ссылку сокурсникам в общий учебный чат на peer-review:
   ```text
   🔍 PR на ревью: [Динамическая игра: <Название игры> (логика, раннер и тесты)]
   📎 Ссылка: https://github.com/<твой-username>/fullstack-js/pull/<номер>
   📋 Жду ваших комментариев и проверки в терминале!
   ```

### Термины урока

**kind:** `text`

Пройдись по понятиям урока. Убедись, что ты можешь объяснить каждое из них своими словами.

**Термины:**
* **Дискретный такт синхронизации (Heartbeat / Tick)** — квант времени в асинхронной системе, периодический сигнал таймера, инициирующий очередной шаг вычисления состояния.
* **Делитель тактов (Tick Divider)** — архитектурный паттерн разделения непрерывного инфраструктурного таймера (системный тик ядра) и контролируемой логической скорости работы домена (доменный шаг через счётчик `tickCounter`).
* **Буферизация ввода (Input Buffering)** — сохранение входящей команды пользователя в промежуточное поле состояния для устранения состояния гонки (Race Condition) и предотвращения недопустимых резких переходов между тиками.
* **Точка сборки слоёв (Composition Root)** — самостоятельное конструирование файла запуска `run.js`, где разработчик связывает независимые интерфейсные адаптеры, параметры времени и доменную логику без монолитного фреймворка.
* **Определение пересечений (Collision Detection)** — алгоритмическая проверка совпадения координат сущностей в пространстве для фиксации доменного события.
* **Детерминированное тестирование времени** — проверка асинхронных сценариев и динамики времени синхронными юнит-тестами через прямую подачу события `{ type: 'TICK' }` без таймеров `setTimeout` и моков.
* **Холостой такт (Idle Tick)** — такт таймера, в котором состояние системы не изменилось, позволяющий оптимизировать ресурсы и исключить избыточную перерисовку интерфейса.
