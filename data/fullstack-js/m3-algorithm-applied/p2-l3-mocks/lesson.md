# Инфраструктура хранения, моки и первая функция репозитория

Разбираем модуль `node:fs`, получаем готовые функции `saveToFile` и `loadFromFile` и проверяем round-trip через реальный диск. Выясняем, почему тесты бизнес-логики никогда не должны трогать файловую систему. Разбираем их внутреннее устройство, различия (Mock vs Stub vs Spy), методы настройки (`mockReturnValue`, `mockImplementation`), проверки вызовов и правила очистки (`mockClear`, `mockReset`, `mockRestore`). Закрепляем инструменты мокирования на практике в изолированных тестах без обращения к диску.

**Термины:**
* **Инфраструктурный слой (Infra)** — код, взаимодействующий с внешними подсистемами (файловая система, сеть, база данных).
* **Персистентность** — свойство данных сохраняться на энергонезависимом носителе после завершения процесса программы.
* **Round-trip** — сквозная проверка: сохранение данных на диск и последующее чтение с проверкой идентичности.
* **Тестовый дублёр (Test Double)** — общий термин для любого объекта или функции, подменяющей реальную зависимость в автоматических тестах.
* **Стаб (Stub)** — дублёр, отвечающий заранее заготовленными ответами на вызовы (фокус на возвращаемых данных).
* **Спай (Spy)** — шпион, оборачивающий метод существующего объекта: записывает историю вызовов и обычно сохраняет оригинальное поведение.
* **Мок (Mock)** — дублёр с запрограммированными ожиданиями по вызовам (фокус на проверке взаимодействия: сколько раз вызван, с какими параметрами).
* **Изоляция теста** — гарантия того, что тест проверяет только целевую логику и не зависит от внешнего мира, диска, сети или соседних тестов.
* **Гигиена тестов** — регулярная очистка состояния и истории вызовов дублёров между запусками (`beforeEach` / `afterEach`), предотвращающая взаимное влияние тестов.

### Слой инфраструктуры: сохранение и чтение файлов

До сих пор все наши данные жили исключительно в оперативной памяти процесса: пока скрипт работает — данные есть, скрипт завершился — данные исчезли. Чтобы сервис интернет-магазина работал по-настоящему, заказы должны сохраняться между перезапусками сервера. Это свойство называется **персистентностью**.

Для работы с файлами мы используем встроенный модуль `'node:fs'`. Нам понадобятся синхронные операции:
- `writeFileSync(path, text, 'utf8')` — записать текстовую строку в файл (создаёт новый файл или полностью перезаписывает существующий);
- `readFileSync(path, 'utf8')` — прочитать содержимое файла в виде строки;
- `existsSync(path)` — проверить наличие файла по указанному пути;
- `unlinkSync(path)` — удалить файл с диска.

### Готовые функции `saveToFile` и `loadFromFile`

Слой инфраструктуры не знает ничего о заказах. Он умеет лишь брать любой массив объектов, превращать его в CSV-строку и сохранять в файл, а также читать CSV-файл и восстанавливать массив.

Код файла `infra/file-storage.js` выдаётся готовым:

```javascript
import { writeFileSync, readFileSync } from 'node:fs';
import { toCSV } from '../../utils/business/to-csv.js';
import { fromCSV } from '../../utils/business/from-csv.js';

// Сохраняет массив плоских объектов в файл в формате CSV.
export function saveToFile(path, data) {
  const text = toCSV(data);
  writeFileSync(path, text, 'utf8');
}

// Читает CSV-файл и возвращает восстановленный массив объектов.
export function loadFromFile(path) {
  const text = readFileSync(path, 'utf8');
  return fromCSV(text);
}
```

Обрати внимание на чистоту архитектуры: функции `saveToFile` и `loadFromFile` не содержат ни строчки логики о заказах, интернет-магазинах или сетевых запросах. Это универсальный низкоуровневый инструмент.

### Проблема: почему тесты бизнес-логики не должны трогать реальный диск

Мы проверим `file-storage.js` прямым round-trip тестом на реальном диске — один раз, чтобы убедиться, что модуль работает. Но когда мы переходим к тестированию репозитория (`order-repo.js`) и обработчиков (`handleCreateOrder`, `handleGetOrder`), использовать реальную файловую систему **категорически нельзя**.

Почему?
1. **Скорость:** чтение и запись на SSD или жёсткий диск в сотни и тысячи раз медленнее работы с переменными в оперативной памяти. Когда в проекте сотни тестов, запуск из миллисекунд превратится в минуты.
2. **Хрупкость и взаимное влияние:** если тест упал посреди выполнения и не успел удалить файл, следующий тест начнёт работу с «грязными» данными и тоже упадёт.
3. **Непредсказуемость окружения:** на сервере CI/CD может не быть прав на запись в нужную директорию или диск может быть переполнен.
4. **Сложность воспроизведения редких сценариев:** как протестировать, что репозиторий корректно реагирует на ошибку диска (например, файл заблокирован другим процессом)? Создавать искусственный сбой на реальном диске неудобно, а с дублёром — три строчки кода.

Мы хотим, чтобы тестируемый репозиторий честно вызывал `loadFromFile` и `saveToFile`, но при выполнении тестов данные мгновенно сохранялись в обычную переменную в памяти. Для этого применяют **тестовые дублёры (Test Doubles)**.

---

### Семейство дублёров: в чём разница между Stub, Spy и Mock

В профессиональной литературе (например, у Мартина Фаулера и Джерарда Месароша) дублёры делят на категории по их роли:

1. **Dummy (Пустышка):** значение, которое передаётся исключительно для заполнения обязательного параметра, но внутри тестируемого кода никогда не используется.
2. **Stub (Заглушка):** функция, которая отвечает **заранее заготовленными данными** («если тебя вызовут — просто верни этот массив заказов»). Стаб интересует только **вход** тестируемого кода: дать ему данные или сымитировать ошибку.
3. **Spy (Шпион):** обёртка над существующей функцией или методом, которая «подсматривает» за вызовами: сколько раз вызвали, с какими аргументами, что вернулось. При этом оригинальная функция может продолжать выполняться.
4. **Mock (Мок):** функция с запрограммированными ожиданиями по поведению: мы явно проверяем, что она была вызвана определённым образом (`toHaveBeenCalledWith(...)`).

В экосистеме JavaScript термином «мок» часто называют всё подряд. Но понимание этих трёх ролей — **вернуть заготовку (Stub)**, **подсмотреть за вызовом (Spy)** и **проверить взаимодействие (Mock)** — позволяет осознанно выбирать нужный инструмент.

Тестовый раннер `bun:test` даёт три мощных инструмента: `mock()`, `spyOn()` и `mock.module()`. Разберём каждый подробно.

### Инструмент 1: Автономная функция `mock()`

Функция `mock([implementation])` создаёт независимую обёртку с памятью.

#### Создание и базовая работа

```javascript
import { mock, test, expect } from 'bun:test';

// 1. Пустой мок (по умолчанию возвращает undefined):
const emptyMock = mock();
emptyMock('привет');
expect(emptyMock).toHaveBeenCalledTimes(1);
expect(emptyMock).toHaveBeenCalledWith('привет');

// 2. Мок с пользовательской реализацией:
const addMock = mock((a, b) => a + b);
const sum = addMock(2, 3);

expect(sum).toBe(5);
expect(addMock).toHaveBeenCalledWith(2, 3);
```

#### Важная деталь: мок должен быть вызван!

Распространённая ошибка новичков:
```javascript
function double(x) { return x * 2; }
const doubleMock = mock(double);

// ОШИБКА: вызов оригинальной функции не регистрируется в моке!
double(5);
// expect(doubleMock).toHaveBeenCalledTimes(1); // ТЕСТ УПАДЁТ: мок не вызывался!

// ПРАВИЛЬНО: нужно вызывать сам созданный мок:
doubleMock(5);
expect(doubleMock).toHaveBeenCalledTimes(1); // Тест зелёный
```

#### Настройка возвращаемых значений (превращение в Stub)

Моку можно на лету задать результат или поведение без пересоздания:

```javascript
const fetchUser = mock();

// Все последующие вызовы вернут это значение:
fetchUser.mockReturnValue({ id: 1, name: 'Анна' });
console.log(fetchUser()); // { id: 1, name: 'Анна' }

// Вернуть значение только на один следующий вызов:
fetchUser.mockReturnValueOnce({ id: 2, name: 'Борис' });
console.log(fetchUser()); // { id: 2, name: 'Борис' }
console.log(fetchUser()); // { id: 1, name: 'Анна' } (вернулся к предыдущему)

// Подменить реализацию на лету:
fetchUser.mockImplementation((id) => ({ id, name: `Пользователь #${id}` }));
console.log(fetchUser(42)); // { id: 42, name: 'Пользователь #42' }
```

#### Проверки вызовов (проверки взаимодействия)

`bun:test` содержит готовые матчеры для `expect`:
- `expect(myMock).toHaveBeenCalled()` — мок был вызван хотя бы один раз;
- `expect(myMock).toHaveBeenCalledTimes(n)` — вызван ровно `n` раз;
- `expect(myMock).toHaveBeenCalledWith(arg1, arg2)` — хотя бы один из вызовов содержал указанные аргументы;
- `expect(myMock).toHaveBeenLastCalledWith(...)` — последний вызов был с этими аргументами.

Внутри мока также есть свойство `myMock.mock`, где хранится полный журнал:
- `myMock.mock.calls` — массив массивов всех полученных аргументов (`[[arg1, arg2], [arg1, arg2]]`);
- `myMock.mock.results` — массив результатов всех вызовов (`[{ type: 'return', value: ... }]`).

### Инструмент 2: Наблюдение за объектами через `spyOn(object, method)`

В чём отличие `spyOn` от `mock()`?
`mock()` создаёт **новую отдельную функцию**. А `spyOn(object, methodName)` прикрепляется к **уже существующему методу реального объекта**.

#### Поведение по умолчанию: оригинальный метод продолжает работать!

Шпион по умолчанию не заменяет логику, а лишь записывает вызовы:

```javascript
import { spyOn, test, expect } from 'bun:test';

const calculator = {
  multiply(a, b) {
    return a * b;
  },
};

const spy = spyOn(calculator, 'multiply');

const result = calculator.multiply(4, 5);

// 1. Метод отработал по-настоящему:
expect(result).toBe(20);

// 2. И при этом шпион записал вызов:
expect(spy).toHaveBeenCalledTimes(1);
expect(spy).toHaveBeenCalledWith(4, 5);

// 3. Возвращаем оригинальное состояние объекту:
spy.mockRestore();
```

#### Временная подмена поведения метода

Если мы хотим, чтобы метод не выполнял реальные действия (например, не отправлял логи в консоль или не делал реальный сетевой запрос):

```javascript
const logSpy = spyOn(console, 'log').mockImplementation(() => {});

console.log('Это сообщение не напечатается в терминале');

expect(logSpy).toHaveBeenCalledWith('Это сообщение не напечатается в терминале');

// ОБЯЗАТЕЛЬНО возвращаем настоящий console.log назад!
logSpy.mockRestore();
```

Метод `spy.mockRestore()` восстанавливает исходный метод объекта. Если забыть его вызвать, `console.log` останется заглушенным во всех следующих тестах!

### Инструмент 3: Подмена статических импортов через `mock.module(path, factory)`

А что делать, если зависимость зашита внутрь файла через статический `import`?

Посмотри на структуру:
```javascript
// app/repo/order-repo.js
import { loadFromFile, saveToFile } from '../../infra/file-storage.js';

export function getOrder(id) {
  const orders = loadFromFile('data/orders.csv');
  return orders.find((o) => Number(o.id) === Number(id)) ?? null;
}
```

Здесь `loadFromFile` — это не метод объекта (поэтому `spyOn` не применить) и не параметр функции (поэтому аргументом передать `mock()` мы не можем). Функция импортируется напрямую из файла!

Для таких случаев в Bun есть инструмент **`mock.module(modulePath, factoryFunction)`**:
Он перехватывает загрузку модуля на уровне системы модулей Bun. Когда любой код пытается импортировать указанный путь, Bun отдаёт ему объект из нашей фабрики:

```javascript
import { mock, test, expect, beforeEach } from 'bun:test';

// Заводим фальшивую БД в оперативной памяти тестового файла:
let memoryDb = [];

// Подменяем модуль ДО выполнения бизнес-кода:
mock.module('../../infra/file-storage.js', () => ({
  loadFromFile: mock(() => [...memoryDb]),
  saveToFile: mock((path, data) => {
    memoryDb = [...data];
  }),
}));

// Импортируем тестируемый репозиторий:
import { getOrder } from './order-repo.js';

test('getOrder находит заказ из оперативной памяти', () => {
  memoryDb = [{ id: 1, customer: 'Иван', amount: 1000 }];

  const order = getOrder(1);

  expect(order).toEqual({ id: 1, customer: 'Иван', amount: 1000 });
});
```

При таком подходе:
- Тестируемый `order-repo.js` уверен, что вызывает настоящие функции;
- Реальный диск не трогается;
- Тест выполняется за долю миллисекунды.

### Матрица выбора: что и в какой момент использовать

- **Передать функцию аргументом или коллбэком:** инструмент `mock([fn])`. Создаёт автономную функцию с памятью вызовов. Пример: `users.forEach(mockFn)`.
- **Подсмотреть за методом объекта или временно заглушить его:** инструмент `spyOn(obj, 'method')`. Оборачивает метод существующего объекта, требует `mockRestore()`. Пример: `spyOn(console, 'log')`.
- **Подменить зависимость, импортируемую через `import`:** инструмент `mock.module(path, factory)`. Перехватывает загрузку файла в загрузчике модулей Bun. Пример: подмена `infra/file-storage.js` в тестах репозитория.

### Жизненный цикл и гигиена тестов: `mockClear`, `mockReset`, `mockRestore`

Один из самых коварных источников багов в тестах — **утечка состояния** между тестовыми кейсами.

Представь: тест №1 вызвал мок 3 раза. Тест №2 ожидает, что мок вызовется 1 раз, но проверяет общее число: `expect(myMock).toHaveBeenCalledTimes(1)`. Если счётчик не сбросить, тест №2 увидит 4 вызова и упадёт!

Для управления состоянием у каждого мока есть три метода:

1. **`mockFn.mockClear()`**:
   Очищает историю вызовов (`calls`) и результатов (`results`). **Поведение и реализация сохраняются.**
   *Когда использовать:* в блоке `beforeEach`, чтобы счётчики вызовов обнулялись перед каждым тестом.

2. **`mockFn.mockReset()`**:
   Очищает историю вызовов **И сбрасывает реализацию** (мок снова возвращает `undefined`).
   *Когда использовать:* когда в одном тесте задавалась особая реализация через `mockImplementation`, а в следующем тесте нужна чистая заготовка.

3. **`spy.mockRestore()`**:
   Полностью снимает шпиона с объекта и восстанавливает оригинальный метод, который был до вызова `spyOn`.
   *Когда использовать:* в `afterEach` для всех шпионов, созданных через `spyOn`.

Пример правильной гигиены тестового файла:
```javascript
import { beforeEach, afterEach, mock } from 'bun:test';

let memoryOrders = [];
const loadMock = mock(() => [...memoryOrders]);
const saveMock = mock((path, data) => { memoryOrders = [...data]; });

beforeEach(() => {
  // 1. Очищаем состояние данных в памяти:
  memoryOrders = [];

  // 2. Очищаем счётчики вызовов моков:
  loadMock.mockClear();
  saveMock.mockClear();
});
```
