### Зона ответственности репозитория

**kind:** `text`

Создай каталог `app/repo/` внутри папки проекта `m2-m3-algorithms/m3-p2-http/`.
Создай файлы `app/repo/order-repo.js` и `app/repo/order-repo.test.js`.

**Зона ответственности:**
Репозиторий отвечает за чтение и запись данных заказа, инкапсулируя (закрывая) обращение к файлу через `file-storage.js`. Он знает, что работает с объектом заказа (может явно обращаться по ключам), но **не валидирует данные**, доверяясь клиенту (к нему всегда приходит валидный объект заказа) — он чистое хранилище, ответственное сохранить и выдать данные по требованию.

Чтобы выполнить свою работу, он знает где сохранен файл и путь к нему. Но...

### Проблема путей к файлу данных и два варианта решения

**kind:** `text`

При работе с файловой системой в JavaScript важно понимать, как разрешаются пути, рассмотрим следующий код.

   ```javascript
   import { loadFromFile, saveToFile } from '../../infra/file-storage.js';

   const orders = loadFromFile('/data/orders.csv');
   ```

Тут мы видим две пути в файловой системе.

1. Путь импорта **всегда отсчитывается от расположения самого файла** `order-repo.js`. Из папки `app/repo/` мы поднимаемся на два уровня вверх (`../../infra/`).

2. **Путь к файлу данных для `node:fs`:**
   Путь вроде `'data/orders.csv'` разрешается операционной системой **от текущей рабочей папки терминала (Current Working Directory, чтобы в коде получить в рантайме путь откуда произошел вызов: `process.cwd()`)**, а не от расположения файла `order-repo.js`!

**В чём проблема:**
Если твой терминал открыт в корне всего монорепозитория `fullstack-js/`, а запуск происходит по пути `bun run m2-m3-algorithms/m3-p2-http/server/main.js`, то `process.cwd()` равен `fullstack-js/`. Программа попытается найти `fullstack-js/data/orders.csv` вместо файла внутри проекта!

Соответственно, если запускать код из папки: `fullstack-js/m2-m3-algorithms/m3-p2-http`. Тогда путь разрешится правильно и файл будет найден.

#### Два варианта решения: выбери подходящий

**Вариант 1:** Запускать код всегда с корня проекта, наш текущий вариант:
```javascript
let ordersPath = 'data/orders.csv';
```

Перед запуском, всегда убеждаться что в корне проекта, при необходимости переходить в нее:
```bash
cd m2-m3-algorithms/m3-p2-http
```

**Вариант 2:** Абсолютная привязка
```javascript
import { resolve } from 'node:path';

let ordersPath = resolve(import.meta.dirname, '../../data/orders.csv');
```

Для любого js файла можно получить его абсолютный путь в момент выполнения через: `import.meta.dirname`. Функция `resolve` позволяет передавая абсолютные и относительные получить итоговый путь. В итоге вне зависимости откуда запускается код, пути разрешатся правильно.

Выбери любой из вариантов для переменной `ordersPath` в `order-repo.js`.

**Дополнительно:** добавь ниже функцию:
```js
export function getOrdersPath() {
  return ordersPath;
}

export function setOrdersPath(customPath) {
  ordersPath = customPath;
}

```
Функция `getOrdersPath`, `setOrdersPath` позволяет динамически читать, устанавливать путь, понадобится позже, при написании интеграционных тестов.

### Паттерн Read-Modify-Write и генерация `id`

**kind:** `text`

Поскольку мы храним данные в одном плоском CSV-файле, любая операция изменения строится по алгоритму **Read-Modify-Write**:
1. **Read:** читаем весь массив заказов через `loadFromFile(ordersPath)`. Если файл ещё не создан (ошибка `ENOENT`) — начинаем с пустого массива `[]`.
2. **Modify:** производим нужные изменения в оперативной памяти (добавление, обновление полей, удаление), соблюдая иммутабельность.
3. **Write:** сохраняем изменённый массив обратно на диск через `saveToFile(ordersPath, ...)`.

**Генерация `id`:**
HTTP-обработчик не должен генерировать номер заказа — это обязанность репозитория.
- Если список заказов пуст — новый заказ получает `id = 1`.
- Если заказы уже есть — новый заказ получает `id = Math.max(...orders.map((o) => Number(o.id))) + 1`.

На самом деле тут есть критическая дыра. id это уникальный номер который не должен повторяться никогда. Если мы создадим три заказа, потом удалим последний и создадим новый, то у нас повторно появится заказ с `id=3`.

Решением является другой репозиторий — нумератор, который хранит последнее сгенерированне значение. Но у нас учебный проект, не будем этим заморачиваться.

### Требования к разработке: функции репозитория

**kind:** `text`

В модуле `app/repo/order-repo.js` реализуй функции доступа к данным согласно инженерным требованиям и критериям приёмки:

#### Общие системные требования:
- **Чистое хранилище:** репозиторий не валидирует поля и типы данных — он доверяет данным, приходящим от вызывающего кода, сохраняет и возвращает их.
- **Инфраструктура:** все файловые операции выполняются исключительно через функции `loadFromFile` и `saveToFile` из `infra/file-storage.js`.
- **Иммутабельность:** любые изменения коллекции в памяти не должны мутировать исходные структуры данных.
- **Безопасность первого запуска:** если файл на диске ещё не существует (системная ошибка `ENOENT`), репозиторий не падает, а работает с пустым списком `[]`. При записи создается новый файл.

#### Спецификация функций и критерии приёмки:

**1. Получение заказа по ID:** `getOrder(id)`
- **Вход:** числовой идентификатор заказа `id` (распарсен и проверен вызывающим кодом).
- **Выход:**
  - Если заказ найден — возвращает найденный объект заказа.
  - Если заказ не найден или хранилище пусто — возвращает `null`.
- **Критерии приёмки:**
  - Ищет запись по совпадению числового `id`.
  - При отсутствии записи возвращает `null`, исключение не выбрасывается.
  - Не мутирует коллекцию в памяти.

**2. Получение полного списка:** `listOrders()`
- **Вход:** параметров нет.
- **Выход:**
  - Возвращает массив всех сохранённых объектов заказов.
  - Если файл отсутствует (ошибка `ENOENT`) — возвращает пустой массив `[]`.
- **Критерии приёмки:**
  - Результат всегда является массивом (никогда не `null` и не `undefined`).
  - При ошибке `ENOENT` возвращает пустой массив `[]`, не падая с ошибкой.

**3. Добавление нового заказа:** `addOrder(data)`
- **Вход:** объект данных заказа `data` (распарсенные и валидированные поля заказа без `id`).
- **Выход:**
  - Возвращает созданный объект заказа с заполненным полем `id`.
- **Критерии приёмки:**
  - Переданный аргумент `data` не мутируется.
  - Файл на диске перезаписывается массивом, включающим новый заказ.
  - Первый заказ в пустом хранилище получает `id = 1`.
  - Входящее `id` (если передано) всегда отбрасывается.

**4. Обновление существующего заказа:** `updateOrder(id, updates)`
- **Вход:** числовой `id` заказа и объект изменений `updates` (распарсенные валидные поля без `id`).
- **Выход:**
  - Возвращает полный объект обновлённого заказа.
  - Если запись по `id` не найдена — возвращает `null`.
- **Критерии приёмки:**
  - Поле `id` невозможно изменить через `updates`.
  - Все остальные поля обновлены;
  - Обновлённый объект сохранён в файле;
  - Если заказ с переданным `id` не существует — вызов `saveToFile` не производится.

**5. Удаление заказа:** `deleteOrder(id)`
- **Вход:** числовой `id` заказа (распарсен и проверен вызывающим кодом).
- **Выход:**
  - Возвращает `true` в случае успеха;
  - Возвращает `false`, если объект с таким `id` не найден.
- **Критерии приёмки:**
  - Объект удалён из массива и изменения сохранены в файле;
  - В сохранённом на диск массиве удалённый заказ отсутствует;
  - Если заказ с указанным `id` не существует — вызов `saveToFile` не производится.

**6. Установка пути к файлу:** `setOrdersPath(customPath)`
- **Вход:** строка пути к файлу `customPath`.
- **Выход:** ничего не возвращает (`undefined`).
- **Зачем нужна:** переключает внутренний путь `ordersPath = customPath`. Понадобится нам позже при написании интеграционных тестов сервера, чтобы направлять сохранение данных во временный файл и не затирать рабочую базу `data/orders.csv`.
- **Критерии приёмки:**
  - Принимает строку пути и обновляет значение `ordersPath`.
  - Все последующие вызовы функций репозитория читают и пишут в новый переданный файл.

### Правила написания тестов по TDD

**kind:** `text`

Все тесты пиши в `app/repo/order-repo.test.js` перед реализацией логики, используя знания о моках из прошлого урока:

**Рекомендации к организации тестов:**
1. **Изоляция через мок хранилища:**
   - Подмени модуль `../../infra/file-storage.js` с помощью `mock.module`:
     ```javascript
     let memoryOrders = [];

     mock.module('../../infra/file-storage.js', () => ({
       loadFromFile: mock(() => [...memoryOrders]),
       saveToFile: mock((path, data) => {
         memoryOrders = [...data];
       }),
     }));
     ```
   - Никаких реальных файлов `orders.csv` во время тестов создаваться не должно!
2. **Очистка состояния (гигиена):**
   - В хуке `beforeEach` обязательно очищай `memoryOrders = [];` и сбрасывай счётчики моков через `.mockClear()`.

### Термины урока

**kind:** `text`

Пройдись по понятиям урока.

**Термины:**
* **Паттерн Репозиторий** — слой абстракции над хранилищем данных.
* **Рабочая директория (CWD)** — папка, из которой запущен процесс в терминале.
* **`import.meta.dirname`** — абсолютный путь к папке текущего JavaScript-файла.
* **Read-Modify-Write** — чтение коллекции, модификация в памяти и полная перезапись.
* **Автоинкремент** — инкрементальное вычисление уникального идентификатора.
* **Иммутабельность** — принцип неизменяемости исходных структур данных при модификации.
