# Репозиторий заказов: операции CRUD — краткая выжимка

- Репозиторий (`app/repo/order-repo.js`) выступает чистым CRUD-хранилищем данных: изолирует детали файловой системы и предоставляет удобный интерфейс работы с коллекцией записей без валидации.
- **Проблема путей к данным:** относительные пути в `node:fs` зависят от рабочей папки терминала (`process.cwd()`). Рассмотрели два решения:
  1. Работать строго из корня проекта `m2-m3-algorithms/m3-p2-http` с простым путем `'data/orders.csv'`;
  2. Привязать путь к расположению файла через `resolve(import.meta.dirname, '../../data/orders.csv')`.
- Все операции модификации используют паттерн **Read-Modify-Write**: прочитать текущие данные, модифицировать массив в оперативной памяти и перезаписать файл через `saveToFile`.
- Репозиторий не валидирует данные — проверка данных возложена на обработчики через валидаторы и фабрику `createOrder`.
- Ключевое архитектурное правило: генерация уникального идентификатора `id` — ответственность репозитория (`addOrder`), а не сетевых обработчиков.
- Реализован полный набор операций:
  - `listOrders()` — читает файл и возвращает массив заказов (или `[]`);
  - `getOrder(id)` — возвращает найденный заказ по `id` или `null`;
  - `addOrder(orderData)` — вычисляет новый `id`, добавляет запись, сохраняет и возвращает её;
  - `updateOrder(id, updates)` — обновляет поля существующего заказа или возвращает `null`;
  - `deleteOrder(id)` — удаляет заказ и возвращает его или `null`;
  - `setOrdersPath(customPath)` — изменяет внутренний путь к файлу данных (понадобится позже в интеграционных тестах для изоляции от рабочей базы).
- Все крайние случаи покрыты тестами через мок хранилища `file-storage.js`.
- В следующем уроке переходим к сетевому слою: знакомимся с HTTP, поднимаем локальный сервер `Bun.serve` и разбираем таблицу маршрутизации `server/route.js`.
