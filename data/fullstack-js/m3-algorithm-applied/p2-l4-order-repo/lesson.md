# Репозиторий заказов: операции CRUD

**Краткое содержание:**
Создаём слой доступа к данным `app/repo/order-repo.js` и реализуем функции доступа к данным: `getOrder`, `listOrders`, `addOrder`, `updateOrder`, `deleteOrder` и `setOrdersPath`. Разбираем важную архитектурную проблему: как разрешаются пути к файлам данных в Node.js/Bun и почему относительные пути могут вести себя неожиданно в зависимости от рабочей директории терминала (`process.cwd()`). Рассматриваем оба варианта решения: дисциплину рабочей папки проекта и абсолютное разрешение через `node:path` и `import.meta.dirname`. Реализуем функцию переключения пути `setOrdersPath` для изоляции данных в будущих интеграционных тестах, осваиваем паттерн Read-Modify-Write, реализуем генерацию уникальных идентификаторов `id` и покрываем функции тестами через моки хранилища по TDD.

**Термины:**
* **Паттерн Репозиторий (Repository)** — слой абстракции между бизнес-логикой и хранилищем данных, представляющий коллекцию объектов как коллекцию в оперативной памяти.
* **Рабочая директория (CWD, Current Working Directory)** — папка файловой системы, из которой запущен текущий процесс в терминале (`process.cwd()`).
* **Абсолютный путь** — полный путь от корня файловой системы к файлу или папке.
* **`import.meta.dirname`** — специальное свойство ES-модулей, возвращающее абсолютный путь к папке текущего исполняемого файла.
* **Read-Modify-Write** — алгоритм работы с файловым хранилищем: прочитать весь список, изменить его в памяти и записать обратно на диск целиком.
* **Автоинкремент ID** — автоматическое вычисление следующего идентификатора (на единицу больше максимального из существующих).
* **Иммутабельная модификация** — создание нового массива/объекта при изменении данных без мутации исходной коллекции.

### Зона ответственности репозитория

В прошлых уроках мы подготовили валидаторы сущности в `app/entity/` и освоили инструменты работы с файлами и моками в `infra/`. Теперь пришло время связать эти части и создать слой доступа к данным — `app/repo/order-repo.js`.

Репозиторий отвечает за чтение и запись данных заказа, инкапсулируя (закрывая) обращение к файлу через `file-storage.js`:
- Он знает, что работает с объектом заказа (может явно обращаться по ключам);
- Но **не валидирует данные**, доверяясь клиенту (к нему всегда приходит валидный объект заказа) — он чистое хранилище, ответственное сохранить и выдать данные по требованию;
- Вышележащие слои (обработчики) не думают о том, в каком файле лежат данные, в каком формате они записаны и как называется модуль чтения. Они просто вызывают методы: «дай список», «сохрани заказ», «обнови заказ».

### Проблема путей к файлу данных: где живёт файл?

При работе с файловой системой в JavaScript разработчики часто сталкиваются с неочевидным поведением относительных путей.

Сравни два пути:
1. **Путь в `import`:**
   ```javascript
   import { loadFromFile } from '../../infra/file-storage.js';
   ```
   Здесь путь **всегда разрешается относительно расположения текущего файла** (`app/repo/order-repo.js`). Откуда бы ты ни запускал сервер или тесты, подняться на два уровня вверх — это всегда папка проекта.

2. **Путь в функциях `node:fs` (`saveToFile`, `loadFromFile`):**
   ```javascript
   const ORDERS_PATH = 'data/orders.csv';
   ```
   А вот здесь путь — это просто строка, которую модуль `fs` передаёт операционной системе. В Node.js и Bun все относительные пути для файловых операций разрешаются **от текущей рабочей папки терминала (Current Working Directory, `process.cwd()`)**, а не от файла `order-repo.js`!

#### В чём опасность?

Представь структуру папок:
```text
fullstack-js/                           <-- корень монорепозитория
  m2-m3-algorithms/
    m3-p2-http/                         <-- корень нашего проекта
      app/repo/order-repo.js
      server/main.js
      data/orders.csv
```

- Если терминал открыт в `m3-p2-http/` и ты запускаешь `bun run server/main.js`, то `process.cwd()` равен `m3-p2-http/`. Относительный путь `'data/orders.csv'` попадает точно в цель: `m3-p2-http/data/orders.csv`.
- Но если терминал открыт в корне `fullstack-js/` и скрипт запущен как `bun run m2-m3-algorithms/m3-p2-http/server/main.js`, то `process.cwd()` равен `fullstack-js/`! Программа попытается прочитать `fullstack-js/data/orders.csv`, файла там не окажется, а при сохранении он создастся в корне монорепозитория, а не внутри проекта!
- Если же кто-то перейдёт `cd server` и выполнит `bun run main.js`, программа станет искать `server/data/orders.csv` и упадёт с ошибкой.

#### Два варианта решения проблемы

В современной разработке эту задачу решают двумя способами:

##### Вариант 1: Соглашение о рабочей директории (стандарт для консольных утилит)
Мы договариваемся, что **все команды проекта всегда выполняются из корня проекта `m2-m3-algorithms/m3-p2-http/`**:
```bash
cd m2-m3-algorithms/m3-p2-http
```
В коде репозитория оставляем простой путь:
```javascript
const ORDERS_PATH = 'data/orders.csv';
```
*Плюсы:* предельно чистый и лаконичный код, не требующий вспомогательных модулей.
*Минусы:* если забыть сделать `cd` в папку проекта, путь разойдётся.

##### Вариант 2: Абсолютная привязка к файлу через `node:path` и `import.meta.dirname`
Мы привязываем путь к расположению самого файла `order-repo.js`, независимо от того, где сейчас открыт терминал:
```javascript
import { resolve } from 'node:path';

// import.meta.dirname даёт абсолютный путь к папке app/repo/
// resolve поднимается на 2 уровня вверх (в корень проекта) и переходит в data/orders.csv:
const ORDERS_PATH = resolve(import.meta.dirname, '../../data/orders.csv');
```
*Плюсы:* стопроцентная надёжность. Сервер или тесты можно запускать из любой папки — файл `orders.csv` всегда будет найден в правильном месте внутри проекта.
*Минусы:* требуется импорт модуля `'node:path'` и понимание конструкции `import.meta.dirname`.

*Вывод:* В учебном проекте ты можешь выбрать любой из двух вариантов. Для константы `ORDERS_PATH` в `order-repo.js` выбери вариант, который тебе понятнее, и держи в голове разницу между путями в `import` и путями в операциях ввода-вывода!

### Паттерн Read-Modify-Write

Поскольку мы храним данные в плоском CSV-файле, добавление, изменение или удаление записей строится по единому шаблону:

```text
[ Файл на диске ]
      ↓  (loadFromFile)
[ Массив объектов в памяти ]
      ↓  (добавление, замена или фильтрация)
[ Изменённый массив в памяти ]
      ↓  (saveToFile)
[ Файл на диске ]
```

1. **Read (Прочитать):** вызываем `loadFromFile(ORDERS_PATH)`. Если файл ещё не создан (ошибка `ENOENT`), работаем с пустым массивом `[]`.
2. **Modify (Изменить):** производим нужные манипуляции над массивом в оперативной памяти, соблюдая иммутабельность (создаём новый массив).
3. **Write (Записать):** сохраняем обновлённый массив обратно через `saveToFile(ORDERS_PATH, updatedOrders)`.

### Архитектурное решение: кто назначает `id`

В некоторых проектах можно встретить ошибку: номер заказа генерируют в HTTP-обработчике. Это нарушение границ слоёв:
- HTTP-обработчик отвечает только за приём сетевого запроса и отдачу ответа.
- Назначение уникального идентификатора записи — это обязанность хранилища данных.
- Поэтому **генерацию и присвоение `id` берёт на себя метод `addOrder` репозитория**.

Правило генерации:
- Если список заказов пуст — новый заказ получает `id = 1`.
- Если в списке уже есть заказы — новый заказ получает `id = max(id) + 1`.

> **Тонкость архитектуры:** В таком подходе есть известное ограничение: если создать три заказа, затем удалить последний (`id: 3`) и создать новый — он снова получит `id: 3`. В промышленных системах за генерацию уникальных ключей отвечает отдельный нумератор (sequence/autoincrement) в СУБД, сохраняющий счётчик независимо от удалений. Для нашего учебного проекта вычисления от максимума достаточно.

### Требования к разработке: пять функций репозитория

В файле `app/repo/order-repo.js` должны быть реализованы пять функций доступа к данным:

1. **`getOrder(id)`** — получить заказ по идентификатору:
   - Приводит идентификатор к числу при поиске (`Number(item.id) === Number(id)`).
   - Возвращает найденный объект или `null`, если заказ не найден (без исключений).
2. **`listOrders()`** — получить список всех заказов:
   - Читает файл через `loadFromFile(ORDERS_PATH)`.
   - Возвращает массив записей; при отсутствии файла (`ENOENT`) возвращает пустой массив `[]`.
3. **`addOrder(data)`** — создать новый заказ:
   - Принимает данные без `id`, генерирует следующий `id` (`1` или `max + 1`).
   - Сохраняет объединённый объект `{ ...data, id: nextId }` на диск и возвращает его.
   - Не мутирует переданный аргумент.
4. **`updateOrder(id, updates)`** — обновить поля существующего заказа:
   - Находит запись по `id`. Если не найдена — возвращает `null` (диск не трогается).
   - Объединяет поля `{ ...existing, ...updates, id: existing.id }`, гарантируя неизменность `id`.
   - Сохраняет файл и возвращает обновлённый объект.
5. **`deleteOrder(id)`** — удалить заказ по идентификатору:
   - Находит запись по `id`. Если не найдена — возвращает `null` (диск не трогается).
   - Удаляет запись из массива, перезаписывает файл и возвращает удалённый объект.

### Тестирование через `mock.module` по TDD

В прошлом уроке мы освоили `mock.module`. Репозиторий идеально подходит для проверки этого навыка:
- В тестах `order-repo.test.js` мы подменяем `infra/file-storage.js` заглушкой в оперативной памяти.
- Ни один байт не пишется на физический диск.
- Все пять функций проверяются на успешные сценарии и крайние случаи: пустая база, ненайденный `id`, корректный автоинкремент.

- Проводится прогон всех тестов ядра (`bun test app/entity/ app/repo/`);
- Ветка `feat/order-repo` пушится в репозиторий;
- Оформляется Pull Request с фокусом на правилах валидации, автоинкременте ID и чистоте моков;
- После апрувов ветка мержится в `main`.
