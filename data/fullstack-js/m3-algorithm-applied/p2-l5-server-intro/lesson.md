# Сетевой транспорт: HTTP, Bun.serve и маршрутизация

**Краткое содержание:**
Переходим ко второму этапу проекта — сетевому транспорту приложения (`server/`). Создаём рабочую ветку `feat/http-service` от обновлённого `main`. Знакомимся с протоколом HTTP, методом `GET`, устройством URL (path и query-параметры) и кодами статусов ответа. Получаем готовую серверную обёртку `server/server.js` на нативном `Bun.serve` и заготовку таблицы маршрутизации `server/route.js`. Запускаем тестовый сервер и учимся отправлять к нему запросы через терминал и браузер.

**Время:** ~25 мин

**Основные темы:**
- Протокол HTTP: клиент, сервер, запрос и ответ
- Метод `GET`, структура URL: протокол, хост, path и query
- Коды ответа HTTP: `200 OK`, `400 Bad Request`, `404 Not Found`
- Готовая обёртка сервера: `server/server.js` на `Bun.serve` (выдаётся)
- Почему сервер передаёт в обработчик сырой URL строкой
- Таблица маршрутизации: `server/route.js` (заготовка)
- Первый запуск и проверка через curl и браузер
- Термины урока

**Термины:**
* **HTTP (Hypertext Transfer Protocol)** — сетевой протокол прикладного уровня для обмена сообщениями между клиентом и сервером.
* **Клиент** — приложение, инициирующее соединение и отправляющее запрос (веб-браузер, утилита `curl`).
* **Сервер** — процесс, слушающий сетевой порт, принимающий запросы и формирующий ответы.
* **Path (Путь)** — часть адреса URL после хоста до символа `?` (например, `/get` или `/list`), по которой выбирается маршрут.
* **Query-параметры** — строка пар `ключ=значение` после символа `?` (например, `?id=5&name=Анна`).
* **Код состояния (HTTP Status Code)** — трёхзначное число в ответе сервера, отражающее результат обработки запроса.
* **Маршрутизация (Routing)** — сопоставление пути сетевого запроса с конкретной функцией-обработчиком.

### Как работает сетевой протокол HTTP

В основе современного веба лежит модель «запрос — ответ».

```text
[ Клиент: браузер / curl ]  ---- (HTTP-запрос: метод, путь, параметры) --->  [ Наш сервер ]
[ Клиент: браузер / curl ]  <--- (HTTP-ответ: статус-код, заголовки, тело) --  [ Наш сервер ]
```

1. Клиент устанавливает сетевое соединение с сервером по адресу и порту (например, `http://localhost:3000`).
2. Клиент отправляет текстовый запрос с указанием **метода** (в нашем проекте мы используем метод **`GET`**) и адреса ресурса.
3. Сервер обрабатывает запрос и отправляет ответ: числовой код состояния и тело ответа (обычно строка в формате JSON).

### Анатомия URL-адреса

Адрес запроса состоит из понятных частей:

```text
http://localhost:3000/get?id=101&format=json
────── ────────────── ──── ────────────────────
схема       хост      path        query
```

- **Схема (протокол):** `http://`
- **Хост и порт:** `localhost:3000` (наш локальный компьютер, порт 3000)
- **Path (Путь):** `/get` — именно по этой строке сервер понимает, какое действие от него хотят.
- **Query (Параметры):** `id=101&format=json` — дополнительные данные, разделённые амперсандом `&`. В первом проекте мы уже научились разбирать такую строку с помощью написанной функции `getQueryParams`.

### Коды ответа

Сервер обязан явно сообщать клиенту о результате:
- **`200 OK`** — запрос успешно обработан, в теле ответа лежат запрошенные данные.
- **`400 Bad Request`** — ошибка на стороне клиента: переданы неверные параметры, отсутствует обязательное поле или нарушены правила валидации.
- **`404 Not Found`** — запрошенный путь не существует или запись с указанным `id` не найдена в базе данных.

### Готовый сервер: `server/server.js`

Инфраструктуру сетевого транспорта мы выдаём готовой.
Файл `server/server.js` использует нативный движок `Bun.serve` без подключения сторонних библиотек и содержит централизованный обработчик исключений:

```javascript
export function runServer(routes, port = 3000) {
  const server = Bun.serve({
    port,
    fetch(request) {
      const url = new URL(request.url);
      const handler = routes[url.pathname];

      if (!handler) {
        return new Response(
          JSON.stringify({ error: 'Маршрут не найден' }),
          {
            status: 404,
            headers: { 'Content-Type': 'application/json; charset=utf-8' },
          }
        );
      }

      try {
        // Передаём в обработчик ПОЛНЫЙ сырой URL строкой:
        const result = handler(request.url);
        return new Response(
          result, // перевести в json — обязанность обработчика
          {
            status: 200,
            headers: { 'Content-Type': 'application/json; charset=utf-8' },
          }
        );
      } catch (error) {
        let status = 500;
        if (error.name === 'NotFoundError') {
          status = 404;
        } else if (error.name === 'OrderValidationError') {
          status = 400;
        }

        return new Response(
          JSON.stringify({ error: error.message }),
          {
            status,
            headers: { 'Content-Type': 'application/json; charset=utf-8' },
          }
        );
      }
    },
  });

  console.log(`Сервер запущен: http://localhost:${port}`);
  return server;
}
```

### Обработчик не возвращает Response: чистота архитектуры

Обрати внимание на ключевую архитектурную деталь:
- Функция-обработчик **не создаёт и не возвращает объект `Response`**.
- Возврат `Response` был бы утечкой деталей сетевого протокола (Web API / HTTP) в слой приложения.
- Задача обработчика — принять URL строкой, выполнить оркестрацию (разобрать параметры, вызвать валидатор и репозиторий) и вернуть результат **в виде строки JSON** (`return JSON.stringify(...)`).
- Создание самого объекта `Response`, установка HTTP-статуса `200` и заголовка `Content-Type: application/json; charset=utf-8` — это обязанность сервера (`server/server.js`).

### Централизованная обработка ошибок

Обрати внимание на блок `try / catch` вокруг вызова обработчика:
- **Ошибки бизнес-валидации (`400 Bad Request`):** если обработчик, фабрика или валидатор бросает ошибку `OrderValidationError` (клиент прислал неверные параметры, отсутствует обязательное поле и т.д.), сервер возвращает клиенту JSON `{ error: error.message }` со статусом `400`.
- **Ресурс не найден по логике обработчика (`404 Not Found`):** если обработчик не нашёл запись в репозитории (например, заказ с указанным `id`), он бросает специальное исключение `NotFoundError`. Сервер ловит его и возвращает `{ error: error.message }` со статусом `404`.
- **Маршрут не найден (`404 Not Found`):** если запрошенный путь отсутствует в таблице `routes`, сам сервер возвращает статус `404` с сообщением `{ error: 'Маршрут не найден' }`.
- **Непредвиденные сбои (`500 Internal Server Error`):** любые другие неожиданные исключения возвращаются с кодом `500`.

Благодаря централизации на уровне сервера тонким обработчикам роутов не нужно вручную конструировать ошибочные `Response` на каждый случай — достаточно выбросить ошибку (`throw new NotFoundError(...)` или `throw new OrderValidationError(...)`), и сервер автоматически превратит её в корректный HTTP-ответ с нужным статус-кодом.

### Почему сервер отдаёт сырой URL строкой

Хотя `Bun` умеет автоматически извлекать параметры запроса, наша серверная заготовка **намеренно передаёт обработчику полный сырой URL строкой**.

Это сделано для того, чтобы в слое обработчиков ты применил свои собственные утилиты, созданные в первом проекте: `getQueryParams` и `parseUrl`. Архитектурно сервер остаётся чистым сетевым шлюзом, а прикладным разбором занимается слой приложения.

### Заготовка таблицы роутов: `server/route.js`

Файл `server/route.js` представляет собой реестр зарегистрированных путей:

```javascript
/**
 * Таблица маршрутизации приложения: путь -> обработчик.
 */
export const routes = {
  // В следующем уроке сюда будут подключены обработчики:
  // '/list': handleListOrders,
  // '/get': handleGetOrder,
  // '/create': handleCreateOrder,
  // '/update': handleUpdateOrder,
  // '/delete': handleDeleteOrder,
};
```

### Точка входа: `server/main.js`

Точка входа объединяет сетевой сервер и таблицу маршрутизации воедино:

```javascript
import { runServer } from './server.js';
import { routes } from './route.js';

runServer(routes, 3000);
```

Этот файл запускает веб-сервер с актуальными маршрутами. Как только ты зарегистрируешь обработчик в `server/route.js`, сервис можно сразу запустить командой `bun run server/main.js` и тестировать вживую.
