# Шаги урока: Рефакторинг слоя хранения: границы ответственности и сила тестов

### Архитектурный разбор: иллюзия чистых слоёв

**kind:** `text`

Поздравляем с завершением основного функционала! Ты поднял HTTP-сервер, реализовал полный CRUD-цикл и замёржил Pull Request. Сервер работает, все запросы проходят, а код разложен по аккуратным папкам.

Кажется, что решение идеальное. Но в программировании часто бывает так: код работает без сбоев, выглядит красиво, но внутри заложена архитектурная бомба замедленного действия. 

Давай вместе посмотрим на связку двух файлов: `infra/file-storage.js` и `app/repo/order-repo.js`.

Вспомни, как мы реализовали сохранение:
```javascript
// infra/file-storage.js
export function saveToFile(path, data) {
  const text = toCSV(data);
  writeFileSync(path, text, 'utf8');
}

export function loadFromFile(path) {
  const text = readFileSync(path, 'utf8');
  return fromCSV(text);
}
```

Это решение кажется лаконичным: всего две короткие функции, которые читают и записывают готовый массив. Но обрати внимание, к чему это привело в репозитории `app/repo/order-repo.js`:
- Чтобы найти один-единственный заказ по ID, репозиторий вынужден читать **весь файл целиком в оперативную память** и запускать поиск по массиву.
- Чтобы добавить один заказ, репозиторий сам вычисляет `Math.max` по всем идентификаторам, добавляет объект в массив и **перезаписывает весь файл на диске заново**.
- Чтобы удалить или обновить заказ — снова чтение всего файла, фильтрация или замена в памяти и полная перезапись диска.

В индустрии такая ситуация называется **протеканием абстракции (Leaky Abstraction)**.
Мы создали слой `infra`, но функции `loadFromFile` и `saveToFile` оказались слишком легковесными: они просто сбрасывают массив на диск. Из-за этого репозиторий вместо работы с заказами вынужден знать всю низкоуровневую механику хранения: что данные лежат в едином массиве, как организован обход элементов и как генерируются ключи.

Представь, что завтра проект вырос и вместо CSV-файла данные нужно хранить в базе данных (например, SQLite или PostgreSQL). Если слои чистые — мы просто меняем код инфраструктуры, а репозиторий остаётся нетронутым. Но при текущем подходе репозиторий придётся выбросить и переписать с нуля, потому что он намертво привязан к ручной обработке массива.

Наша цель — сделать хранилище полноценным **табличным хранилищем**, а репозиторий освободить от несвойственной ему работы.

### Архитектурная заготовка: фабрика и инкапсуляция

**kind:** `text`

Как должно выглядеть правильное хранилище? Оно должно вести себя как абстрактная таблица данных. Ему не важно, какие сущности в нём лежат (заказы, пользователи или товары). Оно предоставляет атомарные операции: найти запись, отфильтровать, добавить, обновить, удалить.

В будущем мы подробно разберём объектно-ориентированное программирование (ООП) и классы. Но организовать сокрытие внутренней кухни (инкапсуляцию) в JavaScript можно уже сейчас с помощью **функции-фабрики (Factory Function)** и **замыканий (Closures)**.

Идея простая: фабрика `createStorage(filePath, keyName = 'id')` принимает путь к файлу и имя ключевого поля (по умолчанию `'id'`), возвращая объект с методами доступа к данным.
А вспомогательные функции прямого чтения и записи прячутся внутри модуля и наружу не экспортируются.

Замени содержимое файла `infra/file-storage.js` на следующую архитектурную заготовку:

```javascript
import { existsSync, readFileSync, writeFileSync } from 'node:fs';
import { fromCSV } from '../../utils/business/from-csv.js';
import { toCSV } from '../../utils/business/to-csv.js';

// --- Внутренние функции (инкапсулированы внутри модуля) ---

function readAll(filePath) {
  if (!existsSync(filePath)) {
    return [];
  }
  const raw = readFileSync(filePath, 'utf8');
  if (!raw.trim()) {
    return [];
  }
  return fromCSV(raw);
}

function writeAll(filePath, rows) {
  const csv = toCSV(rows);
  writeFileSync(filePath, csv, 'utf8');
}

// --- Публичная фабрика хранилища ---

export function createStorage(filePath, keyName = 'id') {
  return {
    get(id) {
      // TODO: самостоятельная реализация
    },

    filter(partial) {
      // TODO: самостоятельная реализация
    },

    add(obj) {
      // TODO: самостоятельная реализация
    },

    update(id, partial) {
      // TODO: самостоятельная реализация
    },

    remove(id) {
      // TODO: самостоятельная реализация
    },
  };
}
```

Обрати внимание на архитектуру:
1. Функции `readAll` и `writeAll` не экспортируются (`export`). Никакой внешний код не сможет вызвать их напрямую. Вся работа с файловой системой надёжно скрыта.
2. Объект методов «помнит» переданные `filePath` и `keyName` благодаря механизму замыкания. Вызывающему коду больше не нужно передавать путь и имя ключа в каждый вызов метода.
3. Хранилище стало гибким: по умолчанию оно работает с полем `'id'`, но при необходимости мы можем передать любое имя ключа (например, `'uuid'` или `'sku'`).

### Техническое задание: контракты пяти методов

**kind:** `text`

Твоя задача — самостоятельно реализовать тело пяти методов объекта в `infra/file-storage.js`.

Готового кода мы не даём: ты уже умеешь работать с коллекциями, функциями и условиями. Твоя задача — строго реализовать требования инженерной спецификации.

#### Базовые системные правила:
1. **Универсальность:** хранилище ничего не знает о заказах (`Order`), суммах, статусах или клиентах. Оно работает с произвольными плоскими объектами.
2. **Контракт первичного ключа (`keyName`):**
   - Записи идентифицируются по свойству с именем `keyName`.
   - Местоположение ключа среди свойств объекта не имеет значения (но общепринято что он идет первым).

#### Спецификация методов:

1. **`get(id)`**:
   - Находит запись, у которой значение поля `[keyName]` совпадает с переданным `id`.
   - Если запись найдена — возвращает объект записи.
   - Если запись не найдена — возвращает `null`.

2. **`filter(partial)`**:
   - Принимает опциональный объект полей для фильтрации.
   - Если аргумент `partial` не передан или представляет собой пустой объект `{}` — возвращает копию массива всех сохранённых записей.
   - Если в `partial` переданы поля — возвращает только те записи, у которых каждое переданное свойство совпадает со свойством записи (проверка условий через логическое `И`, для `{ name: 'Anna', status: 'complete' }` должны вернуться только соответствующие обеим значениям записи).

3. **`add(obj)`**:
   - Принимает объект данных.
   - Вычисляет следующий номер идентификатора (автоинкремент: берётся максимальное числовое значение поля `[keyName]` среди существующих записей + 1, либо `1`).
   - Если в `obj` уже передано поле `[keyName]`, оно заменяется на сгенерированный идентификатор.
   - Формирует итоговый объект: `{ ...obj, [keyName]: nextId }`.
   - Сохраняет обновлённый массив на диск через `writeAll`.
   - Возвращает созданный объект.

4. **`update(id, partial)`**:
   - Ищет запись по полю `[keyName]`.
   - Если запись не найдена — возвращает `null` (диск при этом не перезаписывается).
   - Если найдена — объединяет исходные свойства с переданными `partial`, **гарантируя неизменность первичного ключа** (значение поля `[keyName]` нельзя перезаписать через update).
   - Перезаписывает файл на диске и возвращает обновлённый объект.

5. **`remove(id)`**:
   - Ищет запись по полю `[keyName]`.
   - Если запись не найдена — возвращает `null` (диск не трогается).
   - Если найдена — удаляет её из массива, перезаписывает файл на диске и возвращает `null`.

### Рефакторинг репозитория по TDD

**kind:** `text`

Теперь мы готовы перевести репозиторий заказов на работу с новым хранилищем.
Но как профессиональные инженеры, мы делаем рефакторинг по канонам **TDD (Test-Driven Development)**: **сначала адаптируем тесты, затем меняем реализацию**.

#### Шаг 1. Обновляем моки в `app/repo/order-repo.test.js`

Вспомни: в тестах репозитория мы строго изолируем его от реальной файловой системы с помощью `mock.module`. Раньше мы мокали две функции: `loadFromFile` и `saveToFile`. Теперь их нет: модуль `infra/file-storage.js` экспортирует фабрику `createStorage`.

Прежде чем трогать код репозитория, обнови мок модуля в тестах. Ты можешь пойти одним из двух архитектурных направлений:

1. **Мокирование методов объекта (Mock-объект):**
   `mock.module` подменяет фабрику так, чтобы вызов `createStorage()` возвращал объект с мок-функциями `mock()`. В тестах ты точечно задаёшь их поведение через `.mockReturnValue(...)`  и проверяешь вызовы: `expect(storageMock.get).toHaveBeenCalledWith(id)`.
2. **Фейковое хранилище в памяти (In-Memory Fake):**
   Развитие подхода из урока по репозиторию: внутри `mock.module` фабрика возвращает объект, методы которого оперируют простым массивом в памяти `let memoryRows = []`. В `beforeEach` массив очищается, а тесты проверяют изменение записей в памяти.

Когда ты обновишь мок в `order-repo.test.js` и запустишь `bun test app/repo/order-repo.test.js`, тесты **упадут (Red)**. Это нормально — старый код репозитория ещё пытается вызывать несуществующие `loadFromFile` и `saveToFile`.

#### Шаг 2. Обновляем реализацию в `app/repo/order-repo.js`

Теперь перепиши реализацию репозитория, чтобы тесты позеленели (**Green**):
1. Импортируй фабрику: `import { createStorage } from '../../infra/file-storage.js';`
2. Инициализируй экземпляр хранилища: `let storage = createStorage(ordersPath);`
3. Сохрани функцию `setOrdersPath(customPath)`: она остаётся важной точкой конфигурации репозитория для изоляции интеграционных тестов. **Важно:** не забудь внутри неё пересоздавать экземпляр хранилища под новый путь (`storage = createStorage(customPath)`).
4. Перепиши CRUD-функции доступа к заказам через методы `storage`: `getOrder` → `get`, `listOrders` → `filter`, `addOrder` → `add`, `updateOrder` → `update`, `deleteOrder` → `remove`.

Далее работа по циклу: тестовый случай -> RED -> GREEN -> рефакторинг.

Добейся чтобы все тесты репозиториев стали зелеными. После можно переходить к следующему шагу.

### Интеграционные тесты

**kind:** `text`

Как ты мог заметить, на каждом уровне мы тестировали в изоляции, это и называется unit-тестами. Хранилище (storage) тестировался с настоящими файлами. Но репозиторий мокал её. А обработчики мокали репозитории.

Обрати внимание: **сами обработчики (`app/handler/`) и их модульные тесты мы вообще не трогали!** Мы переписали хранилище и перелопатили внутренности репозитория, но внешний контракт функций репозитория (`getOrder`, `addOrder` и др.) остался неизменным. Слой обработчиков даже не заметил рефакторинга фундамента — в этом и заключается главная сила изолированных слоёв.

А теперь настало время интеграционного теста: именно он собирает всю связку воедино и проверяет реальную работу сервера с физическим диском.

Открой файл `server/server.integration.test.js` и посмотри на тестовый хелпер `addOrder`.
Вспомни, как он был написан раньше: он напрямую импортировал старые функции `loadFromFile` и `saveToFile`, вручную читал массив и считал ID через `Math.max`. Но этих функций больше не существует!

Теперь, благодаря фабрике хранилища, хелпер интеграционного теста становится невероятно компактным:
1. Замени старый импорт `saveToFile` / `loadFromFile` на `createStorage`.
2. Создай тестовое хранилище для файла теста.
3. Перепиши хелпер `addOrder(overrides = {})`! Фабрика сама позаботится о генерации идентификатора и сохранении данных в тестовый файл `TEST_FILE`.

Должно получиться что то подобное:
```js
  import { createStorage } from '../infra/file-storage.js';

  const testStorage = createStorage(TEST_FILE);

  function addOrder(overrides = {}) {
    return testStorage.add({
      customer: 'Анна',
      amount: 1500,
      isPaid: true,
      status: 'new',
      review: 'Тестовый заказ',
      ...overrides,
    });
  }
```

Запусти интеграционный тест сервера. Убедись, что сквозной сценарий работы сервера через реальные HTTP-запросы успешно проходит.

### Сила автоматических тестов: проверка всех слоёв

Мы провели глубокий архитектурный рефакторинг: переписали фундамент персистентности и изменили логику работы репозитория.

В проектах без тестов разработчики боятся таких изменений как огня: любая ошибка в нижнем слое может незаметно сломать обработчики, маршрутизацию или формат ответа сервера.
