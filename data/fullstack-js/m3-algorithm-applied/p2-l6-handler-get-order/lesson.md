# Первый обработчик: get-order, юнит- и интеграционные тесты

**Краткое содержание:**
Создаём слой сетевых обработчиков `app/handler/`. Разбираем концепцию тонкого обработчика-оркестратора на примере функции `handleGetOrder`: от бизнес-ТЗ до реализации и регистрации в роутере. Разбираем обработку ошибок: `OrderValidationError` превращается в `400`, отсутствие записи — в `404` (`NotFoundError`). Разбираем фундаментальную разницу между модульными (юнит), интеграционными и E2E-тестами. Пишем настоящий интеграционный тест: поднимаем тестовый HTTP-сервер на отдельном порту, отправляем реальные запросы через `fetch()`, вводим концепцию тестовых хелперов для явной подготовки состояния и настраиваем надёжную уборку (`cleanup`) в хуках `beforeEach` и `afterEach`.

**Время:** ~30 мин

**Основные темы:**
- Зона ответственности слоя `app/handler`: оркестратор входящего запроса
- Раскладка «один роут — один файл — один тест»
- Архитектурный контракт: обработчик возвращает JSON-строку, а не `Response`
- Бизнес-ТЗ и сценарии поведения системы: успешный поиск, 404 Not Found, 400 Bad Request
- Реализация `get-order.js` и модульное тестирование по TDD с моками
- Регистрация маршрута `/get` в `server/route.js`, запуск `main.js` и ручная проверка
- Пирамида тестирования: юнит-тесты (Unit), интеграционные (Integration) и сквозные (E2E)
- Подъём тестового сервера на отдельном порту и сетевые запросы через `fetch()`
- Тестовые хелперы: явная подготовка состояния теста вместо глобального `beforeEach`
- Главное правило интеграционного теста: реальная запись на диск без моков
- Подготовка и уборка тестового окружения: паттерн `beforeEach` + `afterEach`
- Термины урока

**Термины:**
* **Обработчик (Handler)** — функция, принимающая URL сетевого запроса, оркестрирующая валидацию и вызовы репозитория и возвращающая данные в виде JSON-строки.
* **Тонкий обработчик (Thin Controller / Handler)** — паттерн проектирования, при котором обработчик выполняет только распаковку запроса, делегирование нижележащим слоям и возврат данных в формате JSON без собственной инфраструктурной логики.
* **Модульный тест (Unit Test)** — проверка функции в полной изоляции с подменой внешних зависимостей моками.
* **Интеграционный тест (Integration Test)** — проверка совместной работы реальных слоёв приложения без моков (с физическим обращением к диску или сети).
* **E2E-тест (End-to-End Test, сквозной тест)** — проверка всей работающей системы целиком снаружи (через сеть или интерфейс) от точки входа до хранилища данных.
* **Тестовый хелпер (Test Helper)** — вспомогательная функция в тестах, создающая нужные данные или состояние с предсказуемыми значениями по умолчанию.
* **Уборка (Cleanup / Teardown)** — очистка временных данных и файлов до и после тестов (`beforeEach`, `afterEach`) для гарантии их детерминированности и независимости.

### Роль слоя обработчиков в слоистой архитектуре

Слой обработчиков (`app/handler/`) находится на стыке внешнего сетевого мира и внутренней бизнес-логики приложения:

```text
[ Сеть: Bun.serve (server.js) ]  ---> ловит URL, перехватывает исключения в JSON (400 / 404)
         ↓
[ app/handler/*.js ]             ← МЫ ЗДЕСЬ (оркестраторы)
    ├─> utils: разбирает query-параметры в объект
    ├─> entity: валидирует вход (validateId / createOrder)
    ├─> app/repo: сохраняет и возвращает данные
    └─> бросает NotFoundError при отсутствии записи в репозитории
         ↓
[ JSON-строка: JSON.stringify(...) ]   <--- обработчик отдаёт серверу чистый JSON!
         ↓
[ HTTP Response (200 OK) ]             <--- сервер оборачивает в Response с заголовками
```

Каждый обработчик решает свои задачи по чёткому конвейерному принципу:
1. **Разобрать:** извлечь параметры из URL с помощью утилиты `getQueryParams`.
2. **Провалидировать:** проверить входные данные (`validateId` для роутов с идентификатором, фабрика `createOrder` для создания и обновления). Если данные некорректны — выбрасывается `OrderValidationError`, который сервер централизованно упакует в `400 Bad Request`.
3. **Вызвать репозиторий:** передать чистые данные или `id` в соответствующий метод репозитория (`listOrders`, `getOrder`, `addOrder`, `updateOrder`, `deleteOrder`).
4. **Обработать результат:** если репозиторий вернул `null` (запись не найдена) — бросить исключение `NotFoundError`. Сервер перехватит его и вернёт клиенту `404 Not Found` с JSON `{ error: error.message }`.
5. **Вернуть результат при успехе:** сериализовать данные в строку JSON: `return JSON.stringify(result)`.

> **Важное архитектурное правило:** обработчик **не создаёт объект `Response`**. Использование `Response` внутри слоя обработчиков было бы утечкой деталей сетевого протокола в приложение. Обработчик обязан вернуть чистую JSON-строку, а сервер в `server/server.js` сам упакует её в `new Response(result, { status: 200, headers: ... })`.

### Валидация на входе: роль обработчика

Обработчик — это рубеж между ненадёжным внешним миром (сетью) и внутренними слоями приложения:
- Именно обработчик знает, какие параметры ожидает конкретный роут: `/get` требует валидный `id`, `/create` требует поля заказа.
- Обработчик не перегружает себя ручными проверками: он делегирует проверку `id` функции `validateId`, а проверку и сборку заказа — фабрике `createOrder`.
- Репозиторий освобождён от валидации: он является чистым хранилищем данных.

### Почему обработчик остаётся лаконичным

Несмотря на то что обработчик оркестрирует валидацию и сохранение, его код остаётся компактным (буквально 4–6 строк):
- Разбор параметров вынесен в `getQueryParams`.
- Проверка и сборка заказа вынесены в `createOrder`.
- Сохранение и работа с файлом вынесены в `repo`.
- Перехват ошибок валидации в `400 JSON` вынесен на уровень сервера `server.js`.

В результате каждый обработчик легко читать и тестировать изолированно.

### Как результат репозитория превращается в HTTP-ответ

1. **Репозиторий вернул валидный заказ или массив:**
   Обработчик возвращает строку `JSON.stringify(data)` → сервер формирует ответ `200 OK` с этим JSON.
2. **Репозиторий вернул `null` (для `get`, `update`, `delete`):**
   Обработчик бросает `throw new NotFoundError('Заказ не найден')` → сервер формирует ответ `404 Not Found` с телом `{ "error": "Заказ не найден" }`.
3. **Клиент передал некорректные параметры:**
   Валидатор или фабрика бросает `OrderValidationError` → сервер формирует ответ `400 Bad Request` с телом `{ "error": "<текст ошибки>" }`.

### Спецификация пяти роутов сервиса

1. **`/list`** (`list-orders.js`):
   - **Назначение:** список всех заказов.
   - **Успешный ответ:** `200 OK`, JSON-массив валидных заказов `[]`.

2. **`/get?id=...`** (`get-order.js`):
   - **Назначение:** найти заказ по `id`.
   - **Успешный ответ:** `200 OK`, JSON-объект найденного заказа.
   - **Ошибки:** `400 Bad Request` (невалидный `id`), `404 Not Found` (заказ не найден).

3. **`/create?...`** (`create-order.js`):
   - **Назначение:** создать новый заказ из параметров запроса.
   - **Успешный ответ:** `200 OK`, JSON-объект созданного заказа с назначенным `id`.
   - **Ошибки:** `400 Bad Request` (нарушено доменное правило или отсутствует обязательное поле).

4. **`/update?id=...`** (`update-order.js`):
   - **Назначение:** обновить существующий заказ.
   - **Успешный ответ:** `200 OK`, JSON-объект обновлённого заказа.
   - **Ошибки:** `400 Bad Request` (невалидный `id` или поля), `404 Not Found` (заказ не найден).

5. **`/delete?id=...`** (`delete-order.js`):
   - **Назначение:** удалить заказ из базы по `id`.
   - **Успешный ответ:** `200 OK`, JSON-объект удалённого заказа.
   - **Ошибки:** `400 Bad Request` (невалидный `id`), `404 Not Found` (заказ не найден).

В теле любой ошибки всегда возвращается понятный JSON: `{ "error": "Текст ошибки" }`.

### Подключение в таблицу `server/route.js`

Созданный обработчик импортируется в файл `server/route.js`:

```javascript
import { handleGetOrder } from '../app/handler/get-order.js';

export const routes = {
  '/get': handleGetOrder,
};
```

Теперь любой запрос к `/get` попадает в наш обработчик!

### Инженерный цикл разработки: от ТЗ до ручной проверки

Разработка ручки строится по законченному инженерному циклу:
1. **ТЗ и критерии приёмки:** формулируем бизнес-задачу, сценарии (успех, 404 при отсутствии, 400 при некорректном входе) и инженерный контракт.
2. **Модульный тест (TDD):** изолируем обработчик от внешнего мира через мок репозитория (`mock.module`) и реализуем функцию.
3. **Регистрация в `server/route.js`:** подключаем готовую функцию к таблице роутов.
4. **Запуск и ручная проверка:** запускаем `bun run server/main.js` и проверяем реальный HTTP-ответ через `curl` или консоль браузера.

### Пирамида тестирования: какие бывают виды тестов

После того как юнит-тесты подтвердили корректность логики обработчика, а ручной запуск показал работу сервера, встаёт инженерный вопрос: **как правильно тестировать систему комплексно?**

В индустрии тесты делят на три основных уровня — так называемую «пирамиду тестирования»:

```text
       / \
      /   \      E2E-тесты (сквозные) — верхушка пирамиды
     / E2E \     (самые дорогие, медленные, проверяют всю систему целиком)
    /───────\
   /         \   Интеграционные тесты — средний уровень
  / Интеграц. \  (проверяют связку компонентов без моков с реальным I/O)
 /─────────────\
/               \  Юнит-тесты (модульные) — широкое основание пирамиды
/   Юнит-тесты   \ (самые быстрые, изолированные, проверяют одну функцию в памяти)
/─────────────────\
```

#### 1. Юнит-тесты (модульные тесты)
- **Что проверяют:** отдельную функцию, метод или класс в полной изоляции.
- **Когда используют:** бизнес-логика, валидация (`validateId`), алгоритмы, чистые функции, разработка по TDD.
- **Главные правила:**
  - полная изоляция: все внешние зависимости подменяются моками (`mock`, `spyOn`, `mock.module`);
  - мгновенная скорость: выполняются в памяти за доли секунды;
  - детерминированность: всегда дают одинаковый результат;
  - точная локализация ошибки: сразу указывают на конкретную строку кода.
- **Слепая зона:** юнит-тесты не знают, как модули стыкуются в реальности. Если мок возвращает число, а реальный репозиторий отдаёт строку или `null`, юнит-тест будет зелёным, а система упадёт.

#### 2. Интеграционные тесты
- **Что проверяют:** совместную работу нескольких реальных компонентов приложения.
- **Когда используют:** проверка связки слоёв (обработчик → репозиторий → запись в CSV), реальные дисковые и сетевые операции ввода-вывода.
- **Главные правила:**
  - **здесь ничего не мокается:** вызывается реальный модуль, который физически пишет и читает реальный файл на диске;
  - изоляция и безопасность: тесты запускаются в выделенной тестовой песочнице, чтобы не затронуть рабочие данные;
  - поиск стыковочных багов: выявляют несовпадения форматов, некорректные заголовки и проблемы файловых путей.

#### 3. E2E-тесты (End-to-End, сквозные тесты)
- **Что проверяют:** всю систему целиком «из конца в конец» — от сетевого запроса снаружи до диска и сетевого ответа обратно.
- **Когда используют:** критические пользовательские сценарии (Happy Path), приёмочное и регрессионное тестирование перед релизом.
- **Главные правила:**
  - подход «чёрного ящика» (Black Box): тест знает только URL и ожидает ответ, не зная деталей реализации;
  - поднимается полноценный живой веб-сервер на локальном сетевом порту;
  - самые ресурсоёмкие и медленные тесты в пирамиде.
- **Роль в нашем проекте:** в рамках курса мы **не будем автоматизировать E2E-тесты в коде**, чтобы не перегружать кодовую базу инструментами управления фоновыми процессами. Роль E2E-проверки мы выполняем своими руками через `curl`, адресную строку браузера и DevTools Console. Но понимать их место в архитектуре тестирования обязан каждый разработчик.

### Интеграционный тест для handleGetOrder: сервер, хелперы и уборка

В интеграционном тесте `server/server.integration.test.js` мы проверяем полный сквозной путь сервиса рядом с сервером:
1. **Поднимаем реальный HTTP-сервер:** в хуке `beforeAll` перенаправляем репозиторий на тестовый файл через `setOrdersPath(TEST_FILE)` и запускаем `runServer(routes, 3099)` на отдельном тестовом порту, а в `afterAll` возвращаем путь назад и надёжно гасим сервер через `server.stop(true)`.
2. **Отправляем реальные запросы:** тесты вызывают `fetch('http://localhost:3099/get?id=...')`, проверяя реальные HTTP-статусы `200`, `404` и `400`.
3. **Изолируем тестовые данные:** запрос проходит через сервер, роутер, обработчик и репозиторий в изолированный тестовый файл `test-orders.csv`. Настоящая рабочая база `data/orders.csv` остаётся нетронутой.

#### Концепция тестовых хелперов
Не стоит зашивать создание сущностей в хук `beforeEach`:
- Это связывает тесты скрытой зависимостью и делает их код «слепым» (непонятно, откуда взялся заказ и какие у него свойства).
- Нарушается структура **Arrange-Act-Assert**: тест должен сам явно объявлять своё исходное состояние.

Вместо этого мы пишем функцию-хелпер `addOrder(overrides)`, которая создаёт заказ с разумными значениями по умолчанию. Каждый тест вызывает хелпер только тогда, когда ему действительно нужны данные:
- тест на успешный поиск вызывает `addOrder(...)` и затем запрашивает полученный `id`;
- тест на 404 оставляет базу пустой и сразу шлёт запрос с несуществующим `id`;
- тест на 400 шлёт невалидный запрос без предварительного создания данных.

#### Культура уборки окружения
Хуки `beforeEach` и `afterEach` освобождаются от создания данных и отвечают строго за **чистоту окружения**:
- **Золотое правило: чисти и ДО, и ПОСЛЕ.**
- `afterEach` удаляет временный CSV-файл после каждого теста, оставляя файловую систему чистой.
- `beforeEach` записывает чистый файл только с заголовками колонок — это гарантирует чистую песочницу, даже если предыдущий тест упал с ошибкой или был прерван сочетанием клавиш `Ctrl+C`.
