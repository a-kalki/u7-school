### Слой обработчиков

**kind:** `text`

Мы начнем создавать обработчиков. Их у нас 5: `get-order`, `list-orders`, `create-order`, `update-order`, `delete-order`.

Создай каталог `app/handler/` внутри папки проекта `m2-m3-algorithms/m3-p2-http/`.

Каждый обработчик:
- принимает строковый `requestUrl`;
- является оркестратором, выполняет поставленную перед ним задачу.
- возвращает сериализованный результат в виде **строки JSON** (`JSON.stringify`);

**Что импортирует обработчик:**
- разбор параметров — `getQueryParams` из `utils/business/get-query-params.js`;
- функции репозитория (`listOrders`, `getOrder`, `addOrder`, `updateOrder`, `deleteOrder`) из `../repo/order-repo.js`;
- функции валидации — `validateId` из `../entity/validator.js` и фабрику `createOrder` из `../entity/order.js`;
- класс ошибки `NotFoundError` из `./errors.js`.

Когда запрашивается заказ которого нет в БД (база данных), то обработчик выкинет исключение `NotFoundError`, а уровень сервера поймает ее и вернет стандартный ответ `404`. Значит нам нужно создать объект ошибки для этого случая.

Создай вспомогательный файл `app/handler/errors.js`:
```javascript
export class NotFoundError extends Error {
  constructor(message = 'Объект не найден') {
    super(message);
    this.name = 'NotFoundError';
  }
}
```

### Вводные в разработку обработчика

**kind:** `text`

**Обязанности обработчика**

Каждый обработчик работает по одному и тому же конвейеру:
- разобрать параметры запроса, получить входные данные;
- провалидировать входные данные;
- получить данные из репозитория;
- выкинуть исключение, если данных нет (`NotFoundError`);
- сохранить данные в репозитории;
- вернуть успешный ответ в виде строки JSON (`JSON.stringify`).

**Шаги реализации**

Прежде чем браться за все пять обработчиков, пройдём один обработчик через **полный инженерный цикл разработки**:
1. **Техническое задание:** чётко определим вход, выход и критерии приёмки.
2. **Организация теста (TDD):** напишем модульный тест с моком репозитория и реализуем логику.
3. **Регистрация маршрута:** подключим функцию в `server/route.js`.
4. **Запуск и ручное тестирование:** запустим `server/main.js` и проверим вручную.

После этого примера ты реализуешь оставшиеся четыре обработчика по этой же отработанной схеме.

**Инженерный контракт: `handleGetOrder(requestUrl)`**

- **Выход:** строка JSON с данными заказа.
- **Критерии приёмки:**

  - Кидает исключение `NotFoundError`, если заказ не найден в БД;

### Виды тестов: от юнитов до E2E

**kind:** `text`

В автоматизированном тестировании существует устоявшаяся классификация тестов — так называемая «пирамида тестирования». Она делит проверки на три основных уровня по степени изоляции, скорости выполнения и приближенности к реальной среде:
- **Юнит-тесты (модульные тесты):** проверка отдельных небольших функций или классов в полной изоляции с моками. Их в проекте больше всего (основание пирамиды).
- **Интеграционные тесты:** проверка связки нескольких реальных модулей между собой (например, обработчик + репозиторий + файловая система). Средний уровень пирамиды.
- **E2E-тесты (End-to-End, сквозные тесты):** проверка всей работающей системы целиком глазами пользователя или внешнего клиента через сеть. Верхушка пирамиды. В данном проекте мы их реализовывать не будем.

Давай разберём каждый вид подробно: зачем он нужен, когда его применяют и каких правил придерживаются.

---

### Юнит-тесты (модульные тесты)

**kind:** `text`

**Что это:**
Юнит-тест (unit test) проверяет минимальную логическую единицу кода (функцию, метод или класс) в отрыве от остального приложения.

**Когда используют:**
- При разработке бизнес-логики, алгоритмов и чистых функций (валидаторы `validateId`, расчёт сумм, разбор query-параметров в `getQueryParams`).
- Для быстрой проверки крайних случаев, пограничных условий и веток ошибок (`if/else`, исключения).
- В практике TDD (Test-Driven Development), когда тест пишется до реализации функции.

**Главные правила юнит-тестов:**
- **Полная изоляция:** тестируемый модуль не должен ходить в сеть, базу данных или на реальный диск. Все внешние зависимости подменяются моками (`mock`, `spyOn`, `mock.module`).
- **Мгновенная скорость:** сотни и тысячи юнит-тестов должны выполняться за доли секунды прямо в оперативной памяти.
- **Детерминированность:** тест даёт строго одинаковый результат при каждом запуске независимо от внешнего окружения.
- **Точная локализация ошибки:** если юнит-тест падает, мы сразу знаем конкретную строку и функцию, где сломалась логика.

**Слабое место (слепая зона):**
Юнит-тесты не знают, как модули стыкуются друг с другом в реальности. Если мок в тесте возвращает число, а реальный репозиторий в тех же условиях возвращает строку или `null`, юнит-тест останется зелёным, а боевой сервис упадёт.

### Интеграционные тесты

**kind:** `text`

**Что это:**
Интеграционный тест (integration test) проверяет, как несколько настоящих компонентов системы работают вместе как единое целое.

**Когда используют:**
- При проверке взаимодействия слоёв (обработчик → репозиторий → сохранение данных в файл).
- Для проверки реальных операций ввода-вывода (чтение и запись файлов, запросы к базе данных).
- Когда нужно убедиться, что контракты между модулями согласованы и форматы данных совпадают на стыках.

**Главные правила интеграционных тестов:**
- **Никаких моков для проверяемой связки:** мы намеренно не используем заглушки чтобы проверить реальное взаимодействие частей системы.
- **Подготовка и уборка окружения:** тест обязан создать для себя тестовые данные перед запуском и аккуратно убрать за собой после завершения.
- **Изоляция окружения:** тесты должны работать в выделенной тестовой папке или файле, чтобы не повредить боевые данные.
- **Поиск стыковочных багов:** интеграционный тест ловит ошибки несовместимости типов, некорректные заголовки CSV, проблемы с правами доступа и блокировки файлов.

---

### E2E-тесты (сквозные тесты)

**kind:** `text`

**Что это:**
E2E-тест (End-to-End, «из конца в конец») запускает всю систему целиком — реальный сервер, роутер, обработчики, базу данных. Стараются делать последовательность действий так, как это делает конечный пользователь.

**Когда используют:**
- Для проверки ключевых пользовательских сценариев (Happy Path): регистрация пользователя, оформление и оплата заказа, выгрузка отчёта.
- Перед релизом (регрессионное тестирование), чтобы убедиться, что весь собранный сервис запускается и корректно отвечает на сетевые запросы.

**Главные правила E2E-тестов:**
- **Взгляд с ракурса пользователя:** тест ничего не знает про внутренние функции и файлы проекта. Он знает только то, что видит пользователь и делает то что может делать пользователь.
- **Полное боевое окружение:** поднимается настоящий веб-сервер на локальном сетевом порту и настоящая БД (но тестовая).
- **Самые медленные и дорогие:** E2E-тесты требуют времени на запуск серверов, сетевое ожидание и работу с хранилищем. Их пишут значительно меньше, чем юнит-тестов (верхушка пирамиды).

В рамках нашего проекта, у нас нет фронтенда, поэтому у нас не будет `e2e` тестов.

### Интеграционный тест для handleGetOrder

**kind:** `text`

Теперь применим теорию на практике и напишем настоящий интеграционный тест для ручки `/get`.

Важное отличие интеграционного теста от модульного:
- unit: тестирует всевозможные сценарии выполнения тестируемой функции. Для одной функции мы пишем много тестов;
- integration: тестирует связанность объектов, обычно хватает одного тестового случая чтобы проверить всю цепочку взаимодействия функции;

Технические различия от юнит-теста `get-order.test.js`:
- мы **не мокаем** репозиторий и файловую систему;
- мы поднимаем **настоящий HTTP-сервер** с нашей таблицей роутов `routes` на отдельном тестовом порту (например, `3099`);
- отправляем в него настоящие сетевые запросы через стандартный `fetch()`;
- проверяем реальные HTTP-статусы (`200`, `404`, `400`), заголовки и тело JSON;
- данные физически сохраняются и читаются из тестового файла `./test-orders.csv`.

**Понятие тестовых хелперов**

Можно было бы в `beforeEach` написать функционал который создает начальное состояние БД, например:

```js
const initialOrders = [{ ... }]; // начальные значения в БД
beforeEach(() => { saveToFile('test-file.csv', initialOrders) });
```

Это гарантировало бы что в каждом тесте у нас будет некое начальное состояние БД. Но это имеет минусы:
1. **Потеря наглядности (явности):** глядя на тест, непонятно, откуда взялся объект с `id=1` и именем `'Anna'`. Приходится листать файл вверх к хукам.
2. **Неявная связанность:** все тесты делят общее состояние. Если изменить данные в `beforeEach` под один тест, могут случайно упасть пять соседних.
3. **Нарушение паттерна Arrange-Act-Assert:** тест перестаёт быть цельной историей.

> **Паттерн Arrange-Act-Assert**:
>   - Arrange: этап подготовки;
>   - Act: процесс выполнения проверяемой логики;
>   - Assert: верификация полученного результата;

Вместо этого предлагаем использовать паттерн **тестовые хелперы** — небольшие вспомогательные функции, которые берут на себя рутину подготовки данных с разумными значениями по умолчанию. При этом **каждый тест сам явно создаёт то состояние, которое нужно именно ему**:
- тесту на поиск заказа нужно создать один заказ перед вызовом `fetch`;
- тесту на отсутствие заказа не нужно создавать ничего (база должна быть пустой);
- хуки `beforeEach` и `afterEach` занимаются **только чисткой окружения**, а не заполнением данных.

**Заготовка теста: `server/server.integration.test.js`**

```javascript
import { describe, test, expect, beforeAll, afterAll, beforeEach, afterEach } from 'bun:test';
import { existsSync, unlinkSync } from 'node:fs';
import { resolve } from 'node:path';
import { runServer } from './server.js';
import { routes } from './route.js';
import { getOrdersPath, setOrdersPath } from '../app/repo/order-repo.js';
import { saveToFile, loadFromFile } from '../infra/file-storage.js';

const TEST_PORT = 3099;
const BASE_URL = `http://localhost:${TEST_PORT}`;
const TEST_FILE = resolve(import.meta.dirname, './test-orders.csv');

const OLD_DB_PATH = getOrdersPath();

// Тестовый хелпер: подготавливает нужный заказ в хранилище с дефолтными значениями
function addOrder(overrides = {}) {
  const orders = existsSync(TEST_FILE) ? loadFromFile(TEST_FILE) : [];
  const nextId = orders.length > 0 ? Math.max(...orders.map((o) => Number(o.id))) + 1 : 1;

  const newOrder = {
    id: nextId,
    customer: 'Анна',
    amount: 1500,
    isPaid: true,
    status: 'new',
    comment: 'Тестовый заказ',
    ...overrides,
  };

  orders.push(newOrder);
  saveToFile(TEST_FILE, orders);
  return newOrder;
}

describe('Интеграционный тест: сервер + роутер + get-order', () => {
  let server;

  // 1. Перенаправляем репозиторий на тестовый файл и поднимаем сервер
  beforeAll(() => {
    setOrdersPath(TEST_FILE);
    server = runServer(routes, TEST_PORT);
  });

  // 2. Гарантированно останавливаем сервер после завершения всех тестов и возвращаем путь
  afterAll(() => {
    setOrdersPath(OLD_DB_PATH);
    server.stop(true);
  });

  // 3. После каждого теста удаляем файл, чтобы не мусорить на диске
  afterEach(() => {
    if (existsSync(TEST_FILE)) {
      unlinkSync(TEST_FILE);
    }
  });

  test('get-order: возвращает заказ по ID', async () => {
    // Arrange: тест сам создаёт состояние, нужное именно ему
    const created = addOrder({ customer: 'Иван', amount: 2500 });

    // Act: реальный сетевой HTTP-запрос к работающему серверу
    const response = await fetch(`${BASE_URL}/get?id=${created.id}`);

    // Assert: проверяем статус ответа и тело
    const expected = {
      id: 1,
      customer: 'Иван',
      amount: 2500,
      isPaid: true,
      status: 'new',
      comment: 'Тестовый заказ',
    };

    expect(response.status).toBe(200);
    const result = await response.json();
    expect(result).toEqual(expected);
  });
});
```

> Можно заметить магические операторы `async`, `await`. Это ассинхронные вызовы, будем изучать их в этапе "Продвинутый JS". Пока просто используйте их так как приведено.

**Подсказки по уборке (cleanup): как и где её делать правильно**
1. **Детерминированность:** тесты должны выполняться независимо друг от друга в любом порядке и давать один и тот же результат.
2. **Где делать уборку:** используй стандартные хуки тестового фреймворка — `beforeEach` и `afterEach`.
3. **Золотое правило: делай уборку ДО ИЛИ ПОСЛЕ каждого теста.**
   - `afterEach` — удаляет временный файл сразу после штатного завершения теста.
   - `beforeEach` — можно добавить пустой массив, он создаст файл с пустыми данными. Теоретически улучшает тесты при нештатных ситуациях.

Запусти интеграционный тест:
```bash
bun test server
```

### Термины урока

**kind:** `text`

Пройдись по понятиям урока.

**Термины:**
* **Обработчик (Handler)** — функция слоя приложения, которая оркестрирует валидацию параметров и вызовы репозитория, возвращая клиенту сериализованную JSON-строку.
* **Модульный тест (Unit Test)** — тест, проверяющий отдельную функцию в полной изоляции с подменой внешних зависимостей моками.
* **Интеграционный тест (Integration Test)** — тест, проверяющий совместную работу нескольких реальных слоёв системы без моков (с реальной записью на диск или в сеть).
* **E2E-тест (End-to-End Test, сквозной тест)** — проверка всей работающей системы целиком снаружи (через сеть или интерфейс) от точки входа до хранилища данных.
* **Тестовый хелпер (Test Helper)** — вспомогательная функция в тестах, создающая нужные данные или состояние с предсказуемыми значениями по умолчанию.
* **Уборка (Cleanup / Teardown)** — процедура очистки временных файлов и восстановления исходного состояния окружения (в хуках `beforeEach` и `afterEach`), обеспечивающая независимость тестов.
