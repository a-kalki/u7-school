# Первый обработчик: get-order, юнит- и интеграционные тесты — краткая выжимка

- Слой `app/handler/` — оркестраторы запросов: принимают сырой URL, разбирают параметры через `getQueryParams`, валидируют входы (`validateId` и фабрика `createOrder`), вызывают методы репозитория `app/repo/order-repo.js` и возвращают результат в виде JSON-строки (`JSON.stringify`). Они не используют объект `Response`, исключая утечку деталей сетевого транспорта в слой приложения.
- Разработан первый обработчик `handleGetOrder` в `app/handler/get-order.js` по полному инженерному циклу: бизнес-ТЗ → сценарии → модульный тест с моками → реализация.
- Вспомогательный класс `NotFoundError` в `app/handler/errors.js` сигнализирует об отсутствии записи, а сервер централизованно превращает его в `404 Not Found`.
- Маршрут зарегистрирован в `server/route.js`, запущен сервер `server/main.js` и проверен вручную.
- Разобрана пирамида тестирования и фундаментальные различия трёх уровней:
  - юнит-тесты изолируют функцию с моками, мгновенны, но имеют «слепую зону» на стыке компонентов;
  - интеграционные тесты проверяют реальную связку компонентов без моков с сетевым сервером и изолированным тестовым файлом (через `setOrdersPath`);
  - E2E-тесты проверяют систему целиком «из конца в конец» через внешний интерфейс (в данном проекте мы выполняем их роль вручную через curl/браузер, а не кодом).
- Написан полноценный интеграционный тест `server/server.integration.test.js` рядом с сервером:
  - в `beforeAll` / `afterAll` переключается путь через `setOrdersPath`, запускается и останавливается реальный тестовый HTTP-сервер на отдельном порту;
  - реальные запросы отправляются через `fetch()`, проверяются коды 200, 404, 400;
  - введён паттерн тестового хелпера `addOrder`: каждый тест явно формирует нужное ему состояние (Arrange-Act-Assert);
  - хуки `beforeEach` и `afterEach` отвечают строго за чистоту окружения (`cleanup`).
- В следующем уроке самостоятельно реализуем оставшиеся четыре обработчика CRUD по бизнес-ТЗ.
