# Шаги урока: Твой PR глазами ревьюера

---

### Посмотри на свой PR со стороны

**kind:** `text`

Открой свой PR из проекта 3 и пройди по нему так, как это сделает ревьюер:

1. **Заголовок и описание.** Понятно без контекста, что сделано и как проверить? Можно ли запустить тесты, следуя описанию?
2. **Вкладка Commits.** История коммитов: осмысленные сообщения, логичная последовательность? Или «fix», «wip», «правки»?
3. **Вкладка Files changed.** Пролистай diff: имена переменных понятны? Нет ли закомментированного мёртвого кода, отладочных `console.log`?
4. **Тесты.** Открой пару тестовых файлов: описания тестов читаются как спецификация? Покрыты граничные случаи?

Ревьюер увидит всё это за первые две минуты — и от его первого впечатления зависит качество ревью.

**Термины:**
самопроверка — по англ. `self-review`: ревью своего PR до отправки другим;
мёртвый код — код, который никогда не выполнится;
отладочный вывод — забытые `console.log` из процесса отладки

### Чек-лист самопроверки

**kind:** `text`

Пройди по списку — если что-то не так, исправь сейчас (правки в ветку `feat/string-comparison` + коммит + push, PR обновится сам):

- [ ] Описание PR: что сделано + как запустить тесты (если нужно)
- [ ] Нет коммитов-мусора («fix», «правки», «123»)
- [ ] Нет отладочных `console.log` в реализациях
- [ ] Имена переменных и функций понятны
- [ ] Тесты запускаются, покрывают граничные случаи (пустые строки, пробелы, кириллица, `TypeError`)
- [ ] Правила модуля соблюдены (нет запрещённых методов и `.length`)
- [ ] Сообщение в чате живо, ссылка работает

Зачем это нужно: типичные замечания ревьюеры делают именно по этим пунктам. Самопроверка — это скорость ревью: чем чище PR приходит, тем меньше кругов доработки.
