# Шаги урока: Правила ревью

---

### Тон комментариев: предложение vs критическое

**kind:** `text`

У каждого комментария ревьюера должен быть понятный автору «вес». У нас два типа:

🟢 **Предложение** — «Предлагаю...», «Можно...». Автор сам решает, принимать или нет.

```
Предлагаю переименовать переменную code1 в charCodeA,
потому что текущее имя не говорит, чей это код.
```

🔴 **Критическое замечание** — «Нужно...», «Необходимо...». Обязательно к исправлению.

```
Нужно добавить проверку на длину строк, потому что
сейчас функция упадёт с ошибкой на строках разной длины.
```

Формула всегда одна: **действие + потому что**. Комментарий без объяснения («плохое имя») бесполезен — автор либо не поймёт, либо не согласится.

**Термины:**
предложение — по англ. `suggestion`: 🟢 «Предлагаю/Можно...» — автор сам решает, принимать ли;
критическое замечание — 🔴 «Нужно...» — обязательно к исправлению, блокирует мерж;
Approve — одобрение: ревьюер считает изменения готовыми;
Request changes — запрос изменений: ревьюер нашёл проблему;
Comment — комментарий без вердикта

---

### Итог ревью: Approve vs Request changes

**kind:** `text`

Завершая ревью, ревьюер выбирает итог:

- Только предложения → **Approve** ✅ (PR можно принимать)
- Есть критические замечания → **Request changes** ❌ (PR блокируется до исправления)
- **Comment** — середина: оставил комментарии, но ни approves, ни блокировки

Request changes — это не приговор и не «твой код плохой». Это честное «я нашёл проблему, исправь — и получишь мой апрув». Хорошие команды ревьюят именно так: строго к коду, доброжелательно к человеку.

### Памятка: что проверяем

**kind:** `text`

Сохрани себе памятку — она понадобится в этом же проекте, когда будешь ревьюить чужой homework-PR, и во всех следующих проектах с кодом.

**Что проверяем в коде:**
1. Корректность — правильно ли работает?
2. Граничные случаи — пустые строки, `undefined`, отрицательные числа
3. Правила модуля — нет ли запрещённых методов?
4. Читаемость — понятны ли имена?
5. Тесты — покрыты ли основные и граничные случаи?

**Что проверяем в текстовых PR (как homework.md):**
1. Полнота — все ли разделы заполнены?
2. Структура — заголовки по уровням, списки там, где перечисления?
3. Markdown — чекбоксы и форматирование отрисовываются?
4. Читаемость — абзацы не «простыни», нет опечаток

**Правило курса:** для мержа нужно одобрение **двух** ревьюеров.
