# Шаги урока: Повторное ревью и апрувы

---

### Запроси повторное ревью

**kind:** `text`

Когда все правки внесены и на все комментарии отвечено:

1. В правой панели PR найди ревьюеров
2. Рядом с именем каждого — иконка «повторного запроса» (две стрелки по кругу)
3. Нажми её для каждого ревьюера, кто оставлял замечания

Также можешь написать в чате:

```
Правки по ревью внесены, жду повторной проверки 🙏
```

**Термины:**
круг ревью — один проход «замечания → правки → повторная проверка»;
re-request review — запрос повторного ревью (иконка 🔄)

---

### Жди повторного прохода: 2 апрува — зелёный свет

**kind:** `text`

Как это работает:

- Ревьюер открывает PR снова и смотрит **исправленные места** (diff с прошлого ревью)
- Если всё ок — ставит **Approve**. Если нашёл новое — снова Request changes, и цикл повторяется (это нормально, 2–3 круга — обычное дело)
- Новые коммиты в ветку автоматически попадают в открытый PR — новый PR создавать не нужно

**Цель: 2 апрува и все conversations resolved.** Как только это есть — переходи к следующему уроку и делай мерж.

Если ревьюер пропал — алгоритм эскалации из урока 5 проекта 2: вежливое напоминание через 1–2 дня → пинг в чате → другой ревьюер (2 апрува не обязательно от одних и тех же людей) → крайний случай ментор.

### Пока ждёшь апрувов: статьи о парном программировании (на выбор)

**kind:** `text`

Пока твой PR находится на повторной проверке, есть время познакомиться с альтернативным подходом к код-ревью.

В реальной разработке ревью бывает не только **асинхронным** (через PR и ожидание комментариев), но и **синхронным в реальном времени**. Это называется **парным программированием** (pair programming): два инженера работают за одной задачей вместе, непрерывно обсуждая решения и проверяя код на лету.

Выбери одну из статей (или прочитай обе) — они помогут взглянуть на совместную разработку шире:

1. **[Парное программирование: стили, организация, тайм-менеджмент](https://habr.com/ru/companies/barsgroup/articles/533630/)** (перевод статьи с сайта Мартина Фаулера).

Мартин Фаулер (Martin Fowler) — всемирно признанный эксперт в сообществе программистов, соавтор Agile-манифеста и автор классических книг по разработке и архитектуре («Рефакторинг», «Архитектура корпоративных программных приложений»).

В статье подробно разбираются практические стили работы в паре:
- классический «Водитель и штурман» (Driver & Navigator);
- стиль «Пинг-понг» (особенно органичен для TDD: один пишет падающий тест, второй реализует код);
- стиль «Сильный — начинающий» (Strong-Style);
- организация удалённой работы и тайм-менеджмент сессий (техника Pomodoro).

2. **[О плюсах парного программирования](https://habr.com/ru/companies/raiffeisenbank/articles/530934/)** (статья из блога Райффайзен Банка).

Взгляд на практику из боевой разработки крупного финтеха. Автор через метафору ралли (где пилот управляет машиной, а штурман держит карту трассы) разбирает, зачем команды идут на парный кодинг:
- ускоренный онбординг новичков и передача контекста проекта;
- ликвидация «башни знаний» (bus factor) — устранение незаменимости отдельных людей;
- совместное решение сложных архитектурных и кросс-функциональных задач;
- честный баланс: почему замедление в моменте окупается снижением багов и экономией на последующих кругах ревью.

Изучи любую или обе статьи. Вы начнете практиковать парное программирование между собой, студентами.
