# Шаги урока: JSDoc: документирование функций

---

### Зачем документировать код

**kind:** `text`

Код читают намного чаще, чем пишут. Через месяц ты сам будешь чужим человеком для своего кода: что принимает функция, что возвращает, какие ошибки возможны — без документации это придётся выяснять, перечитывая тело функции. А ревьюер в PR читает твой код впервые — и документация экономит его время и нервы.

**JSDoc** — это комментарии `/** ... */` перед функцией, которые описывают её контракт: что она делает, что принимает, что возвращает, какие ошибки выбрасывает. Это стандарт, принятый во всей JS-экосистеме: его понимают VS Code, GitHub, генераторы документации.

Основных тегов пока достаточно четырёх:

- [`@param`](https://jsdoc.app/tags-param) — параметры функции
- [`@returns`](https://jsdoc.app/tags-returns) — возвращаемое значение
- [`@throws`](https://jsdoc.app/tags-throws) — исключения
- [`@example`](https://jsdoc.app/tags-example) — примеры использования

**Термины:**
JSDoc — стандарт документирования JavaScript-кода через комментарии `/** ... */` перед функцией;
докстринг — сам блок комментария перед функцией;
тег — аннотация внутри докстринга: `@param`, `@returns`, `@throws`, `@example`;
контракт функции — что она принимает, что возвращает и какие ошибки возможны

### Хороший и плохой JSDoc: примеры

**kind:** `text`

Сначала посмотри, как выглядит хороший JSDoc, а как — плохой:

**Плохо (так не пишем):**
```javascript
/** @param a @param b @returns boolean */
function isEqual(a, b) { ... }
```
Теги есть, но пользы ноль: не сказано, что за аргументы и что сравнивается.

**Хорошо (так пишем):**
```javascript
/**
 * Возвращает равны ли строки a и b.
 * Сравнение посимвольное, с учётом регистра.
 *
 * @param {string} a — первая строка
 * @param {string} b — вторая строка
 * @returns {boolean} — true если строки равны, false если нет
 * @throws {TypeError} — если любой из аргументов не строка
 *
 * @example
 *   isEqual('hello', 'hello'); // true
 *   isEqual('hi', 'hello');    // false
 */
export function isEqual(a, b) { ... }
```

Обрати внимание на:
- Две звёздочки `/**` в начале — именно так JSDoc отличает документацию от обычного комментария
- Описание **что делает**, а не **как делает** — «как» видно в реализации
- Пустые строки между группами тегов (читаемость)
- Тире `—` после имени параметра и типа возврата
- Отступ в 2 пробела для примеров в `@example`

### Вопросы на понимание

**kind:** `text`

Ответь на вопросы. Если не знаешь ответ — подумай, проверь догадки на своих же файлах.

**1.** Открой любой `.test.js` файл из проектов 3 и 5 и наведи мышку на вызов функции, например `len(...)`. Что показывает VS Code? Откуда он это взял, если ты не писал документацию?

**2.** Представь: ты вернулся к своему коду через месяц. Ты открываешь `is-more.js` и видишь только:
```javascript
export function isMore(a, b) {
  if (typeof a !== 'string') throw new TypeError('...');
  // ... 20 строк алгоритма
}
```
Без JSDoc. Сколько секунд ты потратишь, чтобы понять: что принимает функция, что возвращает (`true`/`false` или `1`/`-1`?), какие ошибки кидает? А если JSDoc есть — ты читаешь 5 строк комментария и уже знаешь ответ.

**3.** Ты отправляешь свой код ревьюеру. Он открывает PR и видит 8 новых функций. Без JSDoc ревьюеру придётся читать тело каждой функции, чтобы понять, что она делает. С JSDoc — пробегает глазами по описанию и проверяет только логику. Как ты думаешь, в каком случае ревьюер:
- Быстрее даст апрув?
- Найдёт больше ошибок в логике (а не в понимании)?
- Будет меньше раздражён?

**4.** JSDoc — это не только для людей. Инструменты вроде `jsdoc-to-markdown` могут сгенерировать из твоих комментариев полноценный сайт с документацией. Попробуй мысленно представить: у тебя 13 функций в проекте. Как быстрее объяснить новому разработчику, что делает каждая — дать ему читать файлы с кодом или открыть сгенерированную страницу с сигнатурами и описаниями?
