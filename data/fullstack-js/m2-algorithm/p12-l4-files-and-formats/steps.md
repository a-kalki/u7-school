### Зачем сохранять данные: персистентность

**kind:** `text`

В первых трёх уроках мы завершили **Этап 1** нашего проекта: научились разбирать строки запросов (`getQueryParams`), анализировать полный URL (`parseUrl`) и группировать коллекции объектов (`groupBy`).

Все эти данные жили исключительно в оперативной памяти (RAM). Как только программа завершает работу или процесс останавливается — оперативка очищается, а все созданные объекты исчезают без следа.

Теперь мы переходим к **Этапу 2: Персистентность и файлы**.
Чтобы данные не пропадали между запусками программ, их сохраняют на постоянный носитель (диск, SSD). Это свойство сохранения данных называется **персистентностью** (persistence).

Самый простой, понятный и переносимый способ хранить данные — **текстовые файлы**. Их можно открыть любым редактором, просмотреть в терминале и передать между любыми операционными системами.

В этом блоке уроков мы научим наши бизнес-утилиты сохранять объекты в файл и восстанавливать их обратно.

### Практика: Bun File API в действии

**kind:** `text`

Среда Bun имеет сверхбыстрые и простые функции для работы с файлами.

Открой терминал и запусти Bun REPL:
```bash
bun repl
```

Попробуй выполнить прямо в консоли две ключевые команды:

**1. Запись в файл: `Bun.write(path, content)`**
```javascript
await Bun.write('hello.txt', 'Привет, мир!\nВторая строчка.');
```
Bun мгновенно создаёт файл `hello.txt` на диске.

**2. Чтение из файла: `Bun.file(path).text()`**
```javascript
const content = await Bun.file('hello.txt').text();
console.log(content);
```

Файл прочитан асинхронно в обычную строку JavaScript.

**Почему перед вызовами стоит `await`?**
Обращение к диску по меркам процессора длится долго. Чтобы программа не зависала в ожидании, в современном JS все файловые операции сделаны **асинхронными** (выполняются в фоне).

Всю теорию асинхронности, промисы (`Promise`) и Event Loop мы будем подробно разбирать в курсе **«Продвинутый JavaScript»**.

Сейчас не нужно глубоко в это погружаться — достаточно простого правила:
- Перед файловыми операциями пишем `await` (буквально: *«подожди, пока файл прочитается или запишется»*): `await Bun.write(...)`, `await Bun.file(...).text()`.
- В REPL `await` можно писать сразу. А внутри своей функции перед `function` ставится слово `async`: `async function saveToFile(...)`.
- Код с `await` выполняется последовательно, строка за строкой, как привычный синхронный код.

Удали созданный файл, чтобы не оставлять мусора:
```javascript
import { unlinkSync } from 'node:fs';
unlinkSync('hello.txt');
```
Выйди из REPL с помощью `.exit` или комбинации Ctrl+C.

### Катастрофа разорванной строки

**kind:** `text`

Текстовый файл — это цепочка байтов. Символ перевода строки `\n` (LF, байт 10) указывает редакторам и операционной системе, где переносить курсор на новую строку.

Мы хотим, чтобы структура нашего файла подчинялась железному правилу:
**Одна физическая строка файла = ровно один объект (запись).**

Посмотри, что произойдёт, если записать в файл объект, у которого внутри свойства есть перенос строки:
```javascript
const order = { id: 1, comment: 'Спасибо за заказ!\nКурьер молодец' };
```

Если просто соединить поля запятыми и записать в файл «как есть»:
```text
id,comment
1,"Спасибо за заказ!
Курьер молодец"
```

**Катастрофа:**
- Вместо двух строк (заголовок + заказ) в файле получилось три!
- Строка 3 (`Курьер молодец"`) — оторванный кусок, у которого нет структуры.
- Любой построчный парсер файлов сломается на такой строке.

**Вывод:** символ перевода строки внутри текста значения не имеет права попадать в файл в виде физического переноса. Его необходимо **экранировать** — превратить в безопасную последовательность символов.

### Наш формат данных: что берём от CSV и от JSON

**kind:** `text`

Чтобы сохранять данные компактно и безопасно, мы создаём свой формат — объединение сильных сторон CSV и JSON:

**1. От CSV берём:**
- Табличный вид: первая строка — это имена колонок (ключи объектов) через запятую.
- Компактность: ключи не повторяются в каждой записи, как в стандартном JSON.

**2. От JSON берём:**
- Сохранение типов: числа пишутся без кавычек (`25`), булевы как `true`/`false`, `null` как `null`, пропущенные свойства (`undefined`) как пустая ячейка между запятыми.
- Строки оборачиваются в двойные кавычки: `"текст"`.
- Экранирование спецсимволов внутри строк:
  - `\n` → `\n` (пара печатных символов: слэш и n)
  - `"` → `\"` (чтобы кавычка не закрыла строку раньше времени)
  - `\` → `\\` (чтобы слэш не перепутался с экранированием)

С экранированием заказ запишется ровно в одну строку:
```text
id,comment
1,"Спасибо за заказ!\nКурьер молодец"
```
Файл аккуратен, строг и предсказуем.

### Три мира перевода строки: память, файл на диске, код на JS

**kind:** `text`

Запомни разницу между тремя состояниями строки с переносом:

| Мир | Где живёт | Что внутри | Как выглядит |
|---|---|---|---|
| **Мир 1: Память JS** | В объекте JavaScript | 1 байт перевода строки (`ch === '\n'`) | Текст переносится на новую строчку |
| **Мир 2: Файл на диске** | В текстовом файле | 2 печатных символа: `\` и `n` | `\n` напечатано на одной строке |
| **Мир 3: Исходный код JS** | В тестах и модулях | Строковый литерал `'\\n'` | Два слэша, чтобы движок понял один слэш |

Проверь прямо в `bun repl`:
```javascript
const memoryStr = 'A\nB';
console.log(memoryStr.length); // 3 (символ переноса — ровно один символ!)

const diskStr = memoryStr.replaceAll('\n', '\\n');
console.log(diskStr); // A\nB (в одну строчку!)
console.log(diskStr.length); // 4 (появился слэш и буква n)
```

- Функция **`toCSV`** переводит данные из Мира 1 в Мир 2 (экранирует).
- Функция **`fromCSV`** переводит данные из Мира 2 обратно в Мир 1 (раскрывает экранирование).

### Кроссплатформенность: CRLF и пути к файлам

**kind:** `text`

Разные операционные системы по-разному работают с файлами:

1. **Разделители строк:**
   - Linux и macOS используют `\n` (LF).
   - Windows использует `\r\n` (CRLF — два байта: возврат каретки 13 и перевод строки 10).
   - **Наше решение:** при записи мы всегда пишем `\n`. При чтении наш парсер будет просто игнорировать `\r` вне кавычек. Благодаря этому файлы одинаково корректно читаются на любой ОС.

2. **Пути к файлам:**
   - В Windows пути пишут через обратный слэш `folder\file.txt`.
   - В Unix — через прямой `folder/file.txt`.
   - **Наше решение:** Bun на всех системах понимает прямой слэш `/`. В коде всегда пишем только прямой слэш: `'business-utils/data.csv'`.

### Термины урока

**kind:** `text`

**персистентность (persistence)** — долговременное сохранение данных на диске между перезапусками программы.
**Bun File API** — быстрые встроенные функции `Bun.write` и `Bun.file().text()` для работы с файлами.
**сериализация** — превращение объектов из памяти в строку или байты для сохранения/передачи.
**десериализация** — обратное восстановление объектов в памяти из сохранённой строки.
**экранирование** — замена служебных символов (`\n`, `"`, `\`) на безопасные текстовые комбинации (`\n`, `\"`, `\\`).
**LF / CRLF** — стандарты перевода строки (`\n` в Unix / `\r\n` в Windows).
**round-trip** — полный цикл проверки: данные → сохранение → чтение → проверка на равенство оригиналу.
