# Файлы, форматы данных и Bun File API: три мира строки

Вводный урок к блоку персистентности и сохранения данных. Студент знакомится с концепцией долговременного хранения данных на диске и встроенными синхронными функциями Node.js/Bun (`writeFileSync`, `readFileSync`). На наглядных примерах разбирается физика текстового файла, «катастрофа разорванной строки» и концепция «трёх миров перевода строки». Формулируются правила нашего формата данных (симбиоз CSV и JSON).

**Время:** ~25 мин

**Основные темы:**
- Персистентность: зачем сохранять данные в файлы
- Синхронный файловый ввод-вывод: `writeFileSync` и `readFileSync`
- Устройство текстового файла и символ \n
- Катастрофа разорванной строки
- Что берём от CSV и что берём от JSON
- Концепция «Три мира перевода строки»
- Кроссплатформенность: Windows (CRLF) и пути к файлам
- План блока персистентности

**Термины:**
персистентность (persistence) — сохранение данных между перезапусками программы в энергонезависимой памяти (на диске)
синхронный ввод-вывод — выполнение операций с файлами последовательно, когда программа останавливает выполнение до завершения чтения или записи диска
сериализация — преобразование структуры данных в памяти (объекта/массива) в строку или последовательность байтов для передачи или сохранения
десериализация — обратное восстановление структуры данных в памяти из строки или байтов
экранирование — замена опасных управляющих символов на безопасные текстовые комбинации
LF (Line Feed) — символ перевода строки `\n` (байт 10), стандартный разделитель строк в Unix/Linux/macOS
CRLF (Carriage Return + Line Feed) — пара символов `\r\n` (байты 13 и 10), исторический разделитель строк в Windows
round-trip — полный цикл жизни данных: объект сериализуется, сохраняется в файл, считывается, десериализуется и сверяется с исходным объектом

### 1. Персистентность: зачем сохранять данные

В уроках 1–3 мы завершили **Этап 1** нашего проекта: научились разбирать входящие адреса (`getQueryParams`, `parseUrl`) и группировать объекты в памяти (`groupBy`).

Но все эти переменные, массивы и объекты живут исключительно в **оперативной памяти (RAM)**.
Как только программа завершила работу или сервер перезагрузился — оперативная память очищается, и все данные исчезают без следа.

Чтобы сохранить результаты работы (список заказов, профили пользователей, аналитические отчёты), данные нужно записать в постоянное хранилище — на **жёсткий диск или SSD**. Это свойство сохранения данных называется **персистентностью** (persistence). С этого урока начинается **Этап 2: Хранилище данных и файлы**.

Самый простой, надёжный и универсальный способ хранить данные — **текстовые файлы**. Их можно открыть любым редактором, передать на другой сервер, просмотреть через терминал и легко обработать программой.

### 2. Синхронные функции файла: `writeFileSync` и `readFileSync`

Для работы с файлами в среде Bun (и Node.js) есть стандартный встроенный модуль `'node:fs'`. Он предоставляет простые и привычные **синхронные** функции.

Открой терминал и запусти консоль Bun:
```bash
bun repl
```

Сначала подключим функции из модуля:
```javascript
import { writeFileSync, readFileSync, unlinkSync } from 'node:fs';
```

#### Запись в файл: `writeFileSync`

Чтобы сохранить текст в файл, используется функция `writeFileSync(path, content, 'utf8')`:

```javascript
writeFileSync('test.txt', 'Привет, Bun!\nВторая строка.', 'utf8');
```

Файл `test.txt` мгновенно создаётся на диске (или перезаписывается, если уже существовал).

#### Чтение из файла: `readFileSync`

Чтобы прочитать файл целиком в виде строки:

```javascript
const content = readFileSync('test.txt', 'utf8');
console.log(content);
// Привет, Bun!
// Вторая строка.
```

Функция `readFileSync` возвращает содержимое файла как обычную строку JavaScript.

#### Почему эти функции синхронные?
Все функции, которые мы писали до этого (и функции работы с файлами `writeFileSync` / `readFileSync`), являются **синхронными**. Это значит, что программа выполняет строчку, дожидается полного завершения операции (например, записи на диск) и только после этого переходит к следующей строчке. 

Никаких сложных понятий вроде `async/await` или промисов здесь не требуется — код выполняется абсолютно последовательно, как мы и привыкли. Управлять асинхронностью мы научимся позже, в курсе «Продвинутый JavaScript».

Удали созданный файл, чтобы не оставлять мусора:
```javascript
unlinkSync('test.txt');
```

### 3. Постановка задачи: как хранить объекты в файле

Мы хотим научиться сохранять массив объектов в текстовый файл так, чтобы каждая запись занимала **строго одну физическую строку файла**.

Допустим, у нас есть вот такой массив заказов:

```javascript
const orders = [
  { id: 1, comment: 'Доставить до 18:00' },
  { id: 2, comment: 'Отличный товар!\nБуду заказывать ещё.' },
  { id: 3, comment: 'Оплата наличными' },
];
```

Мы хотим превратить этот массив в текст, который запишем в файл. Наша главная цель — получить на диске файл со строго фиксированной структурой: **1 строка заголовков + ровно 1 строка на каждый объект**.

Идеальный вид файла на диске должен выглядеть так:

```text
id,comment
1,"Доставить до 18:00"
2,"Отличный товар!\nБуду заказывать ещё."
3,"Оплата наличными"
```

Обрати внимание на заказ №2: в его поле `comment` пользователь при оформлении заказа нажал клавишу Enter (в памяти это реальный перенос строки `\n`). Но в файле эта строка **не должна** ломать структуру.

Давай посмотрим, что будет, если попытаться сделать это «в лоб» без подготовки.

### 4. Катастрофа разорванной строки

Представь, что мы хотим сохранить в файл список заказов из интернет-магазина.
Мы хотим, чтобы наш файл был максимально простым и структурированным:
**Каждая физическая строка файла = ровно один заказ (объект)**.

В памяти программы есть массив:

```javascript
const orders = [
  { id: 1, comment: 'Доставить до 18:00' },
  { id: 2, comment: 'Отличный товар!\nБуду заказывать ещё.' },
  { id: 3, comment: 'Оплата наличными' },
];
```

Посмотри на заказ №2. В поле `comment` покупатель нажал клавишу Enter при оформлении. Внутри строки находится символ `\n`!

Что произойдёт, если мы просто соединим значения запятыми и запишем в файл «как есть»?

```text
id,comment
1,"Доставить до 18:00"
2,"Отличный товар!
Буду заказывать ещё."
3,"Оплата наличными"
```

**Произошла катастрофа:**
1. Мы ожидали, что у нас 3 заказа — значит, в файле должно быть 4 строки (1 строка заголовков + 3 строки данных).
2. Но в файле получилось **5 физических строк**!
3. Заказ №2 разорвало на две части.
4. Строка 4 (`Буду заказывать ещё."`) — это вообще синтаксический мусор! У неё нет поля `id`, нет структуры.
5. Любая программа, которая читает файл построчно, посчитает `Буду заказывать ещё."` отдельным невалидным заказом и упадет с ошибкой.

**Вывод:** мы не имеем права допустить физического разрыва строки внутри значения. Символ `\n` внутри значения ОБЯЗАН быть замаскирован (экранирован)!

### 5. Наш формат данных: таблица с сохранением типов

Чтобы сохранять структурированные таблицы объектов без риска разорвать файл, мы проектируем свой собственный формат (свой «велосипед»), который объединяет две ключевые идеи:

1. **Табличная структура:** первая строка содержит имена колонок (ключи объектов) через запятую (`id,comment,status`). Ключи объявляются один раз сверху, а не дублируются в каждом объекте.
2. **Сохранение типов данных:**
   - Числа пишутся без кавычек (`25`, `100.5`).
   - Булевы значения пишутся как ключевые слова (`true`, `false`).
   - Отсутствие значения пишется как `null`, пропущенные свойства (`undefined`) — как пустая ячейка.
   - Строковые значения оборачиваются в двойные кавычки (`"текст"`).
   - Опасные символы внутри строк защищаются экранированием (например, перенос строки записывается как пара символов `\` и `n` — `\n`).

С таким экранированием наш файл выглядит идеально:

```text
id,comment
1,"Доставить до 18:00"
2,"Отличный товар!\nБуду заказывать ещё."
3,"Оплата наличными"
```

Посмотри: ровно 4 строки! Заказ №2 остался на одной физической строке. Перенос строки сохранён, но временно обезврежен.

*Подробно устройство форматов данных (включая стандарты CSV и нотацию объектов) мы детально разберем и запрограммируем своими руками в следующих двух уроках.*

### 6. Концепция: «Три мира перевода строки»

Это главная ментальная модель, которую нужно усвоить раз и навсегда. Почему со слэшами вечно возникает путаница? Потому что строка существует в **трёх разных мирах**:

| Мир | Где живёт | Что там находится | Сколько символов | Как выглядит |
|---|---|---|---|---|
| **Мир 1: Память JS** | В переменной JavaScript | Реальный байт `10` (LF) | 1 символ (`s.length === 1`) | Курсор переносится на новую строчку |
| **Мир 2: Файл на диске** | Текст в файле `.csv` | Два символа: `\` и `n` | 2 символа | На экране написано `\n` на одной строке |
| **Мир 3: Исходный код JS** | В файле теста `.test.js` | Строковый литерал `'\\n'` | 4 символа в редакторе (два слэша) | Движок JS превращает `'\\'` в один `\` |

Проверь это своими руками в `bun repl`:

```javascript
// Мир 1: реальный перенос в памяти
const original = 'Привет\nМир';
console.log(original.length); // 10 символов (перенос строки — это 1 символ!)

// Переход из Мира 1 в Мир 2: экранируем для сохранения в файл
const inDiskFormat = original.replaceAll('\n', '\\n');
console.log(inDiskFormat); // Привет\nМир (напечатано в одну строчку!)
console.log(inDiskFormat.length); // 11 символов (появился слэш + буква n)

// Записываем на диск — в файле будет строго одна строка!
writeFileSync('one-line.txt', inDiskFormat, 'utf8');

// Переход из Мира 2 обратно в Мир 1: восстанавливаем при чтении
const fromDisk = readFileSync('one-line.txt', 'utf8');
const restored = fromDisk.replaceAll('\\n', '\n');
console.log(restored === original); // true!

// Удаляем временный файл
unlinkSync('one-line.txt');
```

### 7. Кроссплатформенность: Windows (CRLF) и пути к файлам

При работе с файлами важно учитывать различия между операционными системами:

1. **Разделители строк:**
   - В Unix, Linux и macOS для перевода строки используется один байт **LF** (`\n`).
   - В Windows исторически используется комбинация из двух байтов — **CRLF** (`\r\n`: Carriage Return, байт 13, и Line Feed, байт 10).
   - *Как мы это решаем:*
     - При записи файлов мы **всегда пишем стандартный `\n`**.
     - При чтении файлов наш парсер будет **игнорировать символ `\r`**, если он встречается вне строковых кавычек. Тогда файл, созданный в Windows-блокноте, прочитается так же безупречно, как на Linux или Mac.

2. **Слэши в путях к файлам:**
   - В Windows пути к файлам традиционно пишут с обратным слэшем: `folder\file.txt`.
   - Но в коде JavaScript обратный слэш — это символ экранирования.
   - Среда Bun (как и Node.js) на ВСЕХ операционных системах отлично понимает стандартный прямой слэш `/`.
   - **Правило:** в коде мы ВСЕГДА пишем пути через прямой слэш: `'business-utils/data.csv'`.
