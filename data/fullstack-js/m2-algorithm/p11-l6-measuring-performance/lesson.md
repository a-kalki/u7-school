# Измеряем скорость: бенчмарк сортировок и поиска

**Краткое содержание:**
Студент собирает испытательный стенд: скрипт, который генерирует массивы разных размеров и замеряет время работы каждого алгоритма сортировки, а затем сравнивает линейный и бинарный поиск. Вживую видит разницу между быстрыми и медленными алгоритмами ещё до того, как узнает их формальные названия.

### 1. Зачем измерять

Ты реализовал четыре алгоритма. На глаз они делают «одно и то же» — превращают неотсортированный массив в отсортированный. Но на больших данных разница в скорости может быть в сотни раз.

То же касается поиска: в уроке 5 ты реализовал `binarySearch`, который ищет гораздо быстрее, чем перебор `indexOf`. Стенд замерит и эту разницу.

Чтобы не верить на слово — измерим. Для замера времени в JavaScript есть глобальная функция `performance.now()`: она возвращает количество миллисекунд, прошедших с начала работы программы, с точностью до долей миллисекунды.

```javascript
const start = performance.now();
// ...код, который замеряем...
const elapsed = performance.now() - start;
```

### 2. Почему один замер — это шум

Время одного запуска нестабильно: на него влияют нагрев движка (JIT-компиляция), сборщик мусора, другие процессы. Поэтому правильный бенчмарк:
1. **Прогревает** функцию — первый вызов не замеряем, движок «разогревается».
2. Запускает функцию **несколько раз**.
3. Берёт **лучшее (минимальное)** время — оно ближе всего к «чистой» скорости алгоритма.

### 3. Испытательный стенд

Создай файл `sorting/sort-benchmark.js` со следующим содержимым:

```javascript
import { len } from '../arrays/len.js';
import { push } from '../arrays/push.js';
import { indexOf } from '../arrays/index-of.js';
import { bubbleSort } from './bubble-sort.js';
import { insertionSort } from './insertion-sort.js';
import { selectionSort } from './selection-sort.js';
import { quickSort } from './quick-sort.js';
import { binarySearch } from './binary-search.js';

const SIZES = [100, 500, 1000, 2000, 4000, 8000];
const RUNS = 5;

function randomArray(size) {
  const arr = [];
  for (let i = 0; i < size; i++) {
    push(arr, Math.floor(Math.random() * size));
  }
  return arr;
}

function measure(fn, input) {
  fn(input); // прогрев — первый вызов не замеряем
  let best = Infinity;
  for (let i = 0; i < RUNS; i++) {
    const start = performance.now();
    fn(input);
    const elapsed = performance.now() - start;
    if (elapsed < best) best = elapsed;
  }
  return best;
}

const algorithms = [
  { name: 'bubbleSort', fn: bubbleSort },
  { name: 'insertionSort', fn: insertionSort },
  { name: 'selectionSort', fn: selectionSort },
  { name: 'quickSort', fn: quickSort },
];

const sizesCount = len(SIZES);
const algorithmsCount = len(algorithms);

for (let s = 0; s < sizesCount; s++) {
  const input = randomArray(SIZES[s]);
  let line = 'n=' + SIZES[s];
  for (let a = 0; a < algorithmsCount; a++) {
    const ms = measure(algorithms[a].fn, input);
    line = line + '  |  ' + algorithms[a].name + ': ' + Math.round(ms * 100) / 100 + 'мс';
  }
  console.log(line);
}

// Поиск: линейный (indexOf) против бинарного (binarySearch)
const searchSize = 1000000;
const sorted = [];
for (let i = 0; i < searchSize; i++) push(sorted, i); // уже отсортированный массив
const target = searchSize - 1; // ищем последний элемент — худший случай для перебора

const linearSearch = (arr) => indexOf(arr, target);
const binarySearchForTarget = (arr) => binarySearch(arr, target);

const linearMs = measure(linearSearch, sorted);
const binaryMs = measure(binarySearchForTarget, sorted);

console.log('--- Поиск в массиве из ' + searchSize + ' элементов (ищем ' + target + ') ---');
console.log('indexOf (перебор): ' + Math.round(linearMs * 100) / 100 + 'мс');
console.log('binarySearch: ' + Math.round(binaryMs * 100) / 100 + 'мс');
```

Разбор стенда:
- **`randomArray(size)`** — генерирует массив случайных чисел от 0 до `size`. `Math.random()` возвращает случайное число от 0 (включительно) до 1 (не включая); умножив на `size` и округлив вниз через `Math.floor`, получаем целое число в нужном диапазоне.
- **`measure(fn, input)`** — прогоняет `fn` несколько раз на одном и том же `input` и возвращает минимальное время. Так как все наши сортировки иммутабельны, `input` не меняется между запусками — все алгоритмы получают одинаковые данные.
- **`Math.round(ms * 100) / 100`** — округляем до сотых миллисекунды, чтобы числа было удобно читать.
- **`Infinity`** — специальное значение «больше любого числа», удобная стартовая точка для поиска минимума.
- **Блок поиска** — создаёт отсортированный массив на 1 000 000 элементов и ищет последний элемент (худший случай для перебора) двумя способами: `indexOf` проходит всё подряд, а `binarySearch` делит диапазон пополам. Обёртки `linearSearch` и `binarySearchForTarget` фиксируют `target`, чтобы переиспользовать уже готовый `measure`.

> Новые глобальные функции `performance.now()`, `Math.random()` и значение `Infinity` — **разрешённые глобальные** (как `decodeURIComponent` в проекте 10), это не методы массивов/строк/объектов. `Math.floor` ты уже использовал в проектах 3–4.

### 4. Запуск и ожидания

Запусти:

```bash
bun sorting/sort-benchmark.js
```

Запуск может занять от нескольких секунд до минуты — это и есть та самая медлительность, которую мы измеряем.

Ожидаемая картина (у тебя числа будут другими, но закономерность — та же):

| n | bubbleSort | insertionSort | selectionSort | quickSort |
|---|-----------|---------------|---------------|-----------|
| 100 | 0.2мс | 0.1мс | 0.1мс | 0.05мс |
| 500 | 3мс | 2мс | 2мс | 0.2мс |
| 1000 | 10мс | 8мс | 8мс | 0.5мс |
| 2000 | 40мс | 30мс | 30мс | 1мс |
| 4000 | 160мс | 120мс | 120мс | 3мс |
| 8000 | 650мс | 500мс | 500мс | 6мс |

Закономерности, на которые обрати внимание:
1. **На маленьких n все быстрые** — разница незаметна. Поэтому на учебных массивах из 5 элементов «любая сортировка хороша».
2. **С ростом n в 2 раза время пузырька растёт в ~4 раза** (квадратичный рост), а быстрой — в ~2 раза.
3. **На 8000 элементах разница между пузырьком и быстрой — в 100 раз.**
4. **Для поиска контраст ещё сильнее:** `indexOf` на 1 000 000 элементов проходит их все, а `binarySearch` — ~20 шагов. Разница — в десятки тысяч раз.

### 5. Эксперименты

**Эксперимент 1 — отсортированный массив.** Создай второй вариант генератора, который возвращает уже отсортированный массив: `arr[i] = i` (вместо случайных значений). Запусти бенчмарк снова. Что произошло с `insertionSort`? А с `quickSort`? Почему?

> Для этого эксперимента возьми `SIZES = [100, 500, 1000, 2000]` — на отсортированном массиве `quickSort` с опорным первым элементом деградирует и на больших размерах может переполнить стек рекурсии. Это ещё одно проявление деградации, о которой говорилось в уроке 4.

**Эксперимент 2 — больший размер.** Добавь в `SIZES` значение `16000` и запусти только `quickSort` (остальные закомментируй в массиве `algorithms`, чтобы не ждать). Почувствуй, насколько быстрой остаётся быстрая сортировка там, где пузырёк уже неприемлем.

### 6. Что мы только что увидели

Мы увидели главный закон, который будем изучать в следующем проекте: **скорость алгоритма определяется не количеством строк в нём, а тем, как растёт количество операций при росте данных.** Четыре алгоритма делают одно и то же, но три из них имеют «вложенный цикл» (рост ~n²), а быстрая — «разделение пополам» (рост ~n × log n).

### 7. Если что-то пошло не так

**«Maximum call stack size exceeded» (переполнение стека).** Возникает, когда `quickSort` получает большой уже отсортированный массив: рекурсия уходит на глубину n, потому что опорный элемент — первый (минимум). В основном прогоне это не случится (там случайные данные), а в эксперименте 1 размеры ограничены до 2000. Если ошибка всё же появилась — уменьши `SIZES`.

**«Cannot find module .../arrays/len.js».** Неверный путь импорта: скрипт лежит в `sorting/`, а функции массивов — в `arrays/`, поэтому путь через `../arrays/...`. Проверь, что файлы `arrays/len.js` и `arrays/push.js` существуют, и что строки импорта в начале `sort-benchmark.js` выглядят так: `import { len } from '../arrays/len.js'`.

**Скрипт висит дольше минуты.** Пузырёк/вставки/выбор на 8000 элементах — это секунды на каждый запуск, а запусков несколько. Убери большие значения из `SIZES`.

**В выводе одни 0мс.** На маленьких размерах время меньше сотой миллисекунды и округляется до 0. Увеличь `RUNS` (число запусков) или размеры в `SIZES`. Для `binarySearch` 0мс — ожидаемо: он делает ~20 шагов, это почти мгновенно.

**`binarySearch` вернул `-1`, хотя элемент есть.** Причина: бинарный поиск требует **отсортированный** массив. В бенчмарке массив `sorted` собирается по возрастанию (`push(sorted, i)`), так что проблема не возникнет; но если поменяешь генератор — учти это предусловие.
