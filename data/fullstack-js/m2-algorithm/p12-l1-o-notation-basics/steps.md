# Шаги урока: O-нотация — учимся оценивать свои функции

---

### Зачем вообще оценивать сложность

**kind:** `text`

Два разработчика написали функцию поиска подстроки. Первый — простым перебором (наш `indexOf`). Второй — хитрым алгоритмом Кнута-Морриса-Пратта. На строке из 10 символов оба работают мгновенно. На строке из 10 000 символов первый — 3 секунды, второй — 5 миллисекунд. **Разница в 600 раз.**

Эту разницу невозможно заметить на маленьких данных. Она проявляется только когда данных много.

Сложность алгоритма — это способ предсказать поведение алгоритма на больших данных, **не запуская код**. Зная сложность, ты можешь выбрать правильный алгоритм ДО того, как данные вырастут.

---

### O-нотация — язык сложности

**kind:** `text`

O-нотация (Big O) описывает **верхнюю границу** роста алгоритма. Она отвечает на вопрос: «если данных станет в N раз больше, во сколько раз дольше будет работать алгоритм?»

Главное правило: **отбрасываем константы.** O(2n) = O(n), O(n + 1000) = O(n). Нас интересует только порядок роста при больших N.

Четыре основных класса (от быстрого к медленному):

| Класс | Название | Как ощущается |
|-------|----------|--------------|
| O(1) | Константная | Мгновенно, всегда |
| O(log n) | Логарифмическая | Очень быстро даже на огромных данных |
| O(n) | Линейная | Пропорционально данным: ×10 данных → ×10 времени |
| O(n log n) | Линейно-логарифмическая | Быстрее O(n²), медленнее O(n) |
| O(n²) | Квадратичная | Быстро становится неприемлемо медленным |

---

### O(1) — константная сложность

**kind:** `text`

Самая быстрая. Время выполнения **не зависит** от размера входных данных.

Примеры из твоего кода:
- `at(arr, index)` — доступ к элементу по индексу. Одна операция, неважно какой длины массив.
- `push(arr, item)` — добавить в конец. Одно присваивание.

**Задание:** посмотри на свой код и найди ещё хотя бы одну функцию со сложностью O(1). Объясни почему.

### O(n) — линейная сложность

**kind:** `text`

Время растёт **прямо пропорционально** размеру данных. Один цикл по всем элементам = O(n).

Твои функции с O(n): `len()`, `isEqual()`, `isMore()`, `forEach()`, `map()`, `filter()`, `reverse()`, `trim()`, `upperCase()`, `lowerCase()`, `fill()`.

```javascript
function len(str) {
  let count = 0;
  for (let i = 0; str[i] !== undefined; i++) count++;
  return count;
}
```

Вопрос: почему `reverse(arr)` — тоже O(n), хотя цикл идёт только до середины массива (если ты реализовал алгоритмом сдвига начального и конечного индекса к центру)? Потому что n/2 — это всё ещё линейный рост, константа ½ отбрасывается.

**Задание:** выбери 3 своих функции со сложностью O(n) и для каждой объясни почему одним предложением.

### O(n²) — квадратичная сложность

**kind:** `text`

Время растёт как **квадрат** от размера данных. Означает **вложенный цикл**: для каждого из N элементов делаем ещё N операций.

Твой `indexOf(str, search)`: для каждой позиции в строке проверяешь все символы подстроки → ~n×m операций.

Твои `bubbleSort`, `insertionSort` и `selectionSort` — тоже O(n²): вложенный цикл (или сдвиги) по всем элементам. В бенчмарке из проекта 11 ты видел, как при удвоении размера массива их время росло примерно в 4 раза.

Почему O(n²) — проблема:

| Размер данных | O(n) | O(n²) |
|--------------|------|-------|
| 10 | 10 | 100 |
| 100 | 100 | 10 000 |
| 1 000 | 1 000 | 1 000 000 |
| 10 000 | 10 000 | 100 000 000 |

На 10 000 элементах разница — в 10 000 раз. Алгоритм, который работал 0.1 секунды на 100 элементах, будет работать **17 минут** на 10 000.

**Задание:** посмотри на свой код и найди функцию, которая имеет сложность O(n²) (или O(n×m)). Объясни почему.

### O(n log n) — сложность твоей quickSort

**kind:** `text`

В проекте 11 ты реализовал `quickSort` и увидел в бенчмарке, что она заметно быстрее пузырька, вставок и выбора. Теперь назовём её сложность: **O(n log n)** в среднем.

Почему: на каждом уровне рекурсии ты раскладываешь все n элементов на «меньше» и «больше» (n операций), а уровней рекурсии — ~log n (данные каждый раз делятся примерно пополам). Перемножаем: n × log n.

Это медленнее O(n), но **намного быстрее O(n²)**. При N = 1 000 000: O(n) ≈ 1 000 000, O(n log n) ≈ 20 000 000, O(n²) = 1 000 000 000 000.

**Важно:** это средняя сложность. В бенчмарке ты подсовывал `quickSort` уже отсортированный массив — и она деградировала: опорным был первый элемент, стопка «меньше» каждый раз оказывалась пустой. Рекурсия уходила на глубину n, и сложность падала до O(n²). Поэтому выбор опорного элемента так важен.

### O(log n) — логарифмическая сложность

**kind:** `text`

На каждом шаге алгоритм отбрасывает **половину** данных. Как поиск слова в бумажном словаре: открываешь посередине, смотришь — нужное слово левее или правее, отбрасываешь половину, повторяешь. В словаре из 100 000 слов нужное находится за ~17 шагов.

Пример — бинарный поиск в отсортированном массиве. Ты реализовал его в проекте 11 (`binarySearch`). Идея проста:
1. Смотрим в середину массива
2. Если искомое меньше среднего — отбрасываем правую половину
3. Если больше — отбрасываем левую
4. Повторяем с оставшейся половиной

Это единственная твоя функция с O(log n): `binarySearch` из проекта 11 делает ~log₂n шагов.

### Как оценить сложность — три правила

**kind:** `text`

**Правило 1 — найди циклы:**
- Нет циклов → O(1)
- Один цикл по всем данным → O(n)
- Два последовательных цикла → всё ещё O(n) (константа 2 отбрасывается)
- Вложенный цикл → O(n²) или O(n×m)

**Правило 2 — рекурсия:**
- Каждый вызов уменьшает n на 1 (как `factorial(n-1)`) → O(n) вызовов
- Каждый вызов делит данные пополам (как бинарный поиск) → O(log n) вызовов
- Каждый вызов обрабатывает все n элементов И делит данные пополам (как `quickSort`) → O(n log n)

**Правило 3 — отбрасывай константы и младшие члены:**
- O(2n + 5) → O(n)
- O(n² + 100n) → O(n²) (n² доминирует при больших n)
- O(n + log n) → O(n)

**kind:** `text`

- O-нотация — способ думать о производительности до написания кода
