### Прямой пуш документации в main — и когда это допустимо

**kind:** `text`

Когда всё готово — закоммить и отправь на GitHub:

```
git switch main
git add -A
git commit -m "Добавлен JSDoc для всех функций из проектов 3 и 5"
git push
```

Перейди в свой репозиторий на GitHub и открой пару файлов. Убедись, что JSDoc-комментарии видны прямо в коде на GitHub.

**Стоп. Оглянись назад.** Ты только что:
- Переключился в main
- Не создавал feature-ветку
- Внёс изменения во множество файлов
- Закоммитил и запушил **напрямую в main** — без Pull Request, без ревью, без апрувов

> **Разбор: допустимо ли это?**
>
> Зависит от трёх вещей:
> 1. **Работаешь ли ты один.** Сейчас это твой личный репозиторий — сломать чужую работу ты не можешь.
> 2. **Насколько рискованны изменения.** Документация не меняет логику: тесты зелёные до и после. Добавить докстроки — некритичное изменение; переписать алгоритм — совсем другое.
> 3. **Что принято в команде.** В некоторых командах мелочи (документация, опечатки, форматирование) можно пушить напрямую, но весь код — только через PR и ревью. Правила команды важнее личных предпочтений.
>
> Через код-ревью делай то, что требуется по заданиям модуля. Остальные изменения — на твоё усмотрение; если хочешь, можешь просить у сокурсников дополнительные ревью.

### Правило: JSDoc сразу после заглушки в TDD-цикле

**kind:** `text`

Запомни правило: начиная с этого проекта, **каждая** новая функция должна быть задокументирована в JSDoc **сразу после заглушки**, до начала реализации — это часть TDD-цикла.

Почему именно так? Потому что JSDoc заставляет тебя **сначала подумать о контракте функции**: что она принимает, что возвращает, какие ошибки возможны. Это улучшает дизайн ещё до того, как ты написал первую строку реализации.
