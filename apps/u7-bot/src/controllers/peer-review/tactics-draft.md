## 1. ReviewCampaign: наследование и структура UC

Будущие типы кампаний: `stream_completed` (сейчас), `course_completed`,
`pair_programming`, `code_review`, `exit`. Вопросы: общий агрегат или
иерархия? Общие UC или по типу?

Варианты:

- **A. Один агрегат + `context` + правила по типу** (полиморфизм поведения в
  Policy/Ds). Просто, но агрегат рискует распухнуть от типоспецифичных полей.
- **B. Абстрактный базовый Ar + подклассы** (`StreamCompletedCampaign`,
  `PairProgrammingCampaign`, …). У каждого типа свой UC создания кампании;
  `create-review-uc` — общий (контекст как поле команды).
- **C. Композиция**: общий каркас (окно, участники, прогресс) +
  типизированный `payload` со спецификой скоупа.

Ограничители: ddd-скиллы (aggregate, naming), «Границы агрегатов» (агрегат
не создаёт агрегат — фабрики в UC), сериализация в json-репо (дискриминант
по `context`).

## 2. Данные по типам кампаний (прикидка полей)

### Общее (кандидат в абстрактную часть)

```
uuid, context, scopeId, createdAt
expiresAt            ← вычислен при создании и СОХРАНЁН (см. §3)
participants[]       ← снапшот на момент создания:
    { userId, role: 'student' | 'mentor', studentStatus? }
```

Правила адресатов (общие): `advanced`/`not_advanced` → одногруппники +
ментор; `enrolled`/`abandoned` → только ментор.

### Специфика по типам

| Тип | scopeId | Состав участников | Специфичные данные |
|---|---|---|---|
| `stream_completed` | streamId | студенты потока + ментор | — (чистый случай) |
| `course_completed` | TBD (courseId? userId?) | завершившие курс | критерий «завершил курс» (advanced последнего модуля?) |
| `pair_programming` | sessionId | программировавший + **несколько смотрящих** | роли внутри сессии: кто писал, кто смотрел; смотрящие пишут о программировавшем; пишут ли смотрящие друг о друге — вопрос |
| `code_review` | sessionId | автор кода + ревьюер(ы) | направление: ревьюер → автор (и обратно?) |
| `exit` | studentId+streamId? | ушедший | причина ухода (из события), адресат — ментор/школа |

Открытые вопросы: где живут нестандартные составы (payload vs подкласс);
как для паспорта считать «возможности/сделано» при нескольких смотрящих
(возможности ≠ участники, а разрешённые пары).

## 3. Окно жизни: константы в домене, expiresAt хранить

- Константы — в доменной зоне пакета (не в UI, не в UC-конфигах):
  `REVIEW_WINDOW_DAYS` и т.п.; возможно свои значения по типам кампаний
  (7 дней для потока — утверждено).
- При создании кампании `expiresAt = createdAt + окно` **вычисляется и
  сохраняется**; агрегат даёт `isExpired(now)` — истёкшость читается из
  состояния, не вычисляется на лету в каждом месте (мнение владельца).

## 4. Exit-кампания: перепривязка триггеров и статус «Не начал»

- Сейчас всё на `stream.completed`. План: после завершения текущего потока
  перепривязать создание кампаний на **личные события** студентов:
  `student.abandoned` (уход — приглашение сразу) и `student.completed`.
- Возможное изменение в `stream`: статус студента **«Не начал»** — переход
  только из `enrolled`; сейчас такие студенты при бездействии получают
  «забросил». Влияет на тексты-подсказки (S05) и лейблы.
- Вопросы: кампания на каждого ушедшего отдельно или на поток; окно
  exit-кампании; взаимодействие с кампанией по завершению потока
  (дубль отзывов о менторе?).

## 5. Абстракция пагинации в bot-ui-story

Пагинация нужна: S07 отзывов (ui-spec) и дерево учебной программы
(S03 streams — сейчас тупая обрезка).

Кандидат: хелпер в `bot-ui-story` (core/ui): на входе элементы +
рендерер одного элемента + лимит символов; на выходе — страницы и кнопки
навигации в ту же сторю (кнопки-мосты с параметром страницы).

Критерий «хорошая» абстракция (иначе — не форсировать, локальная пагинация):

- не знает домена (чистая функция элементов → страниц);
- элемент не рвётся посередине (страница наполняется целыми элементами);
- лимит учитывает шапку экрана и клавиатуру (суммарно < 4096);
- переиспользуется минимум в двух местах: отзывы + nav-tree.

Открытые вопросы: где живёт (core-хелпер vs shared бота); адресация страниц
(параметр в callback-коде); поведение вместе с «хлебными крошками»
(листание страниц — edit на месте, не новые сообщения).
